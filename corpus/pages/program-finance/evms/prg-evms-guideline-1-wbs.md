## Purpose

Sets out what the guide requires when a contractor defines the work breakdown structure for a program, and what that structure contains.

## The rule

| Field | Value |
|---|---|
| Instrument | DoD EVMS Interpretation Guide, not a codified instrument [@CL-PRG-0151] |
| Codified citation | Not established. |
| RFO citation | Not established. |
| Edition date | Not established. |
| Text status | Not established. |
| Applies to | Programs for which the contractor must define the authorized work elements [@CL-PRG-0152] |

The guideline asks the contractor to define the authorized work elements for the program and treats a product-oriented structure, tailored for effective internal management control, as the common way to do it [@CL-PRG-0152]. The structure is a product-oriented, hierarchical breakdown of the program requirements [@CL-PRG-0153]. It carries every program element, whether hardware, software, services, data or facilities, and it is cut to lower levels for planning, budgeting, scheduling, cost accounting, work authorization, progress measurement and management control [@CL-PRG-0560].

All subcontracted work scope belongs in it too [@CL-PRG-0154]. The contractor must extend the structure to a level needed for effective internal management control, and that level should not be an arbitrary level set across the program [@CL-PRG-0155]. A single structure serves one contract and reaches the level needed for management action, including intercompany scope as well as subcontracted scope [@CL-PRG-0157].

## How it works

The guideline starts from the authorized scope and asks for one product-oriented structure in which the whole contract, including subcontracted and intercompany work, appears [@CL-PRG-0157]. The guide says a product-oriented structure facilitates data collection and traceability and provides a control framework for work authorization, tracking and reporting [@CL-PRG-0561]. Depth follows the need for effective internal management control rather than an arbitrary level across the program [@CL-PRG-0155].

## Worked example

Synthetic example. The numbers are made up.

A program breaks its scope into 3 product levels and ends with 12 elements at the level where managers authorize work, each carrying hardware, software and data, plus 4 subcontracted elements. The answer is that the structure can be used, because every piece of contract scope, subcontracted work included, appears in it and the depth follows management need.

## Never confuse

A work breakdown structure divides the work by product, while an organizational breakdown structure divides responsibility by organization, and the two are laid over each other when control points are set [@CL-PRG-0159; @CL-PRG-0166]. The structures are not one-to-one, since one organizational element can hold more than one control point [@CL-PRG-0170]. A reporting structure used for cost collection may need to differ from the structure used inside the earned value system for program management [@CL-PRG-0156].

## Company calibration

Whether the company's programs extend the work breakdown structure to the depth their earned value requirement needs, and whether that structure is the one the validated system uses [@CL-PRG-0155; @Q-037]
