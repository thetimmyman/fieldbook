# Control register

Every control that keeps Fieldbook inside its security claims has one row here: what it catches, where it runs, what evidence it leaves, how we know it can fail, and which card or release brings it. The register is the evidence source for the control matrix in the intake pack (artifact 4). It makes no compliance claim. The matrix against NIST SP 800-171 Rev 2 is written separately, from these rows. See [docs/intake/README.md](intake/README.md).

## How to read it

- **Runs** uses these places: pre-commit, pre-push, PR CI, weekly, release, edition build, home, laptop. `weekly (control)` is the weekly run of the negative control itself: it plants the fault again and requires the check to fail, so a check that was switched off in the meantime is found within a week.
- **Negative control** is a test that plants one violation in a temporary copy of the synthetic fixture Corpus (`tests/fixtures/corpus-mini`), or in a synthetic metadata fixture, and expects exactly one failure. A control with no negative control could be switched off without anyone noticing. Rows marked † have a negative control specified by this register; the card that brings the control builds it. The test carries the line `// control: <ID>` within three lines above its `fn`, or the case in `tests/known-bad/cases.toml` carries `control = "<ID>"` ([testing.md](reference/testing.md#controls)); the lint `controls_have_tests` fails a † row of a merged card that has neither. Unmarked rows come from [ADR 0001](decisions/0001-foundation.md).
- **Brought by** names the card by its slug, as listed in [docs/plan/PLAN.md](plan/PLAN.md), or the release (E1, Day 30, Day 60–75, R2). A control is in force once its card has merged and, for a row marked †, the lint `controls_have_tests` finds its test. The tracker holds each card's status, and a merged card's file is deleted. A † row whose Brought by names only a release word (E1, Day 30, Day 60–75, R2) is not read by `controls_have_tests`; the gate of that release lists it. A row gets its card slug in the same edit that adds the `// control: <ID>` step to that card.
- Control ids are stable. A retired control keeps its row, marked retired, with the reason.
- Frozen words (edition, transfer statement, intake pack, day-one binder, context pack) are defined in the README.

## Labels and scans

The tool refuses; it never classifies. A record carries labels: `public`, the company's own labels and the built-ins `unlabelled` and `marked` ([ADR 0004](decisions/0004-company-boundary.md#2-labels)). A fourth built-in, `owner-supplied`, belongs only to text the owner types at a prompt for one request; no page, source version or record carries it. `public` is given by an act (the edition build, a policy source row for a folder inside its `root`, or a typed confirmation to `corpus-add` on a machine with no company store) and never by default. Public text is in git and in editions. A company label is held only in a company store whose `holds` list names it, never in a source repository or an edition, and it leaves a store only through a destination that the company's policy names for it. Controlled unclassified and export-controlled material is held only where the company's own system is authorised for it, and its markings are never stripped, edited or hidden. Fieldbook reads a source's declared label, the file's markings and the policy's rules; it never decides by meaning that something is controlled, and it makes no compliance claim.

These rows are the evidence for IT-30 and IT-33. They make no compliance claim: Fieldbook enforces the company's file and does not judge it, and a label is only as good as the source's label, the file's markings and the company's rules.

## Network silence and code

The silent build (the default, and the only build in an edition) opens no socket, starts no process, contains no model and makes no outbound connection. The AI build (feature `net`) adds outbound HTTPS to endpoints that the company's policy lists and the settings name, only on an explicit command and after the audit record is written. With the further feature `bridge` it also holds, only while `fieldbook chat` runs, one listener on 127.0.0.1 behind a per-session token. `fieldbook mcp` uses standard input and output and opens no socket in any build. Neither build starts a process; only the dev-only `xtask` crate does. First-party crates forbid unsafe code (a compile-time lint), except one file of the leaf crate `fieldbook-win` that makes the Windows system calls (a test fails on `unsafe` anywhere else). deny.toml bans the native crates it lists. Dependencies, the Rust standard library and the platform C runtime remain trusted components; these lints are not a sandbox. The dev-only `xtask` crate is never shipped.

## Critical failures

Ten kinds of failure fail a release whatever the averages. Each has a named control or test, so none can disappear when the regression set uses fewer headings. [SM-02](decisions/0001-foundation.md) requires every row's named test to pass and the regression set to hold zero critical misses (FB0128). A docs lint checks that each control id named here is a row in this register.

## Limits

- **Agent identity.** GS-02 treats a commit as an agent's when its author name ends in `(agent)` or it carries a `Co-authored-by` trailer, so an assistant working in the owner's checkout is judged too. Both are attribution, not proof: it stops mistakes and an unattended agent, not a determined actor. The repository ruleset and the owner's weekly read of merged work are the backstop.
- **What the net-log proves.** It proves the pages and renderable files, loaded in headless Edge with the listed flags, make no request that is not to a local file. It covers the tested edition and the tested interactions only, and says nothing about the laptop's Edge policy, other browsers, or the signed program (NS-04 and NS-06 cover that at R2).
- **What the gate proves.** It proves a request passed the policy check, the marking scan and the audit step, and that the reply was validated. It says nothing about whether a model's answer is right; `cite-check` checks existence and applicable locator/quotation facts, retaining unavailable facts as unchecked, and a person decides what is true.
- **What the policy proves.** Fieldbook enforces the company's policy file and does not judge it. A permissive policy is possible; `policy show` and the `policy.change` events make a change visible, and the policy hash is in every egress event. A label is only as good as the source's label, the file's markings and the company's rules: a wrong source label passes the labeller and the subset test, and the mismatch scan sees only a marking that is in the text. Print and clipboard controls are advisory, because a reader can still select text. Who may read a store is the company's decision: a store whose row names `readers` is not opened for a person outside that operating-system group, and Fieldbook does not authenticate the person, the logon does.
- **What an endpoint keeps.** Retention, logging and training on a prompt are the endpoint operator's. IT-27 asks IT to approve the operator, and the endpoint's row in the policy lists the labels it may receive.
- **What `audit verify` proves.** The journal is intact and in order. It does not prove a call was made only when it says so, and a person with write access to the folder can replace the whole file.
- **What the journal sees.** It records what the program did. It does not record a page opened in Edge, a file edited by hand, or an `xtask` build step; at home git records the Corpus, and on the laptop nothing records a hand edit. A hash chain shows an edit, a removal or a cut-off end; it does not stop someone who can rewrite the whole file. The length and head each backup records, and a head the owner keeps, are the outside copy.
- **Role is declared until there are accounts.** The actor's principal is read from the operating-system token (`os:<DOMAIN>\<user>`); Fieldbook does not authenticate it, the logon does. In the personal build the journal's role (owner, lead, agent) still comes from `settings.toml`, and the accept gate is a terminal. `label add` ignores the role word on the laptop preset: it needs a console, a typed confirmation and, where the store row names one, the `changers` group. Who may read a store is the store's `readers` group. In the shared application the role comes from the company identity (`later-accounts`, `later-roles`). Like GS-02, this stops mistakes and an unattended agent, not a determined person at the keyboard.
- **The core calls no model.** `check`, `build`, `search`, `calc` and the editions never call a model, and no output of theirs depends on one. Only an adapter behind a pipeline port can, and its calls are in the journal.
- **Unsafe code and C.** First-party crates forbid unsafe code (a compile-time lint), except one file of the leaf crate `fieldbook-win` that makes the Windows system calls (a test fails on `unsafe` anywhere else). deny.toml bans the native crates it lists. Dependencies, the Rust standard library and the platform C runtime remain trusted components; these lints are not a sandbox. A docs lint fails any line that says "`unsafe` code" or "C code" without "first-party" or "build graph".
- **Pages without text.** Fieldbook does no OCR. A scanned page has no text to match a quote against; `extraction.toml` lists such pages in `thin_pages`, and FB0223 warns when a consequential claim rests on a version with them. The warning is advisory, and the owner reads the page image in the original.
- **Public PDFs.** Originals are kept byte-exact, as published. Fieldbook records their hash and page count and does not inspect them for active content. They open in the viewer the laptop already uses, under the same policy as any downloaded PDF.
- **Tier-0 integrity.** The out-of-band hash shows the zip matches what the sender built. It does not show who built it. Signing starts at R2.
- **Dependencies.** DP-02 and DP-04 currently combine standard committed-lock Cargo/cargo-deny checks with required exact-source MAX/JEV review under [Review evidence](reference/dependencies.md#review-evidence). The complete DEPS command and replay controls are deferred and unpassed. Usefulness and maintainer health remain the row author's judgement, read in the owner's weekly review.
- **Not claimed.** Fieldbook is not certified under any scheme, and no row here says it is.
