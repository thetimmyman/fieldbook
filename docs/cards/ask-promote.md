# ask-promote

- **Runs where:** home, CI Linux
- **Schema impact:** none
- **Review:** auto

## Outcome

`fieldbook queue review` now ends with the questions to look at: every logged question that got no result, a broken citation or a flag, one screen each. A key turns the question into a `regression_case` proposal (the unit that should have come back) or a `gap_question` proposal (nothing in the Corpus answers it), or dismisses it. The proposal is accepted at once or later with `queue accept`, and the accept appends one `[[case]]` to `corpus/eval/regression.toml` or one row to `questions.csv` in a single atomic write with one journal pair. `queue flag` marks the last answer as a miss and `queue pin` keeps a good answer as a case. Nothing is written without a terminal and a role of owner or lead, and `critical` is set only by a key the person presses.

## Why

- The owner's own questions are the test set; nobody writes a held-out question as a chore. `ask-log` keeps the first-run result of each question, and this card turns the misses into cases and gaps. Control HG-07 (every question that is not a bare id is logged, and `queue review` offers every miss) is finished here, and the gate counts come from the rows ([Gates](../decisions/0001-foundation.md#gates), [controls.md](../controls.md)).
- The regression file protects the ranking, so a case is only ever added. Control HG-08: a promoted case reaches `corpus/eval/regression.toml` only by an interactive accept, in one atomic write with one journal pair, and a person alone sets `critical`. An agent may append a case by commit; the guard of `guard-statuses` (GS-02) bars an agent's edit, removal or `critical` mark, and the negative control of this card proves it.
- "Nothing answers it" is a `gap_question`, not a case. A case must name a unit that exists (FB0126), and a case that the Corpus cannot satisfy yet is a warning (FB0127), which is its purpose. Nobody tunes the ranking to pass a promoted case ([Regression set](../reference/search.md#regression-set)).
- A promotion is a proposal like any other, so it uses the queue, the gate, the journal pair and the order of `review-queue`. The two kinds are rows of the `KINDS` table that `review-queue` created, and each handler is an `Admit` adapter with its `ADAPTERS` row, fixture folder and contract test ([Adding a regression case](README.md#adding-a-regression-case) and [Adding a proposal kind](README.md#adding-a-proposal-kind)).
- `handoff-cite-check` is a precondition because a `cite_failed` row exists only when its check finds a broken citation. `guard-statuses` is one because the negative control commits the file as the agent author.
- No page, template or string shown in a browser is built here, so there is no Design bullet. The Verb map already has the chip for `queue flag`; `queue pin` has none.

## Steps

1. Core, `eval.rs`. `Case` gains `from: Option<String>`, the key `from`, in the form `A-nnnn`; every other unknown key is still refused. Add `next_case_id(&[Case]) -> Option<String>` (`rg-` and three digits, one more than the largest number among the ids of that form, none at 999) and `append_case(text, &NewCase) -> String`, pure. The old bytes are kept exactly; one newline is added if the text does not end in one; then a blank line and the block with the keys in the order `id`, `query`, `expect`, `from`, and `critical = true` only when `NewCase` says so. `top` is not written, because 5 is the default. The query is a TOML basic string with `\"` and `\\` escapes; a control character in it is refused by `RegressionAdmit::plan` (step 5) before this call. The test `append_keeps_the_old_bytes_as_a_prefix` runs on the `corpus-mini` file.
2. Core, `asked.rs` (from `ask-log`). `with_outcome` is the function of `ask-log`; here it is called with `flagged`. Add `with_state(rows, id, state)` (preserves labels and inputs), `open_misses(rows)` (state `open` and outcome `no_result`, `cite_failed` or `flagged`, in file order, which is oldest first), `last_row(rows)` and `is_hashed(question)`. A row whose question is a hash (modes `hash` and `off` give up promotion) is never offered; the screen counts them in one line.
3. `io/asked.rs`. `set_state(id, state, lease: Option<&StoreLease>)` reuses Some or acquires a short write lease for None, then reads the file, changes one row by id and writes the whole file through the atomic helper with the `StateScope` token. It appends no journal event: the file is untracked state, and the `ask` event of the row keeps the first-run outcome. An unknown id is an error that names it. The flagged outcome is set with set_outcome of ask-log, passing None for the standalone queue flag call. Dismissal likewise calls set_state with None. Both helpers use one private rewrite path and never reacquire a borrowed lease.
4. Core, `pipeline/promote.rs`. Typed bodies for the two kinds, read from the opaque table of `pipeline-ports`: `[case]` with `query`, `expect` (one or more unit ids) and, when set, `critical = true` with `critical_by = "person"`; `[question]` with `area` and `text`. Both bodies also have required source_labels and inputs copied from AskedRow, and public_confirmed (false until the home confirmation below). The inputs use the same sorted store/id tables as ask-log, as TOML values here rather than a CSV cell. Preserve these fields when the query text is edited; no field-edit prompt may replace the inputs. `candidate` names no file: `file` is the asked row id, `sha256` is the form `asked::hashed` gives for the question text, and `bytes` is its length. A proposal of these kinds has no `extraction`, `[row]`, `[links]` or `[ai]`. `parse` denies unknown keys and refuses `critical` without `critical_by = "person"`, which checks the claimed origin, not who wrote the file. Only the owner or lead is authorized to set critical through the reviewed acceptance flow; this writable marker does not authenticate a person. `render` writes one fixed key order, and `render(parse(x)) == x` for the two fixtures, which this card rewrites to the typed form.
5. Core, the two handlers, both `Admit`: `RegressionAdmit` with `id()` `regression-add@1` and `GapAdmit` with `id()` `gap-add@1`. `RegressionAdmit` is built with the text of `corpus/eval/regression.toml` and the set of unit ids of the Corpus. `plan` refuses a query that holds a control character (`AdmitError::Invalid`), runs `scan::marking` and `scan::identity` on the query (FB0400, FB0401 as `AdmitError::Invalid`), builds the case with `next_case_id` and `append_case`, parses the new text with `eval::parse`, and runs the FB0126 rule of `check/regression.rs` on it, so a case that `check` would reject is never planned. The list holds one `Rendered` write, built with `PlannedWrite::new` of `pipeline-ports`: the file replaced whole, and the old bytes are its prefix. `GapAdmit` is built with the text of `corpus/registers/questions.csv` and the area codes of `corpus.toml`. A text that starts with `=`, `+`, `-`, `@`, TAB or CR is FB0403; an area that is not a code is `MissingField(area)`. It appends the row in normal form with `core-csv`: `question_id` from the next `Q-nnn` of the view (none at 999), the area, the text, `day_one` false, `status` open and every other cell empty. Both use the complete Admit signature, passing None for extraction, and return `AdmitOutcome::Planned { files, affected }`: regression includes the allocated case reference and gap includes the allocated question reference. Equal inputs give equal files and affected.
6. `kinds.rs`. Add the two `KindRow`s of `review-queue` (step 9), for `regression_case` and `gap_question`. `check_source` finds the asked row, requires it to be `open` and its question to hash to `candidate.sha256`, with labels and inputs matching the body, and otherwise returns FB0820 and the proposal is stale (the row changed or the log was deleted, so the question is not the one proposed). `admit` resolves current effective input labels before planning. For the Corpus it calls the shared label_context with public_confirmed, labels the proposed text under that act and unions the input labels; non-public or unresolved inputs fail Corpus admission. For a regression case, include the expected units as dependencies too. `admit` reads the file through `env.world`, takes the unit ids and the area codes from `env.model`, and returns the handler of step 5. The Corpus is the only content store here; `r2-state-and-journal` puts the match on the store in front of this line. `after_accept` sets the row to `promoted` through `set_state(id, Promoted, Some(lease))`, using the borrowed lease from after_accept; if that write fails it returns `Err("question log not updated: <reason>")`, which `queue accept` prints as a warning, and the exit code stays 0, because the Corpus write has happened.
6a. The registry. Each handler is an adapter. In `crates/fieldbook/src/adapters/registry.rs` add the rows `regression-add@1` and `gap-add@1` (port `Admit`, not the default, `Built`, `Silent`, crate `fieldbook-core`, `Needs::None`, `sees` labelled, suite `admit_suite`). Each has a fixture folder `tests/fixtures/ports/admit/<id>/`: `input.toml` is a copy of `tests/fixtures/queue/regression_case.toml` or `tests/fixtures/queue/gap_question.toml`, and `expect.toml` asserts Planned, the allocated affected case/question reference and the planned path (`corpus/eval/regression.toml` or `corpus/registers/questions.csv`) with the SHA-256 of its bytes, for a run over `tests/fixtures/corpus-mini`. Add `contract_admit_regression_add_1` and `contract_admit_gap_add_1` to `crates/fieldbook-core/tests/pipeline.rs`; each runs its fixture through the handler and through `admit_suite`.
7. `promote.rs`, `look_at(ctx, world) -> Looked`, called by `review` after its last waiting proposal (one call in `queue.rs`). It reads the log, takes `open_misses` and drops any row that already has a waiting proposal (found by `candidate.file` in the headers). It prints `questions to look at: N` and, when some rows hold hashes only, one line that says how many cannot be promoted. For each row the screen shows the id, `via`, the date of `at`, the outcome, the question, what the first run returned (the recorded `top_ids`, or `no results`) and what the question returns today: the five best hits of the same core search that `search` uses, each with its unit id, kind and a title cut at 60 characters [J]. It calls the core function and not the `search` verb, so looking at a question logs nothing. The prompt is `[1-5] should have come back  [i] type a unit id  [n] nothing answers it  [d] dismiss  [s] skip  [q] quit >`. `render_asked` is a pure core function and its output is the golden.
8. A number or `i` makes a `regression_case`. `i` asks for a unit id and checks it against the unit ids (a miss asks again). Then `Query text (Enter keeps it) >` and `Mark it critical? A miss then fails check. [y/N] >`, where only `y` sets it and Enter never does. On the home Corpus path ask `Declare this question public? [y/N]`; only y calls the shared label_context and sets public_confirmed. No answer leaves the question unpromoted. This classifies only the typed text, never its inputs. Build the proposal with the next free number across `queue/` and `queue/done/`, append `queue.propose` first (the shared queue payload: proposal, proposal_kind, labels, optional sha256 and an empty adapters object), write the file, and call the accept function of `review-queue` for it: it runs the pre-checks, prints the path and the added lines, and asks `Write this? [y/N]`. `y` does the ordered write of `review-queue` (`write.begin`, the file, `write.end`, `queue.accept` with `ids` holding the case id) and then `after_accept`. `N` leaves the proposal waiting and prints `kept as P-0012; accept it later with queue accept P-0012`.
9. `n` makes a `gap_question` the same way: `Area code [cmp, est] >` from the codes of `corpus.toml`, `Question for the company, in company-neutral words (Enter keeps the text) >`, then the same public-text confirmation, proposal, accept screen and write. A finding of step 5 is printed on the spot and the prompt is asked again. `d` sets the row to `dismissed` and writes nothing else. `s` leaves it. `q` stops and prints how many are left. The last line is `done: 1 case (rg-031), 1 gap (Q-025), 1 dismissed, 2 skipped`, zero counts left out.
10. `queue flag [A-nnnn]` has no gate and writes only the log: with no id it takes the last row; an `answered` row becomes `flagged` and prints `flagged   A-0007  <question cut at 60>`; a row that is already a miss prints `already a miss (no_result)`; an unknown id is exit 2, an empty log prints `no questions logged yet` and exits 1. `queue pin A-nnnn` runs the gate first (FB0822 without a terminal or with another role), needs an `open` row whose outcome is `answered`, and goes on at the screen of step 7 for that one row. Neither verb calls a model or appends an event of its own.
11. `cli.rs`, `lib.rs`, `queue.rs`: the two subcommands and the hook. Remove `queue flag` from `PENDING` in `tests/chips.rs`; `queue pin` is already in `NO_CHIP`. In `tests/queue.rs` remove `regression_case` and `gap_question` from `NOT_YET_BUILT`. Both verbs are in `DETERMINISTIC_VERBS` already and take the plain `Ctx`. Register its case in `tests/support/chip_cases.rs`: a fresh Home copy keeps the documented empty-log result, `no questions logged yet` with exit 1, which is a findings outcome and not a refusal.

## Negative control

In the temporary folder, run `"$B" --state "$S" queue flag A-0001`: it must print `already a miss (no_result)` and the row must keep its outcome. On the branch, make `append_case` write `critical = true` by default: `case_is_not_critical_unless_the_key_was_pressed` must fail. Restore it. Skip the FB0126 rule in `RegressionAdmit`: `unknown_expected_id_is_fb0126` must fail. Restore it. Skip the scans: `marking_in_the_query_is_fb0400` must fail. Restore it. Let `queue pin` skip the gate: `pin_needs_a_terminal` must fail. Restore it. Set the asked row to `promoted` before the write: `row_is_marked_only_after_the_write` must fail. Restore it.
