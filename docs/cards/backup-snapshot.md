# backup-snapshot

- **Runs where:** home, CI Linux, CI Windows
- **Schema impact:** none
- **Review:** auto

## Outcome

`fieldbook backup [--target ID] [--to DIR] [--dry-run]` copies every root of the layout into a new snapshot (at home the Corpus and the state folder; the laptop roots are added by `r2-state-and-journal`), a plain folder `fieldbook-backup-NNNN/` with `backup.toml`, `SHA256SUMS` and `data/`, in a folder target. It hashes each file as it reads it, verifies the copy, and writes `LATEST` last. `backup verify` re-hashes a snapshot (with `--raw`, a plain copy made by another tool) and `backup list` shows the snapshots with their age. The newest 7 snapshots and the newest of each of the last 4 weeks are kept, and an older one is removed only after a newer one has verified. In the silent build and the AI build alike, `backup` and `restore` start no process, install no scheduled task and make no network connection. A snapshot carries a `labels` set, the union of the labels of the items it copies, and is preflighted against its target, then bound to its exact output Delivery by `egress::check` (destination kind `backup`, [ADR 0004](../decisions/0004-company-boundary.md#6-destinations)): a snapshot that holds a `marked` item is refused (FB0901), and so is one that holds an `unlabelled` item, except on a machine with a company store and no policy, where a target that the owner marked `company_storage = true` in `settings.toml` takes it; and with a policy loaded a target that is under no `backup` row's `paths` is refused (FB0918). The target is also tested by the place test (`World::place`): at home a target in a folder that a sync client watches is a warning (FB0813), and on a machine with a company store it is refused (FB0415) unless a `backup` row's `paths` names it (the table in step 5); the result is journaled with the write. The company chooses the target and the retention. After a write verb succeeds, one line on standard error reminds the owner when no verified backup exists or the newest is older than `warn_after_days`; the exit code does not change and `build`, `check` and `search` never print it.

## Why

- What the program backs up, the snapshot layout, the targets and the retention rule are the backup bullet of [AD-16](../decisions/0001-foundation.md#ad-16-release-2-shell-and-its-gate) and control DR-02 in [controls.md](../controls.md); the codes FB0810 to FB0814 are in [08: audit, backup and pipeline](../reference/corpus-format.md#08-audit-backup-and-pipeline). The statement IT receives is section 5 of [data-handling.md](../intake/data-handling.md), and IT-26 in [it-questions.md](../intake/it-questions.md) asks where the copy should go.
- A snapshot is a folder of plain files and not a zip, so a person can restore it by copying in Explorer, IT's agents handle it, and `backup verify` still runs on a damaged copy. It is a full copy each time. The manifest is made from the bytes that were copied, so a file edited by hand during the copy cannot make it lie. `SHA256SUMS` is written by `manifest::write_sums` of `edition-zips`; there is one implementation.
- `BackupTarget` is a port with one default, `folder@1` ([Ports](../decisions/0001-foundation.md#the-architecture-in-one-page)). Its trait is in core and the folder target is in `io`, so the exe has no other way to write a snapshot. A network target or an incremental one is a swap behind the same trait (`later-network-backup`, `later-incremental-backup`); this card builds neither.
- A snapshot is the one output that copies a whole tree, so the label rule is applied to the union of what it holds ([ADR 0004](../decisions/0004-company-boundary.md#6-destinations), Backup). The failure it prevents: a snapshot of company records written to a share the company has not approved for them. The way to have company data backed up is a `backup` row in the company's policy that lists the target's `paths` and the labels it may hold. On a machine with no company store the floor allows `public` and `owner-supplied` only, so at home the question log is copied (Drill 4). On a machine with a company store and no policy, the one narrow route is a target that the owner marked `company_storage = true` in its `[[backup.target]]` table of `settings.toml`, which may also hold `unlabelled` and never `marked`; nothing else is backed up, and a store that holds a `marked` file is not backed up by the tool until a policy maps the marking and `label reapply` has run (FB0901, with the count). A snapshot copies every root of every configured store and is labelled by exclusion: every file it copies must be of a known kind with a declared label, and a stray file adds `unlabelled`. Only a validated, known text-free control schema adds no label: the journal, locks, sync cursors, backup metadata, validated metadata-only reports and reference-only named-pack indexes. `.packs` here means a pack index that holds only its name, ids and view fingerprint, or a report that holds only its validated metadata fields; a pack body, a Handoff ticket or any other text-bearing sidecar is a labelled kind that keeps the union of its saved labels and current effective-input labels. A filename pattern alone proves nothing; text-bearing sidecars are labelled and an unknown or malformed kind adds `unlabelled`.
- This is a Must that sits outside the floor ([Cut line and floor](../decisions/0001-foundation.md#cut-line-and-floor)). If it is cut, `edition-001` ships with the written Tier-0 copy steps and the `Get-FileHash` comparison of [transfer.md](../runbooks/transfer.md) as the backup, and the card ships in a `v0.1.x` patch before Day 30. The journal is still on disk.
- No page, template or string shown in a browser is built here, so there is no Design bullet. The Backup status page (`status-command`) reads `backup list --json`.

## Steps

1. Core, `backup/plan.rs` and `backup/retention.rs`, pure and without a clock: `plan_backup(listing, include, next_number) -> BackupPlan` (the files to copy in byte order of path, with the roots `corpus` and `state` at home), `plan_retention(snapshots, newest_verified, keep_last, keep_weekly) -> Vec<Number>` (the newest `keep_last`, plus the newest of each of the last `keep_weekly` calendar weeks; never the newest verified; never fewer than 2 if 2 exist; only entries that carry their own `backup.toml`), the place test of a target, which judges the `PlaceFacts` of `core-labels` with `labels::placement` (the facts come from `World::place`, which step 3 adds; this card keeps no list of folder names) and `path_budget(target, longest_relative)`, which refuses a target whose longest staged `fieldbook-backup-NNNN.partial/data/...` path (including the temporary suffix) would pass 260 characters and names the shortest working root. The limit applies on every platform, so a snapshot made at home restores on the laptop. Also in `backup/labels.rs`: `snapshot_labels(files: &[CopiedFile]) -> LabelSet`, pure, labelling by exclusion. `CopiedFile { path, kind, labels }` is made by `io` for every file the copy will contain. Under the coherent store lease, the caller parses each known kind and resolves its effective labels against the loaded graph before constructing this value; snapshot_labels only unions those resolved values and applies the control/stray rules. `kind` is a validated PendingWrite (its write-set labels and current referenced-file labels; unresolved references add unlabelled), a page, a source version, a record, an original, extraction text, a queue proposal, a question-log line, a call record, a Handoff pack (`handoff/H-nnnn.txt`, labelled by the saved labels and current effective inputs of its ticket `handoff/H-nnnn.toml`), the label ledger, a validated known text-free control file (journal, locks, sync cursors, backup metadata, validated metadata-only reports and reference-only named-pack indexes) or `Stray`. The set is the union of the labels of the files of a known kind (`labels::effective_item` over the full provenance graph for a page, source version or record, including its handling and ledger; the saved own labels plus current effective input labels of a proposal, a question-log line, a call record or the ticket of a Handoff pack; a kind with no derived inputs supplies an empty input list). A typed control file adds nothing only after its exact known schema validates; a glob such as `handoff/*.toml` never grants that status, and a pack body is the Handoff kind above rather than a control. A later card that writes text-bearing metadata registers its labelled kind and tests its real backup path in that same card. Until then it is Stray, as is malformed control metadata. A `Stray` file, which is a file that fits no kind (a stray file in a root, anything in `working` that is not a page or an original), adds `unlabelled`. A derived folder (the site, the index, and `pages/` and `drill/` of the state folder, judged by the path from the root and not by the folder name) is not copied at all. `corpus/pages/` is Corpus content and is copied. For a nonempty selection made entirely of known, validated text-free controls, the result is `LabelSet::public()`. Otherwise union the resolved labels; unknown or malformed files contribute `unlabelled`. Ordinary empty-set normalization is unchanged.
2. `backup/toml.rs`: `BackupToml` with `backup_version = 1`, `tool_version`, `snapshot`, `created_utc`, `labels` (a sorted list of label ids), `roots`, `files`, `bytes`, `fingerprint`, `journal_seq`, `journal_head`, `journal_state` (`ok` or `broken`) and `manifest_sha256`. It parses with unknown keys denied, through `BackupToml::parse(text)`. `fingerprint` is `manifest::fingerprint` of `edition-manifest` over the pairs (`corpus/<path>`, SHA-256) taken from the `SHA256SUMS` lines for `data/corpus/` at backup time, in the order of the fingerprint rule of [Scope and versioning](../reference/corpus-format.md#scope-and-versioning). `backup/mod.rs` has `corpus_entries(sums: &str) -> Vec<(String, String)>`, pure, which gives those pairs from the text of a `SHA256SUMS`; `backup` and `restore` both call it, so there is one input, and this card reads `manifest.rs` and does not change it. `backup/target.rs`: the trait `BackupTarget` with list/read/remove and `begin`, returning data or typed errors. `begin<'a>(&'a self, snapshot: u32, allowed: &'a Allowed) -> Result<Box<dyn SnapshotStage + 'a>, BackupError>` refuses an occupied snapshot and retains the delivery token. `SnapshotStage::write(&mut self, rel: &Path, bytes: &[u8]) -> Result<(), BackupError>` accepts only the approved relative file/hash, and `finish(self: Box<Self>) -> Result<(), BackupError>` syncs the files, renames partial to final, then updates LATEST atomically. The I/O adapter is constructed with World and the matching Audited token, which every mutation uses; neither core trait mentions binary I/O types. A dropped/failed stage never advances LATEST. One file is in memory at a time, as in add. FolderTarget::write_snapshot orchestrates these operations.
3. `io/state.rs` reads `[backup]` (`default`, `warn_after_days = 7`, `keep_last = 7`, `keep_weekly = 4`) and each `[[backup.target]]` (`id`, `kind` of `folder`, `it-location` or `synced`, `path`, `include`, and `company_storage`, a switch that is false when absent) from `settings.toml`. These two tables are read here with their own check, and an unknown key in them is FB0812 naming the key. `BackupSettings::parse(text)` in `io/state.rs` does the reading: it is pure, reads only these two tables and is `pub` for the test of step 11. The refusals in step 4 apply before anything is written. In `crates/fieldbook-core/src/backup/mod.rs` define `pub const BACKUP_TARGET_TEMPLATE: &str = "[[backup.target]]\nid = \"main\"\nkind = \"folder\"\npath = \"<a folder outside the Corpus and the state folder>\"\n";`, the one text of the lines to add (`status-command` prints the same constant). With no target, `backup` prints `no backup target; add this to settings.toml in the state folder:` and the template on standard error, and exits 2. `--to DIR` is a one-off target of kind `folder` with `company_storage` false. This card reads `company_storage` and passes it to `egress::check` as `Dest::Backup { path, company_storage }`; nothing else in this card uses it. `lib.rs` adds the method `World::place(path) -> PlaceFacts` to the trait, with the `PlaceFacts { reparse, sync_root, network }` of `core-labels`. `Disk::place` in `io/mod.rs` calls `io/win.rs` (`windows-facts`), which reads the reparse tag or junction, the cloud-file attributes of a sync client or a sync-root registration, and a network drive or UNC path on Windows, and answers every fact false elsewhere. `TestWorld` of `audit-journal` returns the facts that a test sets with `set_place(&Path, PlaceFacts)` for a path, and none for any other. `FaultyWorld` forwards `place` to the world it wraps.
4. `io/journal.rs`: `Journal::begin_backup(allowed, target, kind, snapshot)` appends `backup.begin` with `dest` (`backup`), `labels` and `policy` taken from the `Allowed` token, and returns the `Audited` token that `io::atomic` needs, and `Journal::end_backup(token, outcome)` appends `backup.end` with `files`, `bytes`, `manifest_sha256`, `journal_seq`, `journal_head`, `fingerprint` and `target_kind` (the folder/it-location/synced value supplied to begin_backup). The run holds the exclusive store lease and journal lock, so no `write.begin` is open during the copy. `journal_seq` and `journal_head` are those of the `backup.begin` event, which the copy contains. Before `begin_backup`, `backup.rs` computes `snapshot_labels` and calls `egress::check(&eff, &Dest::Backup { path: target, company_storage }, Some(&labels), None, now, shipped)` and the place test for the target (`target_place`, step 5). `eff` is the `EffectivePolicy` that `run_backup(world, &eff, &options)` receives. Until `policy-load`, the dispatcher in `lib.rs` passes `EffectivePolicy::floor(false)` (`core-policy`), and `policy-load` replaces that call with the run's own policy. On a deny it appends `refuse` (`dest` `backup`, `labels`, `reason` of `unlabelled`, `marked`, `label`, `no-row` or `place`), prints the code (FB0901, FB0918 or FB0415) with the count of items that cause it and no title, writes nothing and exits 2 for FB0901 and FB0918, the codes that the 09 table gives Exit 2. FB0415 and FB0812 are findings-class refusals and stay exit 1. The text of the refusal names the way out. For `unlabelled` items it is a real label (the policy's `[[source]]` default rules do it at intake, and `label add` does it by hand). For `marked` items it is a `[[marking]]` rule in the policy that maps the marking, and then `label reapply`, because `label add` leaves `marked` in place. For a target that no `backup` row names, it is a row that names it. FB0918 is decided here, in process, so its known-bad file names a test and not a planted tree (step 8).
5. `io/backup_folder.rs`, `FolderTarget` (id `folder@1`): refuse a target inside a folder it backs up (FB0812), apply the place rule of the table below through `target_place(laptop, kind, facts, declared)` in `backup/plan.rs` (pure; `laptop` is true when the layout has a company store, which only `r2-state-and-journal` makes true, and `declared` is true when a `backup` row's `paths` names the path), and in every case record the kind in `backup.end`. Before `begin_backup`, prepare its exact event bytes under the journal lock (`Journal::prepare_backup_begin` returns the encoded event, sequence and head without appending). Plan the snapshot journal with those bytes included, its sums and manifest, `LATEST`, the partial and final paths, directory creation, cleanup, rename and retention operations as one Delivery. Check it with `Some(&labels)` and `Some(&delivery)` using the same policy snapshot, time and export age. Only the final Allowed goes to `begin_backup` and the folder target. `begin_backup` checks that the journal head is unchanged and appends exactly the prepared event; a changed head invalidates the plan before output. A refused-tail snapshot plans the unchanged journal and uses the recovery-only Audited scope defined below. Copy each file into `fieldbook-backup-NNNN.partial/data/` with `write_outside(&Allowed, ..)`, hashing as it reads; write `SHA256SUMS` with `manifest::write_sums`, then `backup.toml` last inside the partial (a folder without `backup.toml` is incomplete); re-read the partial and compare; rename it to `fieldbook-backup-NNNN` with `dirs::rename_dir_outside` (`io/dirs.rs`, made by `build-v0`); then write `LATEST` (the number and `manifest_sha256`) last, through `write_outside`. A `.partial` left by a crash is removed by the next run with `dirs::remove_outside` (`PartialSnapshot`) and is never listed. No `World` method and no `FaultyWorld` line is added for a folder operation. `include = ["audit"]` copies only `state/audit/`. There are two cases of a broken chain. A break earlier in the file does not stop appends: `backup` runs as for a clean journal, records `journal_state = "broken"` and exits 1. A last line whose hash does not match makes `Journal::open` refuse every append: `backup` still writes the snapshot and `SHA256SUMS` (a snapshot of a broken journal is better than none), skips `backup.begin` and `backup.end`, records `journal_state = "broken"` with the `journal_seq` and `journal_head` of the last line that chains (0 and 64 zeros when none), prints the refusal and exits 1. A lock held by another process is not a broken chain: `backup` is refused with exit 3 and writes nothing. The way out of a broken chain is `audit verify --repair` (`audit-journal`); backups continue meanwhile.

   | Layout | Plain folder | IT-approved location (`kind = "it-location"`) | Synced path (a sync root; on the laptop a reparse point too) |
   |---|---|---|---|
   | Home, no company store | none | none | FB0813 warning; a one-line notice when the target says `kind = "synced"` |
   | Laptop, company store | none | none | FB0415 error, exit 1, nothing written, unless a `backup` row's `paths` names the path, then none; `kind = "synced"` does not lift it |

   The company decides which sync root its machine may use, so on the laptop only a policy row declares one; at home the owner's own `kind = "synced"` only turns the warning into a notice. A network location is valid in both rows. The `refuse` event for FB0415 has the reason `place`. Each of the six cells has a test of `target_place` (step 9).

6. `backup.rs` and `cli.rs`: `backup verify [--target ID | --in DIR] [--snapshot N] [--raw PATH]` checks `backup.toml` against `SHA256SUMS` (a listed file that is absent, an unlisted file under `data/`, a wrong count or a wrong `manifest_sha256` is FB0811), re-hashes every file (a missing file or different bytes is FB0810, one line per file), and checks that the snapshot's journal reaches `journal_head` at `journal_seq` (FB0802). It appends `backup.verify` and prints `snapshot N verified`. `--raw PATH` checks a plain copy of the data folders made by someone else's tool: the journal chain, the originals against their registers (FB0211) and the extraction hashes (FB0212), with no manifest. With `--raw`, the paired optional flags `--support-catalogue FILE --expect-support-sha256 HEX` perform the public support verification of [Public support verification](../reference/audit-contract.md#public-support-verification) after that ordinary check; both flags are required together and only with `--raw`, any numbered-snapshot selector combined with either is usage exit 2, and a missing or invalid digest never falls back to plain raw verification. Ordinary raw success still prints only `raw copy consistent` and assigns no public provenance. `backup list [--target ID | --in DIR] [--json]` prints the number, `created_utc`, age in days, files, bytes, `journal_state` and whether it has a `backup.verify`; `--json` prints one document, `report_version` first:

     "keep_last": 7,

       {
         "snapshot": 3,

   The snapshot keys are the `backup.toml` fields (`snapshot` is the number, an integer). `verified` and `verified_utc` come from the newest successful `backup.verify` matching that canonical target hash, snapshot number and validated manifest hash in the journal; a snapshot with none has `"verified": false` and no `verified_utc`.
