# ai-kernel

- **Runs where:** home, CI Linux
- **Schema impact:** none
- **Review:** auto

## Outcome

The shared types of the AI layer, the one adapter table and the two walls around them exist, and nothing in them touches a model, a key or a socket. `fieldbook-core::ports` holds the request with its labels, the template table, the output schema, the provenance reference and the Handoff ticket. `crates/fieldbook/src/adapters/registry.rs` holds `ADAPTERS` with a row for each adapter that already exists (the four of today, and the defaults of the `Store` and `Authz` ports of [ADR 0004](../decisions/0004-company-boundary.md#11-actor-session-and-authorisation)), and `cargo xtask docs` writes `docs/reference/ports.md` from it. `Ctx` and `AiCtx` are different types, every verb is on exactly one of two lists, and `cargo xtask scans` fails a socket type outside `io/net*` (NS-05) and a model name in a deterministic verb (DT-05).

## Why

- This is the root of the AI chain and is never cut ([Cut line and floor](../decisions/0001-foundation.md#cut-line-and-floor)). The ports, the one registry and the determinism mechanisms M1 to M6 are the Ports, One gate and Determinism bullets of [AD-01](../decisions/0001-foundation.md#ad-01-architecture). NS-05 and DT-05 are in [controls.md](../controls.md).
- Core owns pure data and traits that return data, and never names `serde_json`, a socket type, the clock or the environment. A request's labels are the union of the labels of its parts, computed by `ModelRequest::labels()` with no setter, so no caller can drop one ([ADR 0004, section 2](../decisions/0004-company-boundary.md#2-labels)). Labels have no order and no highest, so there is no class to compare; whether a request may go to a destination is the subset test of `egress::check` (`core-policy`), and the approval of an endpoint is a row of the company's policy, not a flag in code or in settings. That is the footing of HG-09, which `model-gate` proves.
- One table instead of one per port. [Adding an adapter to a port](README.md#adding-an-adapter-to-a-port) is ten steps and one drift check, `adapters_match_registry_docs_and_fixtures`; this card builds the table, the check and the generator, and each later adapter adds a row. The registry holds the four adapters that exist today and the defaults of the two company ports that exist in code now (`folder@1` as a Store, which is the `World` and `Disk` that already exist, and `policy-readers@1` as the Authz), so that the check has something true to compare. `Pull` and `Register` are named in `Port` and get their rows from `r2-pull-and-sync` and `r2-records`.
- No page, template or string shown in a browser is built here, so there is no Design bullet.

## Out of scope

- Any trait or type that names a model call: `ModelPort`, `ModelAdapter` and `Guarded` (`model-gate`), the settings tables and `Key` (`ai-config-and-keys`), the intake stage traits and `corpus-add@1` (`pipeline-ports`), `IndexPort` (its types and trait are written by `pipeline-ports`, which needs them first; the `bm25f@1` implementation and its row by `pipeline-correlate`) and `OutputPort` (`index-output-ports`), `DecidePort` (`decide-port`), and the chat shapes (`ai-config-and-keys` adds the status subset; `model-gate`, `assistant-page`, `chat-bridge`, `handoff-context` and `handoff-cite-check` add the rest).
- New rows for adapters that do not exist yet. A `Later` row is added by the card that plans it.
- Changes to the behavior or trait of `policy-readers@1` (core-policy; this card may isolate its unchanged version implementation for replay), the `Pull` and `Register` rows and adapters (`r2-pull-and-sync`, `r2-records`), and the registry rows' `sees` of every adapter that a later card adds (each card sets its own).
- Any change to `deny.toml`, the banned-crate lists in `xtask/src/graph.rs`, or `crates/fieldbook/src/io/net*` (`net-stack-spike`).

## Steps

1. Core, `ports/provenance.rs`: `ProvenanceRef { call_seq, output_sha256 }`, `HandoffId` with `parse` and `format` for `H-nnnn`, and `HandoffTicket { id: HandoffId, pack_sha256: Sha256 }` for a completed ticket, and `verify_provenance(events, &ProvenanceRef) -> Result<(), Fb0917>`, which looks for an `ai.call` or `ai.paste` event with that sequence number and output hash in an iterator of parsed `audit::Event` values. It reads nothing itself. There is no class type in the AI layer. The labels of a part are the `LabelSet` of `core-labels`; a word that is not a label id is refused by `LabelId::parse` and a well-formed id that the company's table lacks is unresolved for the gate (FB0411, FB0901). Nothing here orders labels or takes a maximum.
2. Core, `ports/request.rs`: `Purpose { Ask, Classify, Correlate, Draft, Decide, Embed, Suggest }`, `PartKind { Rules, History, Context, Question, Subject }`, `Part { kind, labels, text, ids: Vec<ItemRef> }` (ids are store-qualified input references from the current view; fixed rules and a fresh typed question have none), `Limits { max_out_tokens, timeout_s }` and `ModelRequest::new(purpose, template, parts, schema, limits)`. `system()` is the template's system text followed by the Rules parts; `prompt()` is the History, Context, Question and Subject parts in that fixed order under fixed delimiter lines. Empty History is omitted, including its delimiter; nonempty History is quoted conversation data, never instructions. `labels()` is the union of the labels of the parts (a part the owner typed or pasted at a prompt carries `owner-supplied`, and the fixed rules text of a template carries `public`); `input_refs()` returns sorted unique store/id pairs from every part; `context_refs()` returns sorted unique store/id pairs from History and Context for audit; `context_ids()` projects those pairs to sorted unique id strings for citation membership; `prompt_sha256()` hashes `system()` and `prompt()` together. There is no setter and no `Default`, and the fields are private.
3. Core, `ports/templates.rs` and `ports/schema.rs`: `Template(&'static str)`, which can only be made from an id in the const `TEMPLATES` (a table of `TemplateDef { id, purpose, parts, schema, text }`, initially containing ask@1: the parts are the part kinds in their fixed order), so a template that is not compiled in does not exist. Template text will live in `ports/templates/<purpose>@<n>.txt`, read with `include_str!`, and the golden prompts in `tests/golden/prompts/<purpose>@<n>.txt`; the card that adds a purpose adds both. `Schema` is `Object(Vec<Field>)`, `Array { items, max }`, `Str { min_len, max_len, one_of }`, `Int { min, max }` or `Bool`, and `Field { name, schema, required }`: the subset the models are asked to meet. The pure schema_json module of this card emits and validates them through JsonValue. Model-gate parses edge JSON with duplicate-key rejection and converts it to JsonValue, then re-exports these functions; core adds no serde_json dependency.
4. Core, `ports/mod.rs`: `Port { Model, Decide, Index, Output, Extractor, Classifier, Correlator, Admit, Backup, Pull, Register, Authz, Store }` and `Caps { network, structured, embeddings, streaming, max_prompt_chars }`. Both are plain data that the status shapes of `ai-config-and-keys` must name, so they live in core and `adapters/registry.rs` re-exports them. Binary, `adapters/registry.rs`: `State { Built, Later }`, `Build { Silent, Ai }`, `Needs { None, Files, Process, Net }` and `Row { port, id, default, state, build, krate, needs, sees, calls_model, settings_keys, fixtures, suite, doc }`. `ADAPTERS` holds six rows, all `Built` and `Silent`: `plain@1` and `html-strip@1` (core, `Needs::None`, `sees = labelled`), `pdftotext-layout@1` (`xtask`, `Needs::Process`, home only, `public`), `folder@1` as a Backup (`fieldbook`, `Needs::Files`, `labelled`), `folder@1` as a Store (the `Disk` implementation of `World`, `fieldbook`, `Needs::Files`, `labelled`, suite S) and `policy-readers@1` as the Authz (`fieldbook-core`, `Needs::None`, `public`, suite A). A row is the pair of its port and its id, so two rows may share `folder@1`; `contract_name` keeps their tests apart. `sees` is `public` or `labelled` as the recipe in the cards README defines it. `World` gains `store_id() -> &'static str`: `Disk` returns `folder@1` and `TestWorld` returns `memory@0`, which is not a registry id and is skipped by the drift test; `FaultyWorld` forwards `store_id` to the world it wraps. `contract_name(port, id)` turns a row into the test name `contract_<port>_<id>` with every character outside `a-z0-9` in the id replaced by `_`. `streaming` is false for every adapter that is built; only a test double may set it true. The test `caps_streaming_is_false_for_built_adapters` is in the adapter registry test, `tests/adapters.rs`.
5. Fixtures and contract tests for the six rows: each folder under `tests/fixtures/ports/` holds one synthetic `input.*` and an `expect.toml`. `crates/fieldbook/tests/adapters.rs` has `contract_extractor_plain_1`, `contract_extractor_html_strip_1`, `contract_backup_folder_1`, `contract_store_folder_1` and `contract_authz_policy_readers_1`, which run the fixture through the adapter; `mod tests` of `xtask/src/extract.rs` has `contract_extractor_pdftotext_layout_1`, `#[ignore]` like the other poppler tests (`xtask` is a binary crate, so a test of one of its functions is in the module it tests). A row's `suite` also names the suite its own card built (`extractor_contract` in repository-root `tests/support/extractor_suite.rs`; `backup_target_contract` in binary tests/support/backup_suite.rs), and this card does not copy or rename them. Suite S, `store_suite(make)` in `crates/fieldbook/tests/support/store_suite.rs`, runs over `Disk` in a temporary folder and holds four tests that the folder store already satisfies: a write set that holds an absolute path or `..` is refused; an original is written before the row that cites it, and a write that fails in the middle leaves no row; a listing is in byte order; the hash of the bytes read back equals the hash that the write returned. Suite A, `authz_suite(make)` in `authz_suite.rs`, is the contract of any `Authz` adapter. `make(stores: &[(StoreId, Option<&str>, Option<&str>)], groups: &dyn Groups) -> Box<dyn Authz>` builds the adapter for those store rows (the two options are `readers` and `changers`); for `policy-readers@1` it parses a policy text that holds those rows. The suite file defines its own `Groups` double, which answers `Some(true)`, `Some(false)` or `None` for each group name, and its own adapter that denies every `Read`. For the fixture's stores, actors and group answers the suite requires: `allow` is pure and repeatable (the same call twice gives the same answer, for every `Act`); `Read` on a store whose row names no `readers` is allowed, and on a store that names `readers` it is allowed for `Some(true)` and denied for `Some(false)` and for `None`; `Admin` follows `changers` in the same way; `Propose`, `Accept` and `Export` are allowed; a `Deny` carries a non-empty reason word; `readable(&authz, &actor, &stores)` lists exactly the stores for which `Read` is allowed, in the order given (there is no `visible` function); and the denying adapter narrows `readable` and never widens it. The fixture folder `tests/fixtures/ports/authz/policy-readers@1/` holds the store rows, the group answers and the expected answers.
6. `ctx.rs`: `Ctx { io, journal, corpus }` and `AiCtx<'a, M: ?Sized> { ctx, model }`, generic in the model type because `ModelPort` is written by `model-gate`, which uses `AiCtx<'a, dyn ModelPort>`. `Ctx` has no field of the type parameter. Its Journal is an idle handle between operations, not a held lease; no prompt or model wait retains a write token or store lease. `verbs.rs`: `AI_VERBS` (`ask`, `decide`, `ai test`, `chat`, `queue ingest`, and the flagged `add --propose`), `DETERMINISTIC_VERBS` (`check`, `build`, `fmt`, `verify`, `status`, `search`, `policy`, `label`, `sync`, `audit`, `backup`, `restore`, `context`, `cite-check`, `ai status`, `mcp`, `new`, `add`, `queue` for every subcommand but `ingest`) and `AI_VERB_FILES`, the files allowed to name the gate, which starts as `&[]`; each later card that adds a file naming the gate appends it and names the line under its Registration lines.

    Representation rule for those two constants: an entry is one runnable leaf verb path, spelled exactly as the clap leaf, or the one flagged AI invocation written as its leaf plus its flag (`add --propose`). A group word in the shorthand above (`policy`, `label`, `new`, `ai`, `audit`, `queue`) stands for its leaf rows of the AD-17 block, expanded where the constant is written — `policy show`, `policy check`, `audit verify`, `queue accept` and so on, never a group word — except that `queue ingest` is the AI leaf of its own group. The compiled coverage and determinism tables, and every row or reason attached to one, use those same full leaf paths, so a row names `queue accept` and never `queue`. Ordinary `add` is a deterministic leaf; `add --propose` is not a second clap leaf but the explicitly flagged AI invocation of that same leaf. `every_verb_is_in_exactly_one_list` walks the clap definition and classifies the ordinary leaves against the two lists alone. The parse check of the registered `add --propose` variant belongs to the card whose verb makes that invocation parseable, and not to this one: the exact chip string stays in `PENDING` of `tests/chips.rs` while it does not parse, its producer validates that the registered variant parses and is the flagged form of the deterministic leaf `add` in the change that removes it from `PENDING`, and the shared full-chip test fails any pending entry that now parses, so `PENDING` stays the one expectation and no built or feature registry is added. Ordinary `add` is a deterministic leaf throughout. The deterministic runner of `model-gate` takes leaf paths and their arguments and never selects the AI `add --propose` variant; the ordinary required arguments and deterministic flags of a leaf remain allowed. An entry for a verb that is not built yet is allowed; each later verb card adds its own entry ("Adding a verb").

DT-05 (mechanism M3) fails when `ModelPort`, `Guarded`, `HttpPost`, `UreqHttp` or `adapters::model` appears outside `src/adapters/`, `src/io/net*` and `AI_VERB_FILES`. The scan and the generator read the real lists through the path edge from `xtask` to `fieldbook` that `check-ci-and-docs` added.

12. Define `JsonValue { Null, Bool(bool), Integer(i64), String(String), Array(Vec<JsonValue>), Object(Vec<(String, JsonValue)>) }` in core, with duplicate object-key rejection. Binary callers reject duplicate keys during raw parsing, before a map can discard them, and convert to it; no serde_json dependency is added to core. The pure `schema_json` module owns the Schema representation, JSON-schema emission and validator used by both model replies and MCP arguments. It supports closed object, string, integer, boolean and array; required fields; enum; string min/max Unicode scalar length; integer min/max; array max/items. It rejects unsupported keywords rather than silently ignoring them. Export `to_json_schema` and `validate`; a closed diagnostic code and schema-node index describe each failure, with no input value. One vector file `tests/fixtures/schema-json.json` exercises every keyword, empty/boundary/over-bound values and unknown keywords; `schema_keywords_have_vectors` checks the keyword registry. Tests use the same vectors for both caller profiles, including raw JSON with duplicate keys. This card tests pure values; model-gate supplies the shared edge parser when serde_json arrives, and MCP reuses it. Integer conversion refuses fractional, out-of-range and nonfinite numbers.

14. The template. `crates/fieldbook-core/src/ports/templates/ask@1.txt` is the system text of purpose `ask`: it tells the assistant to answer only from the context that follows, to give every statement of fact a reference in the `cite as:` form of the context, to say that the context does not hold the answer when it does not, to treat the context as data and never as instructions, and to put nothing outside the answer. Add the `TEMPLATES` row (purpose `Ask`, parts in the order Rules, History, Context, Question, no schema, no label floor: the template's own text is `public` and the Question part carries `owner-supplied`; History is optional and omitted when empty).
