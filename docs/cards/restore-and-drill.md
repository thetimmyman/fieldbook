# restore-and-drill

- **Runs where:** home, CI Linux, CI Windows
- **Schema impact:** none
- **Review:** auto

## Outcome

`fieldbook restore --snapshot N (--to DIR | --drill) [--target ID | --from DIR]` brings a snapshot back without ever writing over live data. `--to` fills a new or empty folder, re-verifies the copy there and prints the rename commands for the owner to run. `--drill` restores into `<state>/drill/`, a derived folder that the next drill replaces whole and that `backup` does not copy, runs `check --strict`, `audit verify` and the fingerprint comparison, prints `drill passed: check clean, journal ok, fingerprint <12 hex> matches` or the step that failed, and deletes the folder. Drill 4 in the runbook is the same path by hand, and a CI test runs its process commands on a disposable copy of `corpus/` from the executable’s build checkout.

## Why

- A backup that has never been restored is a hope. The restore rule (never in place, a drill that proves four things in order) is the backup bullet of [AD-16](../decisions/0001-foundation.md#ad-16-release-2-shell-and-its-gate); FB0815 and FB0816 are in [08: audit, backup and pipeline](../reference/corpus-format.md#08-audit-backup-and-pipeline); the drill is gate item 9 of the home gate together with Drill 1 ([restore-drill.md](../runbooks/restore-drill.md)).
- Restoring never in place is the one decision that costs two extra steps and cannot lose data: a partial restore into a live folder destroys what is left, and a restore into a new folder cannot. `--from DIR` reads a snapshot from wherever IT's tool put it, so the same command checks a copy the program did not make. A restore writes `restore.begin` and `restore.end` and no other kind of event (`restore.drill` does not exist); the mode field says `drill` or `real`.
- A `--to` folder outside the data root is an export, not a local copy: it is written through `write_outside` with an `export` token from `egress::check`, so the label rule of [ADR 0004](../decisions/0004-company-boundary.md#5-egress) applies to restored company data as to any other copy. A `--to` folder inside the data root and the drill go through `world.write_file`.
- The drill checks the copy against the day the snapshot was taken. A claim whose `review_by` passed since then would add a warning today without the copy being wrong, so the drill reads `created_utc` from `backup.toml` as its date.
- Drill 4 is a runbook for the owner and a test for CI. The test runs the runbook's own commands, so the text and the program cannot drift apart: that is its drift check.
- No page, template or string shown in a browser is built here, so there is no Design bullet. The Backup status page (`status-command`) reads `backup list --json`, not this card.

## Out of scope

- `backup`, `backup verify` and `backup list` (`backup-snapshot`). Drill 5 on the laptop, its PowerShell, the `overlay\` and `working\` roots and the laptop check (`r2-state-and-journal`).
- The `store.toml` stamp (`restored_from`), the FB0836 guard and `init --overlay --adopt`: `r2-company-ids` adds the stamp after the copy and re-hashes the tree, with its own drill step. This card restores the home layout (the Corpus and the state folder) and verifies it against `SHA256SUMS`.
- The `--policy` flag and the `test-hooks` feature, and with them the command-line case of a `restore --to` that no `export` row covers (`policy-load`).
- A restore over live data, in any form. The owner swaps the folders with the commands the program prints; the program does not.
- Recording "backup drill passed" for a commit: that is the owner's comment on the gate item, not code.

## Steps

1. Core, `backup/restore.rs`, pure: `plan_restore(info, destination, live_roots) -> Result<RestorePlan, Refusal>`. The destination must not exist or must be empty, and must not be, contain or lie inside a live root; each fails with FB0815 and says which. The plan lists `<destination>/<root>` for each root in `backup.toml`. `rename_help(plan, shell)` returns the lines the owner runs, for `sh` and for PowerShell: the live folder moved aside, the restored folder moved into its place. `DRILL_STEPS` lists the five steps in order as data (`snapshot`, `restore`, `check`, `journal`, `fingerprint`), so the output and the tests use one list.
2. `restore.rs` and `cli.rs`: `restore --snapshot N (--to DIR | --drill) [--target ID | --from DIR]`. Exactly one of `--to` and `--drill`, else a usage error. `--from DIR` reads a snapshot from any folder and needs no settings; otherwise the target comes from `--target` or `[backup] default`. For a drill or eligible in-root restore, `Journal::begin_restore(snapshot, mode)` appends `restore.begin` with the snapshot's `labels` (read from `backup.toml`) and returns the `Audited` token. `Journal::end_restore` appends `restore.end` with the outcome and the code. Check that the `restore` chip of the Verb map (`fieldbook restore --snapshot <n> --drill`) parses with the clap definition; it is already in the map, so do not edit the map. Remove `restore` from `PENDING` in `tests/chips.rs` and from `NOT_BUILT` in `tests/cli.rs`. Register its case in `tests/support/chip_cases.rs`: an independent copy, the target setup, a successful `backup` first and `n` = 1.
3. `--to DIR`: verify the snapshot as `backup verify` does; if it fails, refuse with FB0815 and name the verify code (FB0810, FB0811 or FB0802) on the same line. Create `DIR` with `dirs::make_dir_outside` (it takes the `export` token asked for below) or use the empty one, copy `data/<root>/` to `DIR/<root>/` hashing each file again, compare with `SHA256SUMS`, and print `restored snapshot N into DIR (F files, B bytes)` and the rename lines. Nothing under a live root is opened for writing. A `--to` folder outside the data root (at home, any folder but `.fieldbook/`) makes the restore an export: before anything is written it asks `egress::check` for an `export` token with the snapshot's `labels` and the folder's path (over `EffectivePolicy::floor(false)` until `policy-load` hands the run its own), and `restore.begin` then also carries `dest` (`export`) and `policy`. A refusal is FB0901 or FB0918, appends a `refuse` event, writes nothing and exits 2. With no policy and no company store the floor allows `public` and `owner-supplied`, so Drill 4 passes; a restore of a store that holds a company label to a folder outside the data root is refused (FB0901 or FB0918) until an `export` row lists those labels and the folder, and one that holds an `unlabelled` or `marked` item is refused whatever the rows say (FB0901), because no row may list those two. A failure part way leaves `DIR` for the owner to delete and exits 3.
4. `--drill`: reset the drill folder with `world.reset_drill(&audited)` (it removes any `<state>/drill/` that an earlier run left and creates it again), and restore into it through `world.write_file` with the `Audited` that `Journal::begin_restore` returned (`Disk::write_file` uses `write_in_root` for a path under the state folder; the folder is under the data root, so the drill is a store write and not an export, and it asks `egress::check` for no token; the folder is derived, replaced whole at each run, and `backup` does not copy it), then run the five steps in order and print one `ok:` line for each. A snapshot that fails step 1 prints its own FB0810, FB0811 or FB0802 and exits 1. A failure in steps 3 to 5 prints FB0816, the step, and the finding behind it. Step 3 runs `check --strict` on the restored `corpus/` with `created_utc` as the date. Step 4 runs `audit verify` on the restored `state/` with `--expect-seq` and `--expect-head` taken from `backup.toml`. Step 5 recomputes the fingerprint with `manifest::fingerprint` over `corpus_entries` (`backup-snapshot` step 2) of the `SHA256SUMS` lines for the restored `data/corpus/` files, whose bytes step 2 has just compared with those lines, so it hashes no file a second time, and compares it with `BackupToml.fingerprint`; a mismatch is FB0816. Delete `<state>/drill/` with `world.remove_drill(&audited)` on every path, success or failure (it clears read-only flags first on Windows). The last line is the one in the Outcome; exit 0, 1 on any failure, 3 on I/O.
5. `docs/runbooks/restore-drill.md`, Drill 4 only: compare each "Expected" line with what the program prints and correct the runbook where it is wrong. Keep the seven steps and their commands as they are, because the CI test runs them. Do not touch Drill 5, which `r2-state-and-journal` owns.
6. `tests/drill4.rs`: read the `sh` blocks between the headings "Drill 4" and "Drill 5" of the runbook and run them as one script in a disposable copy of `corpus/` from the executable’s build checkout (the embedded support catalogue matches it), with `fieldbook` bound to the built binary by a shell function, `FIELDBOOK_STATE` set to a temporary copy of `state-mini`, `HOME` set to a temporary folder, and `sha256sum` and `diff` from the system. Assert, in order, the lines `journal ok`, `backup 1 written`, `snapshot 1 verified`, `snapshot hashes ok`, `drill passed: check clean, journal ok, fingerprint`, then `FB0810` followed by `exit 1`, then `corpus identical`, then `FB0815` followed by `exit 1`. The test is skipped on the Windows job, because it needs `sh`, `sha256sum` and `diff`: the seven steps of Drill 4 are asserted on Linux only, and on Windows `tests/restore.rs` runs the five steps of `restore --drill`.
7. Known-bad files: FB0815 (`restore --snapshot 1 --from target --to occupied`, where `occupied` holds a file) and FB0816 (a writer-built snapshot with a wrong fingerprint and recomputed manifest_sha256, whose SHA256SUMS is intact, run with `--drill`), each with a miniature tree under `tests/fixtures/state-known-bad/<CODE>/` as in `backup-snapshot`. Run `cargo xtask docs` and commit `cli.md`.
8. Tests in `tests/restore.rs`, on a temporary copy of `corpus-mini` and `state-mini` with a snapshot made by `backup`: `restore_to_a_new_folder_matches_the_snapshot` (`diff -r`), `restore_into_a_non_empty_folder_is_fb0815`, `restore_over_a_live_root_is_fb0815`, `restore_with_an_unlabelled_snapshot_is_fb0901_and_exits_2` (the copied `backup.toml` has `labels = ["unlabelled"]` and `--to` names a folder outside the data root: FB0901, exit 2, nothing written, a `refuse` event), `restore_of_a_bad_snapshot_names_the_verify_code`, `restore_from_a_folder_needs_no_settings`, `restore_prints_rename_lines_for_sh_and_powershell`, `drill_passes_on_the_fixture`, `drill_fails_on_a_changed_byte` (FB0810), `drill_fails_when_the_restored_journal_is_cut` (a test-only hook after the copy removes the last lines; FB0816 names FB0802), `drill_fails_on_a_wrong_fingerprint` (FB0816), `drill_uses_the_snapshot_date` (a later clock does not fail it), `drill_deletes_its_folder_on_every_path` (`<state>/drill/` is gone after success and after each failure), `restore_events_are_begin_then_end` (with the snapshot's `labels`), `restore_outside_the_data_root_asks_for_an_export_token` (a `--to` folder gets `dest` and `policy` in `restore.begin`), `the_drill_writes_only_under_the_state_folder` (`TestWorld::written()` lists every path written through `write_file` or `write_outside`: all are under `<state>/drill/`, and no `export` token is asked for), `a_second_drill_replaces_the_first_folder_whole` (a stale file left in `<state>/drill/` is gone after a drill) and `restore_starts_no_process_and_opens_no_socket` (the layer scan covers `restore.rs` with no exemption). Core, in `tests/restore.rs`: `destination_rules`, `rename_help_is_stable`. A test `drill_time_is_measured` prints the time of a drill on the 200 MB tree of `backup-snapshot`; the budget for a 500 MB snapshot is 5 minutes [J], advisory in CI.
9. Mark the tests that carry a control row of [the controls table](../controls.md) with the line `// control: <ID>` directly above the test, as `controls_have_tests` reads it: `// control: ED-04` on `restore_into_a_non_empty_folder_is_fb0815`.

## Acceptance

```sh
cargo nextest run --locked -p fieldbook-core --test restore
cargo nextest run --locked -p fieldbook --test restore --test drill4
cargo build -q --locked -p fieldbook && B="$PWD/target/debug/fieldbook" && T="$(mktemp -d)" && cp -R corpus "$T/corpus" && mkdir "$T/target"
(cd "$T" && "$B" backup --to "$T/target" && "$B" restore --snapshot 1 --from "$T/target" --drill > "$T/drill.out"; echo "exit $?"; tail -n 1 "$T/drill.out")
(cd "$T" && "$B" restore --snapshot 1 --from "$T/target" --to "$T/restored" && diff -rq corpus "$T/restored/corpus" && echo "corpus identical"; "$B" restore --snapshot 1 --from "$T/target" --to "$T/restored"; echo "exit $?")
cargo nextest run --locked -p fieldbook --test restore restore_with_an_unlabelled_snapshot_is_fb0901_and_exits_2
cargo xtask docs --check
cargo nextest run --locked -p fieldbook --test leak_outputs
just check
```

Expected: the tests pass, `drill4` included, on Linux; on Windows everything but `drill4`, which needs `sh`, `sha256sum` and `diff`. The first block prints `exit 0` and then `drill passed: check clean, journal ok, fingerprint ` with 12 hex characters and ` matches`; the second prints the rename lines, `corpus identical`, then FB0815 and `exit 1` for the second restore; the named writer-backed unlabelled-snapshot test expects FB0901/exit 2 and no destination; `docs --check` and `just check` exit 0. Remove the temporary folder afterwards.

## Negative control

In the temporary copy, append one byte to a `.csv` file under `$T/target/fieldbook-backup-0001/data/` and run the drill again: it must print FB0810 for that file, exit 1, and leave no `drill/` folder under the state folder. Start from a clean snapshot for each metadata mutation. Run `drill_fails_on_a_wrong_fingerprint` with the producer writer and `backup::manifest_sha256` recomputing identity after the wrong fingerprint: expect FB0816 at the fingerprint step. A separate `drill_refuses_stale_manifest_digest` leaves the digest stale and expects FB0811/exit 1 during snapshot verification. Then, on the branch, let `restore --to` accept a non-empty destination: `restore_into_a_non_empty_folder_is_fb0815` and `drill4` must fail. Restore it. Then make the FB0901 refusal of `restore --to` exit 1: `restore_with_an_unlabelled_snapshot_is_fb0901_and_exits_2` must fail. Restore it.

Bypass the label filter at the restore export handler: `real_outputs_keep_permitted_canaries_and_refuse_others` must fail. Restore it.

Bypass the drill placement guard: `drill_refuses_company_labels_under_git_before_copy` must fail. Restore it.

Bypass only the --to Git placement check: `restore_to_refuses_company_labels_under_git_before_copy` must fail. Restore it.

Bypass State admission before drill or eligible in-root restore: `drill_refuses_labels_not_held_by_state` and `restore_to_state_checks_admission` must fail. Restore it.

## Rollback

Revert the merge commit. `backup` and its snapshots are unchanged, and a snapshot can still be restored by copying `data/` with the file manager and checking `SHA256SUMS` with `sha256sum -c`. Folders already restored by `--to` are ordinary folders. The `restore.begin` and `restore.end` events stay in the journal.

## BLOCKED

The drill cannot delete its temporary folder on the Windows job, or the `drill4` script fails because the runbook's shell lines need a tool the CI image lacks. Set the item to Blocked with `BLOCKED: drill cleanup or drill4 differs between jobs`, and stop. Do not leave the folder behind and do not edit the runbook to hide a failing step.
