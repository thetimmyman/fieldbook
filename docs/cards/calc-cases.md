# calc-cases

- **Runs where:** home, CI Linux
- **Schema impact:** none
- **Review:** auto

## Outcome

The Day-1 calculation cases CALC-01 to CALC-04 are synthetic case files that `fieldbook-calc` reproduces to the cent, and a case that differs fails with FB0503. `check` raises FB0500 for a `value` cell of `claims.csv`, and a repository test proves that every `Fixture:` line names a case that exists. The runner is driven by the data in `tests/cases/*.toml`, so a new case is one file and one line in a list, with no case-specific Rust, and a rules test fails a case that lacks a provenance field. The cases can be run from `fieldbook-core`, so the renderer can draw them. Each case names the function it exercises (`fn`), the crate holds the one table of functions (`CALC_FNS`: `build_up@1` and `children_sum@1`), and a case that names a function not in it fails with FB0504. A refusal case states the code it expects. A run has a fixed text form, and an epoch number is tied to the case set, so a change of behaviour cannot pass unnoticed.

## Why

- The synthetic cases stay the oracle for every calculation that later touches a company figure: a function of the pricing modules is first proven against a synthetic case here and only then run on the rate book or a bid cost build.
- The cases, their inputs and outputs and the fixture rules are in [FM0](../decisions/0001-foundation.md#calculation-core-fm0). Where the case files live and how they are pinned is in [AD-14](../decisions/0001-foundation.md#ad-14-money-and-the-calculation-core-fm0), which also holds the function table, the case fields `fn` and `tolerance`, the `Run` record and `CALC_EPOCH` (Cases, Functions, Runs). The case id forms are under [Identifiers](../reference/corpus-format.md#identifiers).
- The codes are in [05: calculation](../reference/corpus-format.md#05-calculation). The `value` column is in [claims.csv](../reference/corpus-format.md#claimscsv). The `Fixture:` line of a `calc` page is in [Page files](../reference/corpus-format.md#page-files).
- Design: the [MAP.md](../design/MAP.md#routes-and-components) rows "CalcTable" and "Charts" (CALC-02 only). This card computes the figures; `build-charts` draws them. [HANDOFF.md](../design/HANDOFF.md) [§5 Components](../design/HANDOFF.md#5-components) (CalcTable) and [Charts](../design/HANDOFF.md#charts). No token group.

## Steps

1. `calc/src/cases.rs`: `Case` (serde, `deny_unknown_fields`) with `id`, `synthetic`, `as_of`, the overhead base (a base word, or `none`), the inputs as decimal text, the rounding policy, `stages` (a list of the rounding stages the case names, by the snake_case words of `Stage`: `unit_price`, `extension`, `total`) and the expected outputs as decimal text. `evaluate(&Case) -> Result<Outcome, CalcError>` computes each output through the `ops` and the named rounding stages of `calc-day1`, using the case’s data and current `CALC_EPOCH`; no function or test names a case id. `compare(&Case, &Outcome)` returns every output that differs, with expected and found. A case without `synthetic = true`, without `as_of` or without `fn` is refused. The field `fn` is the function id with its version (`build_up@1`); in Rust the field is `func`, serialised as `fn`. `evaluate` finds the function with `fns::lookup` (step 9) and dispatches on the row; an id that is not in `CALC_FNS` is `CalcError::UnknownFn`, whose `code()` is `FB0504`. A case may state `tolerance` (decimal text) only for a function whose row is `iterative`; on any other function it is refused, because every other case reproduces exactly. A case may state `refuse = "<code>"` instead of expected outputs: it passes when `evaluate` fails with exactly that code and otherwise fails with FB0503. `Outcome { outputs: Vec<RunOutput>, run: Run }` holds the outputs and the `Run` of the evaluation (`RunOutput` and `Run` are step 10). A case with `[[budget]]` rows runs `children::check_children_sum(parent, children) -> Result<(), SumMismatch>` on the money type of `calc-day1`; `SumMismatch` holds the parent, the children's total and the gap, and `compare` checks that a row expected to be refused is refused with those three figures and that an accepted row is accepted.
2. Write the four case files from FM0. Each carries the provenance fields `id`, `synthetic = true`, a synthetic `as_of` and its overhead base, the function it exercises in `fn` (`build_up@1` for CALC-01 to CALC-03, `children_sum@1` for CALC-04), and names its rounding stages. CALC-04 is the budget case: it states its overhead base as `none` and has `stages = []`, because its figures are two-decimal amounts that are only added. CALC-02 is its own file; it does not edit CALC-01. CALC-04 holds three `[[budget]]` rows, each with `parent`, `children` (decimal text) and `expect` (`accepted`, or `refused` with the `total` and `gap`): (a) parent 50.00, children 10.00, 15.00, 12.50, 12.50 and 5.00 (weights 0.20, 0.30, 0.25, 0.25 and 0.10): refused, total 55.00, gap 5.00; (b) the same parent with children 10.00, 15.00, 12.50, 7.50 and 5.00 (weights summing to 1.00): accepted; (c) children totalling 49.99: refused, gap 0.01. Write `tests/cases/README.md` with the heading `## Adding a case` (the cards README links to it) and the recipe for a new case, eight lines at most: copy a case file; give it the next `CALC-nn` id (ids 90 to 99 are for refusal cases) and the provenance fields, and the `fn` it exercises; state the inputs and expected outputs as decimal text, or, for a negative case, `refuse = "<code>"`; add the file to `CASES` in `core/src/cases.rs`; increase CALC_EPOCH when the case-set binding differs from the selected baseline, then write the current digest into `EPOCH`; run `cargo nextest run --locked -p fieldbook-calc cases::` and the core test.
3. `calc/tests/cases.rs`, in `mod cases`: parse each file with the `toml` dev-dependency. Tests: `calc_01_matches`, `calc_02_matches`, `calc_03_matches`, `calc_04_matches`, `an_exact_sum_is_accepted`, `a_gap_of_one_cent_is_refused`; `calc_02_leaves_calc_01_unchanged` (evaluate CALC-01, then CALC-02, then CALC-01 again, and compare the two CALC-01 outcomes); `markup_is_not_margin` (CALC-01 against CALC-03); `setup_is_added_once`; `a_mismatch_is_fb0503` (a copy with one expected value changed by one cent names the case, the output and both values); `every_case_file_matches` (reads every `tests/cases/*.toml`, evaluates it and compares, so a new file is tested with no new code); `every_case_obeys_the_fixture_rules` (each file has `synthetic = true`, an `as_of`, an `fn` that is in `CALC_FNS`, an overhead base (a base word, or `none`), a `stages` list (`stages = []` only when the overhead base is `none`, as in CALC-04 and CALC-90), and a `CALC-nn` id that is unique and equals its file name; each file in `tests/cases-bad/` is refused for its one broken rule, and the refusal names the file and the rule; add one file there without `fn`); `calc_fns_have_cases` (every row of `CALC_FNS` has a positive case, a file with that `fn` that evaluates and matches or a `[[budget]]` row that is accepted, and a negative case, a `refuse` file or a `[[budget]]` row that is refused; `build_up@1` has CALC-01 to CALC-03 and CALC-90, `children_sum@1` has the rows of CALC-04); `an_unknown_function_is_fb0504` (a copy of CALC-01 with `fn = "build_up@9"` gives `CalcError::UnknownFn` and the code `FB0504`); `a_tolerance_on_an_exact_function_is_refused`; `a_refusal_case_matches_its_code` (CALC-90 gives `FB0501`) and `a_refusal_with_the_wrong_code_is_fb0503` (a copy of CALC-90 with `refuse = "FB0500"` fails with FB0503 and names the case); `canonical_run_is_stable` (the `Run` of CALC-01 prints a `canonical()` text equal to `tests/golden/run-calc-01.txt`, written by hand from the format of step 10, and two evaluations print the same bytes). Follow the shared rule in [testing.md](../reference/testing.md) and add `case_and_replay_parsers_never_panic` in this same `mod cases`: use the shared RNG and 200 seeded byte strings, plus single-byte flips and deletions of each reader's own valid `Case` and `ReplayCase` example; accept a parsed value or a typed error, never a panic, and confirm the original examples parse.

This is the API `build-charts` calls. A test, `every_case_file_is_listed`, fails when a file of `tests/cases/` is missing from `CASES`. The expected values stay in the binary and the repository, outside the Corpus.

An id has the form `name@N` (`^[a-z][a-z0-9_]*@[0-9]+$`). Write `lookup(&str) -> Option<&FnRow>` and `pub const CALC_EPOCH: u32 = 1;`. Add `CalcError::UnknownFn(String)` to `error.rs`, with `code()` returning `FB0504`; `fieldbook-core` maps that text to its `Code` as it does for the other three (the variant exists, because `check-v0` writes `Code` from the catalogue). 10. `calc/src/run.rs`: `Run { func: String, calculation_epoch: u32, rounding: RunRounding, inputs: Vec<RunInput>, outputs: Vec<RunOutput>, stage: String, complete: bool }`, `RunRounding { policy: String, scale: u32, mode: String }`, `RunInput { name, value: Value<Dec>, origin, pointer, unit, currency: Option<Currency> }` and `RunOutput { name, value: Value<Dec>, unit, currency: Option<Currency> }`; the untyped fields are String. Origin and pointer are filled by the caller and validated by core. `evaluate` fills every field from the named function and case. `Run::canonical()` uses exactly the framed UTF-8 format in [Stored calculation runs](../reference/financial-work.md#stored-calculation-runs). The golden is written independently from that format. `canonical_run_changes_with_epoch_rounding_or_unit` varies epoch, policy name, scale, mode, unit and currency independently; each changes the bytes. `canonical_fields_are_unambiguous` includes spaces, colons and newlines in text fields and distinguishes absent currency from every valid currency. The calculation crate hashes nothing; core hashes these bytes when records persist a run. No later card changes this version's meaning.

## Negative control

In `calc-01.toml`, change the expected landed cost by one cent. `cases::calc_01_matches` must fail with FB0503 and name CALC-01, the output, and both values. Restore the file. Then change the fixture page's line to `Fixture: CALC-99`: `fixture_cases` must fail and name the page and `CALC-99`. Restore the file. Then delete `synthetic = true` from `calc-02.toml`: `every_case_obeys_the_fixture_rules` must fail and name the file. Restore the file. Then make `check_children_sum` accept a gap of 5.00: `calc_04_matches` must fail on row (a). Restore the file. Then add a row to `CALC_FNS` with no case: `calc_fns_have_cases` must fail and name it. Remove the row. Then add a comment line to `calc-02.toml` without touching `EPOCH`: `calc_epoch_matches_the_case_set` must fail and print the new line. Restore the file. Then change `refuse` in `calc-90.toml` to `FB0500`: `a_refusal_case_matches_its_code` must fail with FB0503. Restore the file. Then rename `calc-90.toml` to `est-90.toml` in `CASES`: `case_files_use_a_current_prefix` must fail and name `EST`. Restore the name.

Allow an old binding and expected output to change together: the compatibility tests must fail. Restore it.

Omit currency, units, rounding or epoch from canonical(): canonical_run_changes_with_epoch_rounding_or_unit must fail. Restore each.

Replace the margin stage quotient with ordinary division: `calc_03_matches` must fail. Restore it.

Change the case set and update its digest while retaining the baseline epoch: `changed_cases_require_a_new_epoch` must fail. Restore it.

Skip historical execution, accept a missing binding, or overwrite tool with an edition predecessor: the compatibility/stream tests must fail. Restore each.

Make the `Case` or `ReplayCase` reader panic on an exercised malformed input: `case_and_replay_parsers_never_panic` must fail and name the reader. Restore it. Then make the manifest or baseline reader panic on an exercised malformed input: `manifest_and_baseline_parsers_never_panic` must fail and name the reader. Restore it.

Skip current case-set or compiled-epoch binding: the corresponding stale-manifest command test must fail. Substitute CALC_EPOCH for a replay vector’s epoch: `epoch_increase_preserves_historical_vectors` must fail. Restore each.

## Rollback

Revert the merge commit. FB0500 goes back to `pending.toml` and the fixture loses its `calc` page. Revert `build-charts` first if it has merged, and any card that adds a function to `CALC_FNS`.

## BLOCKED

- A case cannot reach its FM0 output with the default rounding policy at the named stages: name the case, the output and the value found. Do not change the expected value or add a rounding step.
- FM0 does not state a value a case needs, such as the overhead base: name it and ask the lead.
- A malformed `value` cell already raises a code from an earlier card: name both codes and stop.
