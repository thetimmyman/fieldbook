# handoff-new-note

- **Runs where:** home, CI Linux
- **Schema impact:** additive
- **Review:** owner

## Outcome

`fieldbook new note --ai-drafted --confirm-public --area <a> --from <file|-> [--subarea <s>] [--question "<text>"]` saves an answer as a `note` page: unreviewed, labelled as AI-drafted, with its question and the fingerprint of the context it was given, after the text passes the scans and has no broken citation. The `note` page type (schema 2) joins the Corpus format. The `note` row of `KINDS` lets `queue accept` write the same page for a proposal that `ask --note` or the Bridge filed. A note is never a source for a claim.

## Why

- The verb is the Day-30 row of [AD-17](../../decisions/0001-foundation.md#ad-17-authoring-experience). The `note` page type, its fields and its codes are the row of [Object types beyond v1](../../reference/corpus-format.md#object-types-beyond-v1) and FB0708 and FB0709 in [07: Handoff](../../reference/corpus-format.md#07-handoff). Control HG-06 in [controls.md](../../controls.md): notes pass the same scans, are saved `ai_drafted` and unreviewed, and may not support a claim. Control AL-04 (an AI call leaves its trace) already says in `docs/controls.md` that a Handoff round trip writes `ai.pack` and `ai.paste` and that `new note --ai-drafted --confirm-public` writes `ai.paste` with no pack, so an answer that enters the Corpus tree from an assistant leaves an event whichever door it used; step 10 names the test that carries it.
- This is the format gate: the card changes what `check` accepts and raises `schema_version` to 2, so the owner reviews it and ADR 0003 (Corpus format v2) is accepted first. The fields below are the ones the lead proposes there; if the ADR lists others, the ADR wins and the steps change to match.
- Two doors, one planner. The owner who works outside the chat uses the verb; a proposal that `ask --note` (`model-handoff-ask`) or the Bridge (`chat-bridge`) filed becomes the same page when the owner runs `queue accept` (`review-queue`). `note::plan_note` is the one function that builds the page, so the bytes are the same whichever door was used, and the scans and the cite check run again at accept.
- The text a person copies from the Assistant page ("Copy as draft note") is a draft-note text: a `Question:` line, an optional `Context:` line with the ids, a blank line and the answer. `new note` reads that form, and any plain answer with `--question`. One quoting function builds the command the page shows; answer text never enters a command.
- Notes are left out of a context pack unless named, as HG-02 says; `handoff-context` could not do this before the type existed, so this card adds the class and the `--include notes` word.
- Size: if sizing shows the card is too large, steps 2 to 4 and 7 to 8 (the page type, its check and its render) are a card of their own, `note-page-type`, and this card keeps the rest.
- Design: the [MAP.md](../../design/MAP.md) rows for the Ask drawer and `#assistant` (AnswerActions: Copy as draft note), CommandChip for the `new note` verb, and `p/<page-id>.html` for the `note` render. [HANDOFF.md](../../design/HANDOFF.md) §9 Cite-check (item 7) and Adapters (Save notes), §6 for the label. Token groups: colour, type and space through the existing page rules; no new token.

## Steps

1. Version: `SCHEMA_VERSION_MAX = 2` and the row `0.2.0` for schema 2 in `version.rs`. `check` and `build` accept schema 1 and 2. A `note` page in a schema-1 Corpus is refused by `check` with FB0108 (the example of that row), and `new note` on a schema-1 Corpus prints `notes need schema_version = 2 (ADR 0003); set it in corpus.toml`, writes nothing and exits 2.
2. Page type: `PageType::Note` and `NoteMeta { origin, reviewed, question, context_fingerprint }` in `schema/page_types.rs`, with `deny_unknown_fields` and every field read as optional, so that a missing one is FB0709 (step 4) and not FB0103; `vocab.rs` gets the origin word `ai_drafted`. A note has no fixed parts and no required content (FB0134), and the part checks (FB0130) skip it. Front matter, in this order: `id` (`<area>-note-<nnn>`), `title`, `area`, `subarea`, `type = "note"`, `stage = 8` [J], `readiness = "PUBLIC-NOW"` [J], `status = "draft"`, `as_of`, `handling = <effective labels, public for Corpus>`, `origin = "ai_drafted"`, `reviewed = false`, `question`, `context_fingerprint`.
3. `note.rs` (core, pure, no clock, no disk): `parse_draft(text) -> Result<Draft, NoteError>` reads the draft-note text, returning an optional question while preserving the headerless body; `pack_fingerprint(ids) -> String` is the SHA-256 in hex of the ids sorted, one per line, each line ending in LF (for no ids, of the empty text); `NotePlan { files: Vec<PlannedWrite>, affected: Vec<ItemRef> }` and `plan_note(model, view, input, today) -> Result<NotePlan, NoteError>` where input includes area, optional subarea, question, context ids, body, request_labels, provenance and the confirmed PublicAct. It runs, in this order: the scans FB0400 to FB0403 over the title, question and body (FB0708); `assist::cite_check(view, body, None)` (`report.unresolved > 0` refuses the note and carries the report, including unavailable or mismatched quotation facts beneath a higher-precedence status); refusal of the answer-only `[@<area>-note-<nnn>]` form as a Corpus citation to a note (FB0300, because `a_page_citing_a_note_id_is_fb0300`), before either door writes and even when the answer also carries a verified citation; the rewrite of each citation of the body to its canonical form with the tolerant lexer; the id (the next free number of the series `<area>-note-`, three digits); the title (the question cut at 80 characters, markup characters removed, a final full stop dropped); the subarea (the one given, else the first subarea of the area); and the file text. The plan.files list holds one `Rendered` write, built with `PlannedWrite::new` of `pipeline-ports`: the page path `pages/<area-slug>/<subarea>/<id>.md` and its bytes. plan.affected holds the allocated note reference. `new note` builds WriteSet from the labels, each planned file and affected references converted to audit::RecordRef; it never reallocates the id. A missing or empty resolved question, or an empty body, is FB0709. The note's `as_of` is the earlier of `today` and the oldest known cited-claim date, comparing a partial date as its first day; it is `today` when no cited claim date is known. Claim dates are not changed, and no note rule suppresses the ordinary age warnings. A model whose `schema_version` is 1 is `NoteError::SchemaOne` (FB0108, with the sentence of step 1), checked before the scans, so that neither door can write a `note` page that `check` would refuse.
4. `check/note.rs`: FB0709 for a `note` page whose `origin` is not `ai_drafted` or whose `question`, `reviewed` or `context_fingerprint` is missing or malformed (the fingerprint is 64 lowercase hex characters). The usual scans and citation checks apply to the body of a note like any page. Register the pass in `check/mod.rs`.
5. The verb, in `new.rs` and `cli.rs`: `new note --ai-drafted --confirm-public --area <a> --from <file|->` with the optional `--subarea` and `--question`. The flags --ai-drafted and --confirm-public are required for Corpus admission; the latter calls the shared label_context and is refused on a company-store machine. The flag `--ai-drafted` is required (a note by hand is not a v1 object). Read the input as UTF-8 (at most 256 KiB; empty is exit 2). The view for `plan_note` comes from `note_view(world, model, policy) -> Result<LabelledView, Fb>` in `new.rs`: the `LabelledView` for the `edition` destination (the set `public`), made from the selection-only token of `egress::check(&effective, &Dest::Edition, None, None, now, shipped)`, with the current policy snapshot and export age, as the edition build selects its view, because the context of a Corpus note is `public` (a denial is exit 2 with its code). Read all input before taking a lease. Then take the store write lease and open the journal, retaining the lease through write.end. Before normal tree loading, inspect matching pending intent through the existing new recovery coordinator. A pending tree uses only its matching recovery reader; a fresh request loads through read_tree_under. In this order: parse the retained input draft (a `--question` replaces the `Question:` line; with neither, FB0709, `note not written: a note needs a question`, exit 2); resolve pending intent through the existing new recovery coordinator before `plan_note` (no fresh planning or allocation during matching recovery); `plan_note` for a fresh request only (no write yet; a refusal prints `note not written` and its reason (for a schema-1 Corpus, the sentence of step 1) and exits 2 for FB0108, FB0708 and FB0709, 1 for an unresolved citation with the line `N of M citations do not resolve`, and 1 for an answer-only note reference (FB0300), which names the reference); `Journal::begin(&lease, &intent, &write_set)`; append `ai.paste` with `output_sha256` (of the body bytes) and no `pack_seq`, and if the journal cannot append, exit 3 with FB0903 and write nothing; write the page through `world.write_file` between `write.begin` and `write.end`; print the id, the path and `unreviewed: read it, then set reviewed = true`. Exit 0.
6. The accept path. `note_kind.rs` is not a file: the `note` row of `KINDS` in `kinds.rs` is `check_source` (re-hash the whole `[note]` table of the proposal; another hash is FB0820), `admit` (builds `NoteAdmit` and returns it) and `describe` (area, title, question, `AI-drafted, unreviewed` and the first five lines of the body); `after_accept` does nothing. `NoteAdmit { model, view: LabelledView, today, public_act }` is in `note.rs`; it is an `Admit` with `id()` `note-add@1`. The row's `admit` builds it as the verb does: `model` is `env.model`, `view` is `note_view(env.world, env.model, env.policy)` of step 5, public_act comes from the explicit acceptance confirmation, and `today` is the date of `env.world.now()`, the one clock seam. `NoteAdmit::plan(&Proposal, &Edits, &CorpusView, Option<&VerifiedExtraction>) -> Result<AdmitOutcome, AdmitError>` ignores `Edits` and `CorpusView` (a note has no cells to fill, so it never returns `MissingField`), reads the eight keys below, calls `plan_note` with the table's area, question, context, body, request_labels and provenance, and returns `AdmitOutcome::Planned { files, affected }`. This non-source kind receives None for extraction. The shared note plan exposes its allocated note ID, and affected contains its store-qualified ItemRef; do not allocate again. A `[note]` table has exactly eight keys: area, title, question, context, body, origin, request_labels and provenance; `origin` must be `ai_drafted`, and any other value or a missing key is `AdmitError::Invalid`. `plan_note` derives the page title (step 3) and ignores the table's `title`, which is the display label for `queue list`, `queue show` and `describe`. Replace the `[note]` table of `tests/fixtures/queue/note.toml` (written by `pipeline-ports`) with these eight keys, and remove `note` from `NOT_YET_BUILT`. `review-queue` is a merged card (see Cards merged), so `kinds.rs` and the list exist and this step has no condition. `NoteAdmit::plan` maps every `NoteError` of `plan_note` to `AdmitError::Invalid(fb)`, and the row's `admit` returns a failure of `note_view` as an `AdmitError::Invalid` with its code, so `queue accept` writes nothing for a note that `new note` would refuse.
