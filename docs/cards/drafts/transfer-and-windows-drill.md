# transfer-and-windows-drill

- **Runs where:** home, CI Linux, CI Windows
- **Schema impact:** none
- **Review:** owner

## Outcome

The `windows` job of AD-08 runs drill 2 of restore-drill.md on windows-2025, through `cargo xtask drill`. It extracts into a path with spaces, runs the hash checks, the Edge harness on the extracted edition and every command chip in cmd and in PowerShell Constrained Language Mode, and makes FB0607 (a brief printed on more than one page) an error. The job already exists (`windows-facts` built it, gated by `changes` and needed by `ci-ok`); this card adds the drill steps after its nextest step. They run when `changes.code` or `changes.corpus` is true, and the full run is weekly (`scheduled.yml`) and on release tags, for which `release.yml` gets a `windows` job of its own. `scheduled.yml` compares the Linux and Windows trees (DT-02). Drill 3 on the laptop is the owner's own item in PLAN.md, so this card closes without it and without IT's answers.

## Why

- The steps are [Drill 2](../../runbooks/restore-drill.md#drill-2-the-windows-2025-drill-in-headless-edge-from-e1) and [Drill 3](../../runbooks/restore-drill.md#drill-3-the-owners-laptop-drill-e1); the owner's hash command is [transfer.md step 4](../../runbooks/transfer.md#step-4-check-each-zip-against-the-out-of-band-list), and README.txt's paragraph is [Mark-of-the-Web](../../runbooks/transfer.md#mark-of-the-web).
- Chips run unchanged in cmd and CLM ([AD-17](../../decisions/0001-foundation.md#ad-17-authoring-experience); [Command chips](../../reference/corpus-format.md#command-chips)). FB0607 is in [06: site and edition](../../reference/corpus-format.md#06-site-and-edition).
- Controls: SG-01, MW-01, DT-02, and the Windows runs of NS-03, ED-02 and WB-05, in [controls.md](../../controls.md).
- The card changes CI jobs and `release.yml`, which is the release gate, so the review is the owner's. It may pass 400 lines; split at the seam between steps 1 to 5 and step 6 if it passes 500.
- Design: the [MAP.md](../../design/MAP.md) row Edge from `file://`, cmd and PowerShell command chips, the Windows half. [HANDOFF.md](../../design/HANDOFF.md) §13 Design evidence (Not yet verified: Edge from `file://`, the chips in cmd and CLM, the CSP in Edge, print). Token groups: none.

## Steps

1. `drill.rs`: `cargo xtask drill` reads the fenced `powershell` blocks of Drill 2 steps 2 to 6 from `restore-drill.md` and runs them in order, after `cargo xtask edition`; step 2 runs the transfer.md loop with the real file names. A block and the Expected paragraph after it form a pair, and a step holds one or more pairs. The blocks run in ONE PowerShell session, because variables set in step 3 are read in steps 4 to 6: one child `powershell -NoProfile -Command -` fed on standard input, each block followed by the line `Write-Output "<<END step N>>"`. The output is split at those sentinels and each part is compared with the Expected line of that block. `run_steps` takes the session as its `run` closure, so tests drive it with a fake that keeps variables in a map. It stops at the first miss, naming the step. The runbook stays the one source of the commands.
2. After step 4 it checks that the extracted `README.txt` holds the Mark-of-the-Web paragraph (MW-01). It copies one zip, changes one byte, and requires the step 2 loop to print `False` for it (SG-01).
3. Chips: for each chip of `strings::chips` whose verb exists in this build, fill its placeholders from `const CHIP_SAMPLES: &[(&str, &str)]` (the exact pre-substitution row.chip string, then the command to run: a reference placeholder takes an id that exists in the fixture, a creation placeholder takes a valid absent id, and other placeholders such as type or subarea take valid fixture-backed values; a chip with no placeholder has no row, and a chip with a placeholder and no row fails the run and names the chip) and run it once with `cmd /c` and once in `powershell` with the language mode set to `ConstrainedLanguage`. Every chip execution in each shell gets its own fresh disposable copy: the backup-dependent chips (`fieldbook backup`, `fieldbook backup verify`, `fieldbook restore --snapshot <n> --drill` and `fieldbook backup list`) copy the build checkout's `corpus/` as `restore-and-drill` step 17 says and assert snapshot creation succeeds first, while every other chip copies `corpus-mini`; one chip's writes cannot affect the next chip or the other shell, and setup runs in that same copy. An exit code of 2 fails and names the chip and the shell. Three chips need state that a fresh copy lacks, so `const CHIP_SETUP: &[(&str, &[&str])]` (the exact pre-substitution row.chip string, then the steps run first in the same copy, in order; a step is the word `target` or a command) prepares them. `target` writes `settings.toml` in the state folder of the copy with one `[[backup.target]]` (`id = "drill"`, `kind = "folder"`, `path` a new temporary folder outside both the copy and the state folder, because a target inside a folder it backs up is FB0812). The rows are `fieldbook backup` (`target`), `fieldbook backup verify` (`target`, then `backup`) and `fieldbook restore --snapshot <n> --drill` (`target`, then `backup`; its `CHIP_SAMPLES` row gives `n` = 1). A chip with no placeholder has no `CHIP_SAMPLES` row but may have a `CHIP_SETUP` row, and a chip whose run exits 2 after its setup still fails and names the chip and the shell. The chips of `const TERMINAL_ONLY: &[&str] = &["fieldbook verify <claim-id> --on YYYY-MM-DD", "fieldbook queue review", "fieldbook queue accept <proposal-id>", "fieldbook queue reject <proposal-id> --reason <word>"]` refuse a run with no person at a console, and a job is such a run: for them the exit code is not tested, and the run passes only if standard error holds `needs a terminal` (`verify` and the queue verbs print it on standard error, as `verify-status-fmt` and `review-queue` say). Any other output from them fails. `label add` has no chip, so it is not in the list.
4. `harness.rs`: on Windows, print each page of type `brief` to a PDF with Edge (`--print-to-pdf`) and count its pages with `print_count.rs` of `day-one-binder-and-registers-xlsx`; FB0607 is an error there, and on Linux the same finding stays a warning. `drill.rs`: the plants for the controls, `--plant doubled-top-folder`, `--plant one-byte` and `--plant no-motw`, each of which must make the drill fail at its named step. `one-byte` changes one byte of a zip in `out\dist` before step 2 (SG-01), `doubled-top-folder` builds the edition zip with the top folder `edition\edition\`, and `no-motw` removes the Mark-of-the-Web paragraph from the extracted `README.txt` before the check that follows step 4 (MW-01). The paragraph is the one that starts with the line `MARK-OF-THE-WEB` (`edition-zips` writes it).
5. `ci.yml`: extend the `windows` job that `windows-facts` created (`windows-2025`, read-only token, the pinned actions). Add the steps after its nextest step, each with `if: needs.changes.outputs.code == 'true' || needs.changes.outputs.corpus == 'true'`: the drill extracts and opens the edition, which a Corpus change alters as much as a code change does. The steps are `cargo run --locked -p fieldbook -- build --out out`, `cargo xtask harness` (it writes the network-silence summary that `cargo xtask edition` refuses to build without), `cargo xtask edition` and `cargo xtask drill`; they are the commands behind `just site`, `just browser` and `just edition`, and the job has no `just`. Add no second job, no job-level `if` and no path list, and leave `needs` of `ci-ok` as it is (it already lists `windows`; the test `ci_ok_needs_every_job` fails if it does not). The AD-08 row for `windows` already says this, so this card does not edit the table. `release.yml`: add a job `windows` with `runs-on: windows-2025`, `needs: tag-check` and `if: github.ref_type == 'tag' && (!startsWith(github.ref_name, 'edition-') || needs.tag-check.outputs.kind == 'site')`. It has no `permissions` key of its own (it takes the `contents: read` of the workflow), uses the checkout, toolchain and cache actions at the SHAs `ci.yml` already pins, runs the same four steps without the `changes` condition, and uploads nothing. In `xtask/tests/release.rs`, `release_yml_triggers` also requires that the `windows` job runs on `windows-2025`, needs `tag-check` and carries that same validated Site-or-tool condition, and `release_yml_is_read_only_and_pinned` also requires that the job has no `permissions` key.
6. `scheduled.yml`: a full `windows` job that builds the edition as step 5 does, runs the drill and the three plants (each must fail), and uploads `edition-hashes-windows` laid out like `edition-hashes-linux` (both complete zips and their published `SHA256SUMS`; step 8 of `scheduled-workflow` sets it), and a `compare` job that needs both jobs, downloads both artifacts and runs `cargo xtask drill --compare edition-hashes-linux edition-hashes-windows`. Both new jobs begin with the checkout step of `edition-linux`, then its `heading` step (step 8 of `scheduled-workflow`; the `heading` step of the `windows` job has `shell: bash`), and give every step after those two `if: steps.heading.outputs.run == 'true'`, so that while `corpus/changes.md` has no `## edition-` heading they end green with the notice `no edition to build`, as `edition-linux` does, and the weekly run stays green. `--compare` verifies each downloaded package set and calls the shared `compare_payload` of `edition-zips`. It prints `DIFFERS <path>` and exits 1 on a deterministic payload mismatch, missing path or invalid manifest. Use the one `ATTESTATION_PATHS` list: the measured browser summary and transfer statement may differ; their own hashes and derived manifests must still verify. A synthetic one-byte change must be reported (DT-02).
7. Drill 2 step 6: `drill.rs` takes the copy and compare block under the heading "Back up `working\`" of [transfer.md](../../runbooks/transfer.md#back-up-working), replaces its `$src =` and `$dst =` lines with `$src = "$dest\working"` and `$dst = Join-Path $env:TEMP ('working-drill-' + [guid]::NewGuid().ToString('N'))`, and runs it once on the synthetic `working\` file that the runbook's earlier block made (Expected: no output). After the runbook's block that appends one character to the copy, it runs only the last line of the transfer.md block, the compare loop, again and asserts exactly one `MISMATCH` line; it does not run the whole block again, because that would copy the appended character back. The job fails if the first run prints anything or the second prints nothing.
8. Tests, in `mod tests` of `drill.rs` (`xtask` is a binary crate, so a file in `xtask/tests/` could not call these functions), which run on every system because the part that needs PowerShell is one closure. Split `drill.rs` into `parse_drill2(text) -> Result<Vec<Step>, DrillError>` (a `Step` holds its number and its pairs, each pair a fenced `powershell` block and the `Expected` paragraph after it), `run_steps(steps, run: &mut dyn FnMut(&str) -> StepOutput) -> Report` (runs each block through `run`, checks the Expected line and stops at the first miss), `Plant::parse(&str) -> Option<Plant>` with `Plant::step()` (the step the plant must fail at: `one-byte` step 2, `doubled-top-folder` step 3, `no-motw` step 4), `compare_copies(first: &str, second: &str) -> Result<(), String>` (step 7), `check_readme(text: &str) -> Result<(), String>` (the paragraph that starts with the line `MARK-OF-THE-WEB`; the error names MW-01), `plant_one_byte(bytes: &[u8]) -> Vec<u8>` and `compare_payload` (step 6); the real `run` is the one PowerShell session of step 1. The tests: `drill_2_steps_2_to_6_are_read_in_order` (on the real `docs/runbooks/restore-drill.md`: the steps are numbered 2 to 6 and each holds one or more pairs of a block and an Expected line, so a runbook edit that breaks the reading fails here and not on the runner), `variables_persist_between_drill_2_steps` (on the real runbook text and the real `run_steps`: step 3 sets `$dest`, step 4 reads it, and the fake session keeps its map of variables across blocks, so the run passes only if the blocks go through one session), `the_first_miss_stops_the_run_and_names_the_step` (a scripted `run` that gives the Expected text for steps 2 and 3 and not for step 4: steps 5 and 6 are never run and the report names step 4), `a_missing_expected_line_stops_before_any_block_runs` (the runbook text with step 3's Expected line removed gives `no Expected line for step 3`, and `run` was called zero times), `the_three_plants_are_known_and_each_names_a_step` (the three names parse, any other is a usage error with exit 2, and each names the step above), `a_first_run_with_output_or_a_second_run_with_none_fails` (`compare_copies` accepts a first run with no output and a second with exactly one `MISMATCH` line, and refuses the other three combinations), `the_one_byte_plant_changes_exactly_one_byte` (SG-01: the result differs from the input in one position, and `Plant::step()` for `one-byte` is 2), `a_readme_without_the_mark_of_the_web_paragraph_fails` (MW-01: `check_readme` accepts the real `docs/intake/edition-readme.txt` and refuses the same text with the paragraph removed), `a_one_byte_difference_between_two_trees_is_reported` (DT-02: two verified synthetic packages differing in one deterministic byte report that path), `only_declared_attestations_may_differ` (two verified packages differ only in the browser summary and transfer statement; their comparison passes), `a_false_manifest_is_refused` (a package byte changes without its manifest; verification fails before comparison), `every_chip_with_a_placeholder_has_a_sample` (over `strings::chips`) and `terminal_only_names_are_chips` (each entry of `TERMINAL_ONLY` exactly equals a `row.chip` in `strings::chips`, before substitution). Mark the tests that carry a control row of the controls table with the line `// control: <ID>` directly above the test, as `controls_have_tests` reads it: `// control: SG-01` on `the_one_byte_plant_changes_exactly_one_byte`, `// control: MW-01` on `a_readme_without_the_mark_of_the_web_paragraph_fails` and `// control: DT-02` on `a_one_byte_difference_between_two_trees_is_reported`. The chips themselves, FB0607 and the real commands run only in the `windows` job.

9. Generate the marked edition update block of the integrity guide from the transfer runbook. Test `integrity_guide_update_matches_recipe`, `update_interruption_keeps_a_complete_pair`, `rollback_restores_previous_pair_after_success` and `withdrawn_original_is_absent_after_update` through the transfer harness. Never overlay old originals or delete the previous pair after success. Retain it through the next accepted update and verified recovery copy; fault every move in both update and rollback and compare both trees with their manifests.

10. The generated update guide follows the transfer recipe’s edition-only branch before paired ZIP verification: copy the retained originals archive under the new name only when its hash matches the new out-of-band list, preserving the rollback pair. Test matching reuse and mismatched refusal; treating equal extracted contents as archive equality must fail.

11. CHIP_SAMPLES, CHIP_SETUP and TERMINAL_ONLY all key by the exact source chip string before placeholder substitution. TERMINAL_ONLY contains `fieldbook verify <claim-id> --on YYYY-MM-DD`, `fieldbook queue review`, `fieldbook queue accept <proposal-id>` and `fieldbook queue reject <proposal-id> --reason <word>`. Select terminal handling before substitution. `terminal_only_names_are_chips` rejects a bare verb in place of a complete chip.

12. `repeated_drill_runs_use_fresh_extractions` runs the real Windows drill path four times in one test: the ordinary run succeeds, then the one-byte, doubled-top-folder and no-motw plants fail specifically at steps 2, 3 and 4. Each invocation allocates a fresh parent through the runbook extraction block and keeps one PowerShell session for that invocation. Assert four distinct roots, all retaining the path-with-spaces suffix.

13. The Windows chip drill includes audit show and backup list from the shared map. Prepare the same disposable backup target/settings and successful snapshot used by the backup chip before backup list; each literal chip must be in the map and parse. Preserve the confirmed-add fixture variant and base-chip rule.

14. Extend `release_yml_raw_mode_skips_site` to the Windows job: tool tags and Site/absent descriptors run the four Site commands; raw edition tags run none; malformed/mismatched descriptors fail tag validation. Keep tool-tag coverage and the read-only pinned workflow checks.

15. Bind `FIELDBOOK_SECURITY_CONTACT` from the owner-provisioned same-named repository secret in every packaging step this card adds, including scheduled, release and Windows calls as applicable. Forward the environment through child edition/intake commands. Tests use synthetic contact text, verify the workflow binding and require IN-01 for missing/blank input; do not print or commit the real value. No token permission changes are needed.

16. `chip_new_page_writes_independently_in_cmd_and_powershell` runs the confirmed `new page` sample in cmd and in constrained PowerShell, each in its own fresh copy: both must exit 0 and create the page independently. The same sample with an occupied creation ID must exit 2 and change no content.

## Negative control

`cargo xtask drill --plant doubled-top-folder` builds a zip whose top folder is `edition\edition\`. Step 3 must fail with `Test-Path` returning `True` for the second check. Then run the drill on a changed copy of `restore-drill.md` with step 3's Expected line removed: it must stop with "no Expected line for step 3". Then open a scratch pull request that changes only a file under `docs/`: the `windows` job finishes with success and its drill steps show as skipped. Open another that changes only a file under `corpus/`: the drill steps run. Remove the `corpus` half of the `if` of a drill step and repeat: the second pull request must then skip the drill, which shows that the condition is what decides.

In `run_steps`, go on to the next step after a miss: `the_first_miss_stops_the_run_and_names_the_step` must fail. Restore it. Start a new session for each block: `variables_persist_between_drill_2_steps` must fail. Restore it. Let `Plant::step` give step 3 for `no-motw`: `the_three_plants_are_known_and_each_names_a_step` must fail. Restore it. Let `compare_copies` accept a second run with no output: `a_first_run_with_output_or_a_second_run_with_none_fails` must fail. Restore it. Let `compare_payload` ignore a changed deterministic byte: `a_one_byte_difference_between_two_trees_is_reported` must fail. Restore it. Remove `needs: tag-check` from the `windows` job of `release.yml`: `release_yml_triggers` must fail. Restore it. Remove the `backup` row of `CHIP_SETUP`: the chips run must fail and name `backup`. Restore it.

Overlay the originals, delete the prior pair immediately after success, or roll back the edition alone: the corresponding transfer test must fail. Restore each.

Skip manifest verification or broaden the attestation list to include a payload file: the manifest and deterministic-byte tests must fail. Restore each.

Replace a terminal-only entry with its bare verb: `terminal_only_names_are_chips` must fail. Restore it.

Reuse an extraction root across invocations: `repeated_drill_runs_use_fresh_extractions` must fail. Restore it.

Substitute an existing creation ID, or reuse the first shell's mutated fixture: `chip_new_page_writes_independently_in_cmd_and_powershell` must fail. Restore each.

Restore the unconditional Windows tag condition: `release_yml_raw_mode_skips_site` must fail. Restore the validated mode condition.

## Rollback

Revert the merge commit. The drill steps leave the `windows` job of `ci.yml`, which keeps the nextest step of `windows-facts` and stays in `ci-ok`; `release.yml` loses its own `windows` job; DT-02 has no compare until the drill returns, and E1 waits for drill 2.

## BLOCKED

A request leaves `file:` in Edge on Windows, the CSP is rejected, a chip fails in CLM, or the trees differ. Each is a stop-and-ask case: name the page, chip or file, and stop.
