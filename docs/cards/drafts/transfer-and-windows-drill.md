# transfer-and-windows-drill

- **Runs where:** home, CI Linux, CI Windows
- **Schema impact:** none
- **Review:** owner

## Outcome

The `windows` job of AD-08 runs drill 2 of restore-drill.md on windows-2025, through `cargo xtask drill`. It extracts into a path with spaces, runs the hash checks, the Edge harness on the extracted edition and every command chip in cmd and in PowerShell Constrained Language Mode, and makes FB0607 (a brief printed on more than one page) an error. The job already exists (`windows-facts` built it, gated by `changes` and needed by `ci-ok`); this card adds the drill steps after its nextest step. They run when `changes.code` or `changes.corpus` is true, and the full run is weekly (`scheduled.yml`) and on release tags, for which `release.yml` gets a `windows` job of its own. `scheduled.yml` compares the Linux and Windows trees (DT-02). Drill 3 on the laptop is the owner's own item in PLAN.md, so this card closes without it and without IT's answers.

## Steps

1. `drill.rs`: `cargo xtask drill` reads the fenced `powershell` blocks of Drill 2 steps 2 to 6 from `restore-drill.md` and runs them in order, after `cargo xtask edition`; step 2 runs the transfer.md loop with the real file names. A block and the Expected paragraph after it form a pair, and a step holds one or more pairs. The blocks run in ONE PowerShell session, because variables set in step 3 are read in steps 4 to 6: one child `powershell -NoProfile -Command -` fed on standard input, each block followed by the line `Write-Output "<<END step N>>"`. The output is split at those sentinels and each part is compared with the Expected line of that block. `run_steps` takes the session as its `run` closure, so tests drive it with a fake that keeps variables in a map. It stops at the first miss, naming the step. The runbook stays the one source of the commands.
2. After step 4 it checks that the extracted `README.txt` holds the Mark-of-the-Web paragraph (MW-01). It copies one zip, changes one byte, and requires the step 2 loop to print `False` for it (SG-01).
3. Chips: use the chip parser and shared cases made by `check-command`. Availability means that the complete source chip, filled with the shared valid syntax samples, parses with the actual `Cli` of this built profile; leaf-verb existence is insufficient. `PENDING` remains the exact-full-chip test expectation in `tests/chips.rs`, not a second runtime verb registry. A pending flag variant is not executed, and the ordinary chip suite must agree with the actual full-command parse. Every now-parseable source chip has its execution case before it leaves `PENDING`.

    The one case table is `tests/support/chip_cases.rs`, included by `#[path]` from this card's `drill.rs` and from `tests/chips.rs`, and from `crates/fieldbook/tests/drill5.rs` once that file exists. It is keyed by the exact pre-substitution `row.chip` string together with its execution context, and holds the sample values, fixture, setup steps and expected outcome; it defines neither verbs nor a built or feature list. Move the sample and setup data into it rather than keeping parallel `CHIP_SAMPLES` or `CHIP_SETUP` registries, and derive `TERMINAL_ONLY` from its `Terminal` expectations rather than keeping a second terminal list.

    Run each substituted literal command in `cmd /c` and in `powershell` with the language mode set to `ConstrainedLanguage`, using the current runner. First validate the case's substituted argv with the same `Cli`; a bad case sample is a setup failure, never a reason to mark the chip pending. Each case, shell and supplemental confirmed-add variant gets an independent fresh root. Default `Home` cases use the existing temporary Home Corpus and State fixture; a Laptop case runs only through the existing provisioned drill5 path and its test-hooks shim, in both shells and with a fresh layout per case. Literal `ask` and `decide` need no endpoint settings, key or network requirement: their default route is Handoff. A table entry records the owning contract's successful or findings result; an I/O or setup failure is not a passing command smoke. Only a case that names a refusal may accept exit 2, with its documented diagnostic and an unchanged-tree assertion; no case accepts an arbitrary exit 2.

    Context and build availability are separate. `Home` cases run in the ordinary Windows chip drill and `Laptop` cases through the existing provisioned drill5 path. No release binary acquires test hooks, and no new policy or known-folder override is introduced. Full-chip parsing still determines whether a case exists in that build; a chip's release tag is not a replacement build registry. Record which context exercised each chip, and do not claim Home execution proves Laptop behavior.

    The cases keep their existing command text and owning success or findings expectation:

    - `fieldbook verify <claim-id> --on YYYY-MM-DD`, `fieldbook queue review`, `fieldbook queue accept <proposal-id>` and `fieldbook queue reject <proposal-id> --reason <word>`: the existing valid syntax samples on a fresh Home copy, with the `Terminal` expectation selected by source key before substitution. Preserve the current stderr `needs a terminal` contract and let any other output fail; do not weaken a gate or require a success exit. These four are the derived `TERMINAL_ONLY` set.
    - `fieldbook backup`: a disposable synthetic/public Corpus and State root (never a copy that must match the executable's compile-time checkout), that generation's support catalogue built by the real pure producer and its separately known expected digest verified through the real optional raw path first, the existing target setup outside both the copy and the State folder; exit 0 and a successful snapshot.
    - `fieldbook backup verify`, `fieldbook backup list` and `fieldbook restore --snapshot <n> --drill`: an independent copy for each shell and case, that generation's support catalogue built by the real pure producer and its separately known expected digest verified through the real optional raw path before the target setup and a successful `backup` first, with `n` = 1. Exit 0 with the owning verify, list or drill success evidence; list keeps the snapshot precondition.
    - The three base add chips, file, file with source id and folder: existing fresh synthetic candidate files and a valid source id. Run the literal base chip without adding a confirmation: exit 1 with FB0410 and an unchanged Corpus. Keep the separately identified confirmed-add variant on another fresh copy, adding the confirmation only for that supplemental test and requiring a successful addition. It is a variant of the same source-chip case, not another `strings` row or verb.
    - `fieldbook new page --confirm-public <area>-<slug> --type <type> --subarea <subarea>`: the existing valid absent-id Home sample; each shell independently exits 0 and creates the page. Keep the occupied-id supplemental case: exit 2 and unchanged content.
    - `fieldbook new note --ai-drafted --confirm-public --area <a> --from <file>`: a private temporary `corpus-mini` copy whose `corpus.toml` is set to schema 2, the valid `tests/fixtures/handoff/draft-note.txt` of its owning card copied outside `corpus/`, and a fixture-backed area; exit 0 and one note. Keep the schema-1 exit-2 test in the owning `new_note` suite. Never mutate the committed schema-1 `corpus-mini` or suppress the confirmation flag.
    - `fieldbook ask "<question>"`: a fresh Home `corpus-mini` with default Handoff settings and a valid synthetic question, and no endpoint configuration; exit 0 with a deferred pack. Silent is supported, not a skip reason.
    - `fieldbook decide <file>`: a fresh `corpus-mini` plus the owning `tests/fixtures/state-decide/state/` facts, where the file resolves to the valid `decisions/D-0001.toml` beneath that State, and default Handoff; exit 0 with the pack and sidecar. Do not use an arbitrary file outside `decisions/` and then accept its usage error.
