# r2-org-intake

- **Runs where:** home, CI Linux, CI Windows
- **Schema impact:** none
- **Review:** owner

## Outcome

On the laptop, a company document becomes a source in the company store, the `overlay\` folder, and in no other tree. `add FILE`, `add FILE --text TEXTFILE` and `add FILE --propose` read the document, extract plain text, Markdown, HTML, CSV and workbooks with the core extractors, take pasted text for a PDF or a Word file (method `supplied`), and write the original, the text and one row whose `handling` is the label set that the labeller found (`unlabelled` when nothing says, until a person gives it a real label with `label add`, which adds a line to the label ledger and does not rewrite the row). `queue accept` writes the same files through a second Admit, `overlay-add@1`, which admits a proposal only if the store holds every one of its labels (FB0412). The card also builds the verbs `label add`, `label reapply` and `label show`. `overlay-add@1` also admits a proposal of the kind `reclassify`, which moves a source version to another `doc_kind` or `series` and changes no other cell, and `add --doc-kind WORD` declares the document kind of what it adds. A company source has a company id (`SO-000042`) and so cannot repeat a public id by shape. Before any company file is read, every stage that would see it is checked against the `sees` word of its registry row, and a stage that sees `public` only refuses a labelled file with FB0901. The source page labels a supplied text "text supplied by hand; not checked against the original", and a consequential claim that rests on one raises FB0223.

## Why

- The verbs and the overlay paths are the R2 row of [AD-17](../../decisions/0001-foundation.md#ad-17-authoring-experience); the folders (`edition\`, `overlay\`, `state\`) are the Data root bullet of [AD-16](../../decisions/0001-foundation.md#ad-16-release-2-shell-and-its-gate); the write rules (one journal pair for each write, the row last) are AL-01 in [controls.md](../../controls.md). Company text must never reach a source repository or an edition, and inside the company store the question is what each label may do and not who may enter, so this is the first code that reads company text and the owner reviews it before it merges. The barrier is the store rule: the repository Corpus holds `public` only, and the company store holds the labels its `holds` list names ([ADR 0004, section 4](../../decisions/0004-company-boundary.md#4-stores-and-admission)).
- The program starts no process unless an extractor has a row in the adapter table, so it does not run poppler on the laptop. A text, Markdown, HTML, CSV or workbook (`.xlsx`, `.xlsm`) file is extracted in the exe by the core extractors; a PDF or a Word file is added with no extraction, or with text the owner pasted into a file (`supplied`). A reviewed extractor for a company device is one more row of the same kind (`sees` labelled), in process or as a named helper with `Needs::Process`, and writes its output into the company store beside the original with the original's labels; no helper runs without a row, and none is built here. Reading a PDF in the exe is `later-pdf-native-ocr`, and the company-document profiles (quote, specification, schedule, transaction) are `later-company-doc-profiles`. The seam for them is built here (the extractor row, `sees` and the company source kinds), and each profile is built when the pricing module needs it. Nothing the owner reads says that R2 intake handles company PDF or Word files yet.
- A supplied text is not the original's own text. The format already names the method ([Extraction](../../reference/corpus-format.md#extraction)) and says FB0223 treats it like a thin page; the home extraction and source renderer already implement both; this card reuses them.
- The model gate checks the labels of each model request. A stage that does not call a model (an extractor, the rules, the index, the Admit) has only its registry row to say what it may see, and that row has a `sees` word, `public` or `labelled`. The check is made once, when the stages are wired and before any file is opened. A stage that sees `public` only and is wired for a labelled file fails at once, and one test pins the `sees` word of every stage.
- The company store merges with the edition in one index, so an id that repeated a public id would make a citation such as `S-0042-v1` name two documents. The id decision is made now, and it is by shape: a company source is `SO-000042`, with six to ten digits, the writer digits first and a prefix that no public id has ([ADR 0004, section 10](../../decisions/0004-company-boundary.md#10-identity)). The numbering needs no shared counter and no reserved range. Allocation reads this store's rows and this writer's only (`r2-company-ids`), and the edition's register is read for hashes only, so a file that the edition already holds is `present`. A test fails on an id that appears in two stores.
- `corpus-add@1` admits a proposal whose labels are all `public` and refuses every company label (the Corpus rule of `labels::admit`: FB0400 for a marking, FB0410 for any other label). `overlay-add@1` admits a proposal whose labels the company store holds (FB0412 otherwise), and `public` is one of them, so the company profile does not refuse what the repository holds. A proposal file copied between state folders is labelled again at accept and checked against the store it would write to, so it cannot write into the wrong tree, whatever its `labels` line says.
- A company source arrives with `doc_kind` empty, which means not yet classified ([ADR 0004, section 9](../../decisions/0004-company-boundary.md#9-provenance-extraction-and-records)). The failure this prevents: a backlog of contracts, quotes and exports that all look alike and are then re-keyed by hand. Three routes fill the cell and each goes through the same vocabulary: `--doc-kind` on `add`, a rule of `rules.toml` that suggests it and a person confirms at review, and a `reclassify` proposal for a source that is already held. `series` is not set here: `sync` writes it for a vintage stream (`r2-pull-and-sync`), and a `reclassify` may change it. The repository Corpus keeps both cells empty (FB0215). A `reclassify` replaces one line of a register, so a planned write learns to show a replaced line (`shown`, step 1): the failure it prevents is an accept screen that prints nothing for a changed row, or prints the wrong cells.
- Design: the [MAP.md](../../design/MAP.md) row "Source drawer" (SourceDrawer, LocatorView, Excerpt, AnswerMeta), built as the page `s/<version-id>.html`; [HANDOFF.md](../../design/HANDOFF.md) section 5 Components (the `SourceDrawer` row, whose five variants stay as they are; the note is one line under the page title), section 7 Status display rules (only verification gets colour, so the note is words and a mark, never a status colour), and section 0 Fixed template text (the line is shown by the template alone, so it is not a frozen string; listing it in that table is the UI lane's pull request to the spec). Token groups: Colour (the neutral text and border tokens), Type and Space of section 4.

## Out of scope

- The company store itself: `init --overlay`, `build --overlay`, how `check` and `search` read it, the label banner and the store's column set (`r2-overlay`, `r2-company-ids`). Below, "the company store Model" is the one that `r2-overlay` loads for `check`.
- Reading a PDF in the exe (`later-pdf-native-ocr`), reading a Word file (`later-docx-import`), OCR, a reviewed extractor row for a company device, and the company-document profiles (`later-company-doc-profiles`). The seam is built here and each profile is built when the pricing module needs it. `cargo xtask stage` runs at home only.
- Correlation against the edition's units and a `VersionOf` link to an edition source. The correlator's index is built over the overlay's units; the INT idea of searching the overlay and the edition's shards together waits for the search `r2-overlay` builds.
- A range of ids reserved for the company store. It is not needed, because company ids differ from public ids by shape; the allocator and the shape checks (FB0416, FB0417) are `r2-company-ids`. This card has the test that no id appears in two stores.
- A folder other than `state\inbox\` for `--propose`: a proposal keeps the file name relative to the inbox, and that format is frozen. Direct `add` takes any path.
- The company store's regression set and company notes (`r2-state-and-journal`); `migrate` (`r2-migrate`); the policy rows that decide whether a model may see a label (`policy-load`, `ai-config-and-keys`). The origin of a figure (`quoted`, `computed` or `judgment`) is the `basis` column of the record envelope (`r2-records`), not a property of a source.

## Steps

1. Core, `add.rs`: `Target { Corpus, Overlay }` with pure functions: `original_dir()` (`sources/public` or `sources/org`), `text_dir()` and `register()` (`sources/text` and `registers/sources.csv` for both), `store()` (`StoreId::Corpus` or `StoreId::Overlay`) and `default_kind()` (none, or `company_document`). Every path is relative to the content root (`corpus` at home, `overlay` on the laptop). `AddOptions` gains `target` (default `Corpus`), `labels` (the `LabelSet` that the labeller gave the original; the plan writes `to_cell()` to the `handling` cell), `writer` (from `store.toml`), `other_stores: Option<StoreKeys>` and `doc_kind: Option<DocKind>` (the plan writes its word to the `doc_kind` cell and leaves the cell empty for `None`; `series` and the three origin cells are always empty here, because only a puller writes them, FB0215; a `doc_kind` with `Target::Corpus` is a usage error before the plan is built). `store_keys(csv_text) -> Result<StoreKeys, StoreKeysError>` finds the columns `source_id`, `version` and `sha256` by header name in the register of another store of the layout (the edition) and keeps the version ids and hashes; a missing column or an unparsable row is an error that names the line. With `Target::Overlay`, `plan_add` stores the original under `original_dir()` with its version id as the stem, sets `handling` to the labels, sets `source_kind` to the kind given or `company_document` (the kinds `vendor_quote`, `company_record` and `company_document` exist in the company store only), allocates the source id with `ids::next_company(Family::Source, writer, rows)` of `r2-company-ids` from the rows of this store and this writer only, and returns `AddOutcome::Present` when the hash is in the company register or in the keys of another store. `--source` finds its source in the company register only. With `Target::Corpus` no output byte changes: the tests of `add-new-and-edition` and `add-folder-mode` pass untouched. `PlannedWrite` of `pipeline-ports` (in `pipeline/admit.rs`) gains the field `shown`, which `PlannedWrite::new` sets to `Tail` so that no earlier plan changes: `Tail`, the default, which every plan so far returns and for which the accept screen keeps printing the lines after the old text of a replaced file (the plan must keep the old text as a prefix), and `Rows(Vec<String>)`, the lines to print in place of them for a replaced file whose new text does not keep the old text as a prefix (step 4a is the first plan that returns it, and `r2-records` returns it for its records file). The prefix rule applies to `Tail` only. A plan that returns `Rows` sets `shown` on the value that `PlannedWrite::new` gave it. `queue accept` prints the rows of a `Rows` entry as they are, and `io/queue.rs` ignores `shown`.
2. Core, `pipeline/candidate.rs`, `view.rs`, `admit.rs`. `Vocab::for_store(&StoreRule)`: for the Corpus it is `from_schema()`, which offers ten fields and never `doc_kind`; for a company store `source_kind` offers `vendor_quote`, `company_record` and `company_document`, there is no `authority_tier` [J] (the Corpus's tiers rank public publishers and this card sets no company tier), and `doc_kind` is offered with the eleven words of `DocKind::ALL` (`SuggestField::DocKind`, built by `pipeline-ports`), so `Vocab::fields()` of a company store lists `doc_kind` and not `authority_tier`. A suggestion for `authority_tier` or for a `doc_kind` outside `DocKind::ALL` on a company candidate fails `validate` and is dropped and counted like any value outside the vocabulary (`DropReason::FieldNotOffered` for a field the vocabulary does not list), and a person's edit goes through `Vocab` too. The rules check of `check/pipeline.rs` (FB0826) builds its vocabulary with `Vocab::for_store` of the store's rule, so a `set` of `doc_kind` in the `rules.toml` of a company store is accepted, and in the Corpus's it is FB0826. `CorpusView::with_stores(self, StoreKeys)` makes `has_hash` read the keys of the other stores as well as the rows; `source`, `next_version` and the question rows read this store only, so no `VersionOf` link to an edition source is made, and the id allocator never reads the keys. `from_model` is unchanged and is what home uses. `corpus-add@1` returns the refusal of `labels::admit` with `StoreRule::corpus()` for a proposal whose labels are not all `public` (FB0400 for `marked`, FB0410 for any other label).
3. Binary, `adapters/extract_io.rs`: `Supplied` implements `Extractor` as `supplied@1`. `accepts` is always false, because only `--text` selects it. `extract(bytes, ext)` delegates text parsing to `extraction::supplied_text` from `extract-and-locators`: the helper drops a leading byte order mark, refuses bytes that are not UTF-8 with `ExtractError::NotText` naming `supplied@1`, turns CRLF and CR into LF, and splits on every line that is exactly `[page break]` [J]. Each part is a page, `p0001` upward, and an empty part is still a page. The `Extraction` is built by the constructor and thin-page rule that `Plain` uses, with `method` `supplied`, `tool` `supplied` and `tool_version` `1`. `read_text(world, path)` reads the file through the `World` and returns a usage error (exit 2, no code) for a missing file, a folder or a file over the size limit `plain@1` applies. The text goes through the labeller that `add` runs on an original before anything is staged or written (`labels::for_text` with the context of the store, then `labels::admit`), and the extraction takes the union of the labels of the original and of the text, because the pasted text is derived from the original. A refusal is FB0400 at the repository Corpus and FB0412 in a company store, exit 1, with one `refuse` event (`labels`, `reason = store`, and the `sha256` and `name_sha256` of the text file), and nothing written.
4. Binary, `adapters/admit_overlay.rs`: `OverlayAdd` implements `Admit` as `overlay-add@1`. `plan` labels the extraction text again and takes the union with the proposal's `labels` (so a proposal file edited by hand cannot lower a label), returns the refusal of `labels::admit` with the store's rule (FB0412) when the store does not hold every label, `KindNotBuilt` for any kind but `new_source`, `new_version` and `reclassify` (step 4a), and `AdmitOutcome::Present { id }` for an ordinary duplicate hash (a reclassify has none). Otherwise it returns `AdmitOutcome::Planned { files, affected }` with the source reference and builds the files in the order of `corpus-add@1` (the original, the extraction files, `extraction.toml`, the row last) by calling the same row builder with `Target::Overlay`; the source id comes from the company allocator. The list holds no path outside `sources/org/`, `sources/text/<version-id>/` and `registers/sources.csv`. The row builder writes the `doc_kind` cell from the `doc_kind` field of the accepted proposal (empty when the proposal has none) and writes `series` and the three origin cells only as the proposal's `origin` gives them, which is not at all for a file that came through `add --propose`; `r2-pull-and-sync` adds the origin path through this same builder.
4a. The kind `reclassify` (the body `Reclassify { source_version, doc_kind, series }` of `pipeline-ports`). `add.rs` (core) gains `reclassify_row(register: &str, version: &str, doc_kind: &str, series: &str) -> Result<Reclassified, ReclassifyError>`: it parses `version` as a source `VersionId` and matches both `source_id` and numeric `version` columns by header name, sets the `doc_kind` cell when `doc_kind` is not empty and the `series` cell when `series` is not empty (an empty field leaves its cell as it is, so no proposal clears a cell), writes that one row again with the writer that `plan_add` uses, and keeps every other line byte for byte, with the line endings the file had. `Reclassified { text, changes }` holds one `Change { column, old, new }` for each cell that differs, and `Reclassified::lines(version)` returns the display lines `~ <version-id>  <column>  <old or ->  ->  <new>`, which name the changed cells and print no other cell, so a cell of a restricted row never reaches the screen. `ReclassifyError` is `NoSuchVersion(id)`, `MissingColumn(name)` (a register with fewer than 28 columns) or `BadCell(column)` (a `doc_kind` outside `DocKind::ALL` or a `series` that is not `vocab::stream_id_form`; the parser of the proposal refuses both, and this is the second check for a file edited after it was written). `OverlayAdd::plan` for a `reclassify` reads `registers/sources.csv` of the content root through the `World`, takes the labels in force for the row (its `handling` cell with the ledger lines for it) in union with the proposal's `labels`, so a proposal edited to name fewer labels does not lower them, refuses with FB0412 when the store does not hold one of them (as step 4 does), and returns a list of the one `Rendered` write of `registers/sources.csv` with `shown = Rows(lines)`. A version that is not in this store's register is `AdmitError::Invalid` with the message `no such source version in this store: <id>`. A set with no change (the cells already hold the proposed words, as after a crash between the write and `queue.accept`) returns `AdmitOutcome::Planned { files: [], affected: [the source version reference] }`, for which `queue accept` prints `writes no Corpus file` and completes. It is an acceptance decision, not the duplicate-original `Present` outcome. The list holds no original, no text and no other register, so the hash, the ids, `handling`, `supersedes` and `source_kind` of the version cannot change. `kinds.rs` gains the row `reclassify`, a `KindRow`: `check_source` requires the named version to be in the register (else `no such source version in this store: <id>`, exit 1, nothing written), `admit` returns `Box::new(BorrowedAdmit(&env.stages.admit))`, `after_accept` does nothing (a `reclassify` has no staging folder), and `describe` prints `reclassify  <version-id>` and, for each changed cell, a line `  <column>  <old or ->  ->  <new>`. In the repository Corpus `Stages.admit` is `corpus-add@1`, which returns `KindNotBuilt`, so `queue accept` prints `kind reclassify is not built in this build` and the Corpus keeps both cells empty. Remove `reclassify` from `NOT_YET_BUILT` in `tests/queue.rs`. No verb writes a `reclassify` proposal: AD-17 has none, and a new verb needs a superseding ADR that the owner reviews. Until the owner decides one, the proposal is a file in `queue/` in the shape of `tests/fixtures/queue/reclassify.toml`, and `queue list`, `queue show`, `queue accept` and `queue reject` treat it like any other kind.
5. Binary, `adapters/pipeline.rs`: `Stages::for_labels(model: &Model, settings, rows, ai, sink, &LabelSet, supplied) -> Result<Stages, SeesRefusal>`. It builds what `configured` builds from the same `model`, with `overlay-add@1` as the Admit for the company store and `corpus-add@1` for the Corpus, and it reads the rules from `<content_root>/pipeline/rules.toml` of the layout. Then it checks the labels against the `sees` word of every row it could use: the extractors `plain@1`, `html-strip@1`, `csv-rows@1`, `xlsx-sheets@1` and `staged@1` (and `supplied@1` when `supplied` is true), the classifier, the correlator, `bm25f@1` and the Admit. A row whose `sees` is `public` refuses any set that is not exactly `public`, and the first such row gives `SeesRefusal { port, id }`. The caller prints `error[FB0901]: <port> <id> does not see labelled data`, appends one `refuse` event (`verb`, `code`, `labels`, `reason = store`), exits 2 and has written nothing, not even a staging folder. `Stages::defaults` and `configured` are unchanged.
6. Label threading. `propose.rs` sets `Candidate.labels` and the proposal's `labels` from the labeller: the markings in its text, the policy's `[[source]]` rules for the file's system and stream (only a pulled file has them, and `r2-pull-and-sync` adds that lookup; a hand-added file has none), and the store default, `unlabelled`. Before it writes anything to `staging/` or `queue/`, it admits the labels against the bound destination company store rule (FB0412, reason `store`, nothing written); inbox, staging and queue are transit content, so State holds does not add a second admission gate. For the company store it reads the other stores' registers from `layout.other_registers()` (the edition's `sources.csv` at `<data_root>/edition/corpus/registers/sources.csv`; an absent file is no keys; an unreadable one is exit 3 with the `StoreKeysError`) and builds the view with `with_stores`. `add FILE --propose` is the single-file form: a file inside the state folder's `inbox/` is proposed as the folder form proposes it, and a file outside it is a usage error (exit 2, the message names the inbox path), the rule that `review-queue` gives for a folder. `--text TEXTFILE` is accepted only with a single file; a staging folder that already exists for that file's hash is a usage error naming the folder, because it holds text written by another run. The extraction choice becomes: `supplied@1` when `--text` is given, else `staged@1` when `staging/<sha256>/extraction.toml` exists, else the core extractor, else none. The proposal's `extraction` then reads `{ adapter = "supplied@1", method = "supplied", ... }`. `propose.rs`, `queue accept` and `queue ingest` build their stages with `for_labels`. `queue accept` labels the extraction again (step 4) and refuses a proposal whose labels the layout's content store does not hold with FB0412 (exit 2, one `refuse` event, nothing written), after the terminal and role gate of `review-queue`; a proposal made at home and copied to the laptop therefore cannot write into the wrong tree. `io/queue.rs` joins each path of a plan to `layout.content_root()`, where it joined the Corpus root.
7. Binary, `add.rs`, direct `add` on the laptop. When `layout.content_store()` is the company store, `add_one` uses `Target::Overlay` and the keys of step 6; the order is still: read the bytes, `check_type` (FB0821), the labeller and store admission (FB0400 at the Corpus, FB0412 in a company store), then the plan. The extraction is `Supplied` when `--text` is given, else `extraction::select(ext, head)`, else none; its page files and `extraction.toml` are put in the plan as `Rendered` writes between the original and the row, using the function that renders an `Extraction` for `staging/`. The journal pair, the `present` and `refused` lines and the exit codes are those of `add-folder-mode`. A file with no extraction prints `added      SO-000001-v1  spec.pdf  needs-extraction` [J] and its `--json` object gains `"needs_extraction": true`.
