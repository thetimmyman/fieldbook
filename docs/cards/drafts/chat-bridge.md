# chat-bridge

- **Runs where:** home, CI Linux, CI Windows
- **Schema impact:** none
- **Review:** owner

## Outcome

`fieldbook chat [--site DIR]` of the AI build built with the further feature `bridge` serves the Assistant page with live answers. It binds one listener on `127.0.0.1` and a port the operating system picks, prints `http://127.0.0.1:<port>/#t=<token>`, starts no browser, and serves only the compiled chat shell at `GET /` and the verified native assets named by one renderer-owned response catalogue: never the built site folder generally. The shell is rendered at run time with `CSP_BRIDGE` and never written to a file. Nine `/api/*` paths (eleven routes), each needing the session token, let the page fill a context pack by deterministic retrieval and by a "Suggest context" button, pin, remove and add items, save named packs, see the exact request and its labels before it goes, see the labels that went after it has gone, send it through the audited gate, read an answer whose citations are checked against the context that was sent, and file an answer as a `note` proposal. On the default route, Handoff, a send returns the pack and the paste-back finishes the round trip, so it is recorded. The session ends on the page's End session button, on `q` and Enter at a terminal, or after `[chat] idle_minutes` with no request. Neither the silent build nor the AI build without `bridge` contains any of this code.

## Why

- This is the one listener the program has, and only a build with `bridge` holds it: the Chat row of the Surfaces table in [AD-01](../../decisions/0001-foundation.md#ad-01-architecture), the Assistant bullet of [AD-15](../../decisions/0001-foundation.md#ad-15-ui-technology-and-design-system) and the Assistant-per-host table of [AD-16](../../decisions/0001-foundation.md#ad-16-release-2-shell-and-its-gate). It is the code IT's question on the loopback listener is about, so the owner reviews it at the release [gate](../../decisions/0001-foundation.md#gates). Four controls are built here and appear in [controls.md](../../controls.md): HG-13 (loopback only), HG-14 (token, `Host` and `Origin` on every request), HG-15 (the two page policies) and AL-05 (a session leaves a trace). NS-06 gains the capture of one listener in the chat step.
- The server is written by hand over `std::net` in one file, using no web framework: a crate that parses inbound HTTP would be one more direct crate on top of those of the AI build, and the surface here is small enough to own and to property-test. The limits are fixed: request line and headers 8 KiB, body 256 KiB, 5 s to read a request, 4 connections; a send ends when the limits of the model gate end it (`timeout_s` and `retries` of the settings). The order of checks is fixed too: parse, `Host`, `Origin`, token, then size, then the handler, so a client that is not the owner never reaches code that costs anything.
- The token travels in the URL fragment, which a browser does not send to the server, and the page clears it with `history.replaceState`. It is compared in constant time, and it is in no query string, header the server writes, log, journal line or error. `Host` must equal `127.0.0.1:<port>` and `Origin` must be absent or the same origin, which closes DNS rebinding and cross-site requests. A page opened from `file:` has no token and no route to this server, so it stays on Handoff and says "not recorded".
- The page security policy is split ([Site output paths](../../reference/corpus-format.md#site-output-paths)). `CSP_STATIC` stays on every page written to a Corpus or an edition. `CSP_BRIDGE` (`connect-src 'self'`) is on the one page that `GET /` renders from memory. Both constants exist since `build-v0`; this card only uses the second, and a test makes sure it is never written.
- Nothing here reaches a model except through `ModelPort`, so every send has the egress check (the destination's row and the labels of the request), the marking check, the budget and the `ai.begin` before the byte leaves ([AD-18](../../decisions/0001-foundation.md#ad-18-security-and-confidentiality-guardrails)). A policy refusal never falls back; an availability failure offers the Handoff pack of the same request. A "verified" citation means the reference exists at its locator, not that the answer is right.
- "Suggest context" sends the question and the ids and titles of the 60 best retrieval hits [J], and nothing else, as an ordinary previewed request. The reply is a list of ids; ids that are not in the view of the planned route are dropped and counted, and the owner pins or removes the rest. Context stays deterministic until the owner presses the button.
- Design: the [MAP.md](../../design/MAP.md) row `#assistant`, `#assistant/<id>` (built by `assistant-page`; this card adds a transport to what that page renders when served and adds no route of its own). [HANDOFF.md](../../design/HANDOFF.md) section 9 (AI integration: AI-ready, model-optional) and its Assistant page subsection, section 5 Components (`StatusChip` for the connection state, `StepCard`, `VerdictChips`, `Fold`, `PackMini`) and section 7 Status display rules (a state is a word, never a colour alone). Token groups: Colour, Type, Space, Shape and line and Size of section 4, reached through `app.css`. This card adds no token, and `bridge.js` sets no style.

## Out of scope

- A browser launch (`later-chat-open`; a launch is a subprocess), streamed answers (`later-streaming`; `StreamState::Streaming` is declared and never produced), and any use of the page from a second computer. The listener stays on loopback. The seam for a company-network mode behind a company sign-in is `admit`, the one function that decides who may make a request, and the `Session` that `adapters/chat.rs` writes into the envelope of every event; that mode is `later-remote-tools`, needs the company's IT owners to approve it, and is not built here.
- Company records in the chat are not a separate feature and need no new code here. The context is the `LabelledView` for the planned route: a record is in it when every label it carries is in the allow set of that route's destination (the policy row narrowed by the owner's list) and also in the Bridge's own allow set (step 8), and a record outside either is left out whole. The page shows the Bridge's fixed line `Some records were omitted.`, with no number and no count of its own, whatever the route; the stored Handoff text (`handoff/H-nnnn.txt` and a Handoff reply's `pack_text`) keeps its own Handoff line with the count. With the floor (no policy) the only route is Handoff and the view holds `public` records. The company store and the labels are `r2-overlay` and `core-labels`; the tests of this card use a hand-built model with a synthetic label. The page shows the owner what was sent, by label, before the send (the preview) and after it (the answer card). The laptop's chat step belongs to `r2-state-and-journal`.
- The endpoint adapter, the gate, the router, `ask`, the pack builder and the cite check: they are called here and not changed (`model-adapter-openai`, `model-gate`, `model-handoff-ask`, `handoff-context`, `handoff-cite-check`). The static Assistant page, its markup, `assist.js` and its Handoff flow (`assistant-page`).
- A listing of network paths in `status`. `status` never touches the network; the evidence of a listener is the capture of Drill 5.
- A flag that changes the address or the port. The Bridge binds 127.0.0.1 and a port the operating system picks (`bind` keeps its guard for a test).
- Threads kept across a reload (`later-chat-threads`) and the assistant asking for units outside the context (`later-chat-request-items`).
- A CORS mode, a cookie, a second session in one state folder (FB0954; the lock is per state folder and each Windows user has a state folder of their own, so each user can run one session), keep-alive, chunked bodies, HTTP/2, TLS on the loopback listener, and any route not in the table of step 2.
- A browser that clicks or types. The drill step `bridge-requests` loads the page once in headless Edge, with no CDP, and reads two things from the dumped DOM (step 16); the page's behaviour under clicks is checked by the owner at review in Edge and, on the laptop, by the chat step of Drill 5 (`r2-state-and-journal`).

## Steps

1. The shapes. `ports/chat.rs` already holds the status types (`ai-config-and-keys`), `SendPreview` and `Scan` (`model-gate`), and `Transport` and `ChatCaps` (`assistant-page`), and it re-exports `Origin`, `ContextItem`, `ContextPack` and `NamedPack` from `assist` (`handoff-context`), so the names the page uses do not move. Add the rest, pure data with `serde` derives and no `serde_json`: `StreamState { Idle, Waiting { since_ms }, Streaming { chars }, Done, Failed { code }, Cancelled }`, `ErrKind { Policy, Availability, Invalid }`, `ApiError { code, kind, retryable, fallback }` (`fallback` is an `Option<Transport>` and only ever `Handoff`), `CiteStatus` and `CiteVerdict { reference, status, source_exists, locator: FactVerdict, quote: FactVerdict }` (both defined in `assist` by `handoff-cite-check` and re-exported here; the nine statuses are `broken`, `broken_locator`, `outside_context`, `superseded`, `weak`, `unchecked_locator`, `unchecked_quote`, `quote_mismatch`, `verified`) and `AnswerCard { text, verdicts, neutral, prov, sent, unchecked }`, where `neutral` lists the references to questions and conflicts, which have no status, and `sent` is a `Sent { dest, labels }`: the destination name and the label set that the gate wrote into `ai.begin` for this call, so that after the call the page shows the same words it showed in the preview. This card's own request and reply shapes: `ContextEdits`, a re-export of `assist::Edits { pinned, removed, added, suggested }` (lists of unit ids; `handoff-context`), `SendReply`, a tagged enum with `answer` (an `AnswerCard`), `suggestion` (`ids`, `dropped`), `handoff` (`ticket`, `pack_path`, `pack_text`), `cancelled` and `error` (an `ApiError` and an optional `handoff`, which carries the fallback pack when the router offered one), and `NoteReply { proposal }`. A message text is in none of them: the page shows the catalogue line for `code`. `SendPreview.audited` is set by the gate. The Bridge asks the gate for a preview and, when `audited` is false, answers FB0903 instead of returning it, so every preview the Bridge returns has `audited = true`; a preview that the `file:` page builds for itself has `audited = false` and the page prints "Not recorded." `AnswerCard.unchecked` is true only when the cite check could not run because the Corpus could not be loaded or the context could not be rebuilt; then `verdicts` is empty and the page prints "Do not use this answer." and the catalogue line of the code. It is never true because an answer had no citations. The JSON names are part of the UI lane's contract; `tests/chat_json.rs` (`chat_shape_names_are_stable`) writes one value of each type and compares it with `tests/golden/chat/shapes.json`, in the binary because core names no `serde_json`. The golden holds the nine status names. The `chat_json` serialization cases include `unchecked_quote` with an Unchecked quote fact, and the status list is compared with the shared enum.
2. The route table, data only. In the AI build, `io/net/routes.rs` holds no socket type. `RouteId { Status, Context, Suggest, Preview, Send, Note, Cancel, PacksGet, PackPut, PackDelete, Quit }`, `Route { method, path, id, token, reaches_model }` and `ROUTES`: `GET /api/status`, `POST /api/context`, `POST /api/suggest`, `POST /api/preview`, `POST /api/send`, `POST /api/note`, `POST /api/cancel`, `GET`, `PUT` and `DELETE /api/packs`, and `POST /api/quit`, eleven rows over nine paths. Every row needs the token, and `reaches_model` is true for `Send` only, because `Suggest` makes a preview and `Send` runs it. `MEMORY` lists the two paths whose bytes are compiled catalogue responses (`GET /` and `GET /assets/bridge.js`); their exact bytes, content types and full hashes come from `native_responses()`. The limits are `const`: `HEAD_MAX = 8 * 1024`, `BODY_MAX = 256 * 1024`, `READ_SECS = 5`, `CONNECTIONS = 4`. The module is declared under `cfg(feature = "bridge")`, so neither the silent build nor the AI build with `net` alone has any of it. `xtask/src/ports_bridge.rs` includes this one file with `#[path = "../../crates/fieldbook/src/io/net/routes.rs"]` and prints the section "Bridge" of `ports.md` from it, because a path dependency on `fieldbook` with the feature `bridge` would be unified into every workspace build and put `ureq` into the silent graph.
3. The server, `io/net/bridge.rs` (the only file with a listener type, so NS-05 holds). `bind(text) -> Result<Listener, BindError>` accepts the literal `127.0.0.1` and nothing else (`0.0.0.0`, `::`, `localhost` and any other text are FB0952 before any socket call), binds `127.0.0.1:0` and requires `local_addr().ip().is_loopback()`. `chat` has no `--bind` flag, so no command line reaches `bind` with another address; FB0952 is raised in process by the test `bind_0_0_0_0_is_fb0952_and_makes_no_socket` and by the guard in `bind` if code ever passes one. `read_head(r: &mut dyn Read, deadline) -> Result<RequestHead, ReadError>` is pure over `Read`, so the property test of step 15 needs only a byte buffer. It accepts `HTTP/1.1` and the methods `GET`, `POST`, `PUT` and `DELETE`; the target must be ASCII, start with `/` and hold no `%`, backslash, NUL or `..` (else 404); `Host`, `Origin`, `Authorization` and `Content-Length` may appear once (a second is 400); `Transfer-Encoding` is 400; a body needs `Content-Length`. The request line and headers over `HEAD_MAX` are 431 with FB0955; after `admit` succeeds, `read_body` refuses a declared body over `BODY_MAX` with 413 and FB0955 before reading a body byte; a request not complete `READ_SECS` after it began is 408 with FB0955 (a total deadline, not a per-read one, so a slow client cannot hold a slot). Anything else malformed is 400 with an empty body. Every reply is `Connection: close` with `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `X-Frame-Options: DENY`; none has `Server`, `Date`, a cookie or a CORS header [J].
4. The checks, in this order and no other, in `admit(req, port, token)`: `Host` equals `127.0.0.1:<port>`; `Origin` is absent or equals `http://127.0.0.1:<port>` (`null` is refused); for a path under `/api/` the header `Authorization: Bearer <token>` is present and equal by `ct_eq`, a fold over all bytes with no early exit. A failure is 403 with `ApiError { FB0951, Policy, retryable: false, fallback: None }`, no body detail, and one line on standard error, `chat: FB0951 refused POST /api/send`, with the method and the path without its query and nothing else. A token in a query string is not read. `SessionToken` is a newtype with no `Display`, no `Clone` and a `Debug` that prints `<redacted>`; `expose()` is called by the start line and `ct_eq` only. It is 16 bytes written as 32 lower-case hex digits. `SessionToken::new(fill)` takes the function that fills the bytes; the verb passes `io::net::os_random` (`net-stack-spike`, step 14), which is the only call in this card that reads the system's random source, and the tests pass a fixed fill. If `os_random` fails, `chat` prints `chat: the system gave no random bytes; nothing was started` on standard error and exits 2 before it takes the lock or binds anything.
5. Threads. The accept loop polls every 250 ms [J] so that it can see `quit`, idle and the lock. A connection beyond `CONNECTIONS` live ones is closed at once. Each live connection has a reader thread that reads the bounded head, runs `admit`, enforces the body limit and reads the body with the same total deadline, then hands the request to one of two workers over a channel: the send worker takes `POST /api/send` and the general worker takes the rest, in arrival order, so `status` and `cancel` answer while a send waits. A second send waits behind the first. No process is started and no thread outlives the session; the listener is dropped before the lock is released.
6. Files. `crates/fieldbook-render/src/chat.rs` is the one native response catalogue producer, exported from the already-scoped render `lib.rs`. `native_responses()` is a data list of exact HTTP path, fixed content type, bytes and full byte hash: the compiled `GET /` shell and `GET /assets/bridge.js`, plus each native JS, CSS, icon and font actually required by that shell. The same native asset source and producer supply the built Site bytes; never parse the Site into an allowlist and never duplicate assets into a second directory. Unauthenticated GET serves only entries of that catalogue; there is no `public-assets.toml` manifest, no manifest beside the Site and no extension allow-list fallback. It contains no HTML content page, CSV, JSON data, assist-data.js, search index or source text. The root shell is the explicit HTML exception: native template code and frozen strings only, carrying no Corpus or company text, no settings, no token and no runtime content. `GET /` must answer `200` with `text/html` without a token (subject only to the existing Host, Origin and request guards); HTTP `/chat.html` and `/assistant.html` are `404`, matching HANDOFF, while the static `assistant.html` still exists and works by Handoff from `file://`. All content arrives through authenticated API routes, from the current filtered view and final reply gate.
7. State, `io/chat_state.rs`. `Lock::acquire(state)` takes `chat.lock` with `File::try_lock`; a lock that is held is FB0954 (exit 2), and the lock is released by the operating system if the process dies. Packs: `list`, `read`, `write` and `delete` of `packs/<name>.json` through the atomic helper, names `[a-z0-9-]{1,32}`, content `{ "pack_version": 1, "name", "ids", "view_fingerprint" }` (a `NamedPack`) and never a character of unit text. `assist::view_fingerprint` (`handoff-context`) gives the fingerprint; it is not the backup fingerprint.
8. The verb, `adapters/chat.rs`, entered from `cli.rs`: `chat [--site DIR]`. The subcommand is declared in every build so that `cli.md` lists it; a build without `bridge` answers FB0912 and exit 2 (`avail.bridge_built` of `model-gate`, read before the settings) and contains nothing else of this card. With `bridge`: read the settings (FB0900, exit 2); ask the policy for the `bridge` destination with `egress::check`: a loaded policy with no `bridge` row, an expired row or a Closed policy means no listener (FB0918 or FB0413, exit 2), and the floor allows `public`; the labels the page may show, `bridge_set`, are the row's allow set narrowed by the owner's list, cut to `public` when `World::interactive_logons()` counts more than one interactive logon or cannot count them, because another logon can reach the loopback port and the token is then the only barrier (this card adds the method to the `World` trait in `lib.rs`, returning `Option<u32>` with `None` for a count that cannot be read, the `Disk` body in `io/mod.rs`, which is one line that calls `io::win::interactive_logons` of `windows-facts`, the forwarding line of `FaultyWorld` in `crates/fieldbook/tests/support/faulty.rs`, and the field and setter of `TestWorld` in `tests/support/world.rs`); retain the existing site selection and default (default `out/edition` under the root, else exit 2 with `no built site at <path>; run fieldbook build first`), and refuse a site folder that is the state folder or holds it or is held by it (exit 2); before binding, check the required on-disk native assets against the one catalogue, resolve canonical containment without links or escapes, read and hash them once and retain owned immutable verified bytes; serve only those retained bytes for the session, so a later file replacement cannot alter an unauthenticated response, while the root and `bridge.js` are catalogue-owned compiled responses and need not exist as disk files; unknown, stray, changed or escaped disk files are not admitted and no extension fallback exists; take the lock (FB0954); append `chat.session` with `phase = start` and `calls = 0`, and if that fails exit 3 before anything is bound; make the token; bind; print the URL on standard output as its own line and `chat: listening on 127.0.0.1 only; type q and press Enter to stop` on standard error. The router is built from the settings as `ask` builds it; the Bridge sets no limit of its own. A send can take about four minutes (three tries of 60 s and the pauses); Stop answers at once and the next send waits behind the current one. A session ends in three clean ways: the page's "End session" button (`POST /api/quit`), `q` and Enter at the terminal (read only when standard input is a terminal), or `idle_minutes` with no request while no send is running (any route, and the end of a send, restarts the clock). Each appends `chat.session` with `phase = stop` (the button and `q`) or `idle` and `calls = N`, closes the listener, releases the lock and exits 0; a stop prints `chat: stopped after N calls` on standard error and an idle end prints `warning[FB0953] chat: ended after N minutes with no request`. A stop event that cannot be appended exits 3. Ctrl-C also ends the process at once but is not a clean stop: the program installs no signal handler, so no stop event is written, the lock goes with the process, and the journal shows a start with no stop [J]. `audit verify` does not flag that.
9. Status and context, `chat_api.rs` and `chat_context.rs`. `GET /api/status` returns the `ChatStatus` document (its shape is in the "JSON reports" section of `cli.md`): `report_version`, `"transport": "bridge"`, `calls_left`, `session` (`calls`, `calls_left`, `idle_minutes`), `caps`, `stream`, `adapters` (the `AdapterStatus` list from the builder that `ai status --json` uses) and `messages` (the catalogue lines of the codes the page can show). `caps` is a `ChatCaps` for the route in use: `{ answer: true when the route is a model route and false for Handoff, stream: the adapter's Caps.streaming, keep_threads: false, save_notes: true, request_items: false }`. `stream` is `Idle`, or `Waiting { since_ms }` while a send runs; `Busy` is the state of the route in use while a send runs. `POST /api/context { question, scope, edits }` takes `scope` as `all`, `area:<code>` or `page:<id>` and `edits` as `{ pinned, removed, added, suggested }`: four lists of ids, sent in full on every call (the server keeps no edit state), each empty or omitted. It loads the Corpus (on every call, so an edit shows [J]), plans the route (`ModelPort::plan(None, &base)` for `/api/context`, and the `via` of the request for `/api/preview`), takes two destination-only tokens with `egress::check(&eff, &planned_dest, None, None, now, shipped)` and `egress::check(&eff, &Dest::Bridge, None, None, now, shipped)` from the same fresh policy snapshot. Build the planned-destination view and call `view.restrict(&bridge_set)`, where `bridge_set` is the current narrowed Bridge `LabelAllow`. Never convert either permission list into data labels; an empty intersection selects no units. After rendering, check the exact response labels and Delivery for `Dest::Bridge` before the response sink. It builds the pack with `assist::context_pack(&view, question, scope, budget, &Include::default())` and then `assist::apply_edits(&view, &pack, &edits, budget)` (`handoff-context`). Those two own the origins, the reasons, the order, the stale rule and the budget; this route adds no rule of its own and returns `{ "report_version": 1, "pack": ContextPack }` as they give it. `ContextPack` is `{ question, scope, items, chars, budget, view_fingerprint }`; an item is `{ unit, origin, why, via?, included, stale }`, where `origin` is `auto`, `suggested`, `pinned` or `added`, and `why` is `hit`, `closure` (with `via`, the id of the item that brought it), `scope` or `named` (the owner added it, the model suggested it, or the question names its id). The labels of a chat request are those of its parts: `public` for the Rules, `owner-supplied` for the Question, and for the Context the union of the labels of the units in the pack, and for History the current effective labels of its retained turns; the pack's `Labels:` line is the one `assist::context_pack` writes for the destination, and the items and the displayed context that the page receives (the Context part of a preview too) end with `view.left_out_line(&Dest::Bridge)`, the fixed line `Some records were omitted.` with no number, so the page never shows a count, on a Handoff route too; only `handoff/H-nnnn.txt` and a Handoff reply's `pack_text` keep the Handoff line with its count. A unit that the route's allow set does not hold is not in the view, so no id can bring one in. A pack on screen that was built for another route has another `view_fingerprint`, so its items are `stale` until the page asks again. Offline: the double of the test panics on a model call.

Preview and send. `POST /api/preview { thread_id, question, scope, edits, via? }` builds the `ask@1` request exactly as `ask` does (parts Rules, bounded History, Context, Question), asks `ModelPort::preview`, keeps the request under a `preview_id` (an integer from 1; the newest 32 are kept [J]) and returns `PreviewReply { preview_id: u64, preview: SendPreview }`. `POST /api/suggest { question, scope }` does the same for the template `suggest@1` (purpose `Suggest`; parts Rules, Context holding one `id TAB title` line for each of the 60 best hits within the scope, Question; labels `public` for the Rules, `owner-supplied` for the Question and, for the Context, the union of the labels of the listed hits; reply schema `{ ids: array of at most 12 strings of at most 64 characters }`). Neither calls a model and neither appends an event. `POST /api/send { preview_id }` runs that request through `ModelPort::run(&req, via, stop)`, where `stop` reads the cancel flag of step 11. An `Answer` for `ask@1` becomes an `AnswerCard`: `assist::cite_check` is given `Some(&ids)` with `req.context_ids()`, so a reference that exists but is not among them is `outside_context`, one that does not exist is `broken` even when it is also outside the context, and the other statuses are those of `cite-check`; the references to questions and conflicts go to `neutral`; `prov` is the answer's `ProvenanceRef`, and `unchecked` is true only when the cite check could not run (see step 1). An `Answer` for `suggest@1` becomes `suggestion`: ids not in the view and repeats are dropped and counted, and the page adds the kept ids to `edits.suggested`. A `Deferred(ticket)` becomes `handoff`. The reply of `POST /api/send` is one of `{ "kind": "answer", "card": AnswerCard }`, `{ "kind": "suggestion", "ids": [id], "dropped": N }`, `{ "kind": "handoff", "ticket", "pack_path", "pack_text" }`, `{ "kind": "cancelled" }` or `{ "kind": "error", "error": ApiError, "handoff"? }`; `pack_text` is the whole Handoff pack as text for the clipboard and `pack_path` is `handoff/H-nnnn.txt` in the state folder (a `file:` page builds `pack_text` itself and has no `pack_path`). `POST /api/send { resume, pasted }` reads the ticket `H-nnnn`, calls `ModelPort::resume` and treats the result as above, by the template stored in the ticket. A `ModelError` becomes `error`: the kind and code of the error, `retryable` true for FB0908 only, `fallback` `Handoff` and the pack when the router offered one; the HTTP status is 409 for a policy kind (FB0413, FB0901, FB0902, FB0903, FB0904, FB0907, FB0915, FB0918), 502 for availability and 422 for invalid. A body that is not JSON, holds an unknown key or names an unknown `preview_id` is 400 with an empty body. `asked::log_question(.., policy, Via::Chat, labels, inputs, ..)` (`ask-log`), with the labels and input_refs of the trusted prepared request, runs once per `ask@1` send, before the call.
10a. Save as note. `POST /api/note { text, area, ask_seq, question, title? }` files an answer as a `note` proposal. The server reads the journal event with sequence `ask_seq` (the `ai.call` of a send, or the `ai.paste` of a resumed Handoff round trip) and requires the SHA-256 of `text` to equal its `output_sha256`, so the page can file only text that a recorded call produced. The page sends `text` from the `AnswerCard` it holds and `ask_seq` from its `prov.call_seq`; an answer with no `prov` cannot be filed. A body that is not JSON, an unknown key, a missing or empty `question`, an `area` that is not an area code, or a missing event is 400 with an empty body. `assist::cite_check` runs over `text` with no context, and a broken citation is 422 with `{ "kind": "error", "error": { "code": "FB0701", "kind": "invalid", "retryable": false } }`, as `ask --note` refuses it. Then the writer of `ask_note.rs` (`model-handoff-ask`) runs: `queue.propose` is appended first, and then `queue/P-nnnn.toml` is written with `kind = "note"`, a `[note]` table (area, title, question, context, body, origin, request_labels and provenance, as `ask --note` writes it) and the `[ai]` call that `ask_seq` names; `title` is the given one, else the question cut at 80 characters, and `context` is the context ids that the journal holds for that call. Read request_labels and provenance from trusted server session answer metadata keyed by ask_seq, copied from ModelAnswer when the successful answer is recorded, including retained History inputs. Verify the text against the journal hash as above; never accept provenance from the browser. This works with keep_calls=false or refused call-record storage and does not persist a thread. An ask_seq absent from this session is 400; a missing journal event still refuses. Test `note_keeps_session_provenance_without_call_records` for both retention cases. A journal that cannot append writes nothing and returns FB0903. The reply is `{ "kind": "note", "proposal": "P-nnnn" }`. The route never calls the gate and writes no page; the note becomes a page only when the owner runs `queue accept`.
11. Cancel. `POST /api/cancel` sets a flag and returns `{ "state": "Cancelled" }` at once. The gate's retry loop takes a stop check that reads this flag, so the worker stops before the next retry and otherwise finishes the attempt it is in (it cannot abort a blocking call); `adapters/chat.rs` wraps the `AiJournal` of the session in `CancelJournal`, whose `finish` writes `outcome = cancelled` in place of `ok` when the flag is set, and the worker answers `cancelled` and drops the reply. The flag is cleared when the next send begins, and `status` shows `Waiting` or `Cancelled` meanwhile. A cancel with no send running does nothing.
