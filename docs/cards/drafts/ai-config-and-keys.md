# ai-config-and-keys

- **Runs where:** home, CI Linux
- **Schema impact:** none
- **Review:** auto

## Outcome

The AI part of `settings.toml` is read by one parser that fails closed, and `fieldbook ai status [--json]` shows what the program would do without doing it. The tables `[model]`, `[model.handoff]`, `[model.endpoint.<name>]`, `[search]`, `[mcp]` and `[chat]` load into typed values; an unknown key, an adapter that is not built, a secret-looking key name, an `order` entry that names no endpoint or an `allow` entry that is not a label id is FB0900 and exit 2. The owner's `allow` lists only narrow what the company's policy permits; the approval of an endpoint is a row of the policy and never a setting. A key is read only from the environment variable named by `key_env`, held in a `Key` that cannot be printed, and shown only as `set (N characters)` or `missing`. Nothing is sent anywhere.

## Why

- Every later AI card reads its limits from this file, so the parser comes before the gate. The rules (an endpoint with no `allow` accepts nothing, `allow` can only narrow the policy's row, a key is never in the file) are the label and key rules behind the Ports paragraph of [The architecture in one page](../../decisions/0001-foundation.md#the-architecture-in-one-page); the gate that applies them to a request is `model-gate`. The file holds names and URLs and is backed up, so a key in it would be copied to every snapshot: that is why a key-like name is refused and not ignored ([AD-18](../../decisions/0001-foundation.md#ad-18-security-and-confidentiality-guardrails), control NS-07 in [controls.md](../../controls.md)).
- The owner cannot approve an endpoint here. Approval is a row of the company's policy ([ADR 0004, section 7](../../decisions/0004-company-boundary.md#7-model-endpoints-and-the-ai-before-any-approval)), and `allow` in `settings.toml` is the owner's own narrowing of it, so there is no `company_approved` flag in the file. The failure this prevents: an owner, or a stray copy of a settings file, raising a list and so sending company records to an endpoint nobody approved. The merge is `core-policy`'s; this card reads the file and hands over the lists.
- Nothing here sends anything. `ai status` shows the state of each port from the file, the registry and the journal, and opens no connection. The owner can therefore check a setting, and IT can see the output, before any endpoint exists. FB0900 is in [09: model, decide, index, output, MCP and chat](../../reference/corpus-format.md#09-model-decide-index-output-mcp-and-chat).
- The key rule is the one the audit rests on: the value is read by one function, held by one type with no `Display` and a redacting `Debug`, and handed to one consumer (the header builder of the network adapter). The test NS-07 plants a synthetic key and looks for it everywhere the program writes.
- No page, template or string shown in a browser is built here, so there is no Design bullet. The chat header chip reads the `AdapterStatus` shape that this card defines; the page that shows it is `assistant-page` and `chat-bridge`.

## Out of scope

- The gate that asks `egress::check` about a request's labels, the router that picks a route, and every call record (`model-gate`). The `KeySource` trait is declared here beside `Key`; `model-gate` uses it and adds no second one.
- The network adapter's keys (`chat_path`, `query`, `auth` values beyond the two words, `max_tokens_field`, `response_format`, `send_temperature`) and FB0905 to FB0914 (`model-adapter-openai`). The parser accepts `adapter`, `base_url`, `model`, `allow`, `timeout_s`, `key_env` and `auth` now; the card that adds a key adds it to the table and to its registry row.
- Reading `[asked]`, `[backup]` and `role`. Their cards own those readers; this parser lists them as owned by another reader so that they are not unknown keys.
- An operating-system key store (`later-os-key-store`). A key still comes only from the environment.

## Steps

1. Core, `ports/chat.rs`: the status subset of the chat shapes, with `serde` derives and no I/O. `ConnState { Off, Handoff, Ready, Busy, Unavailable { code }, Blocked { code } }` (Unavailable is an availability failure, Blocked is a policy one), `KeyState { Set, Missing, NotNeeded }`, `LastCall { outcome, at, attempts }` and `AdapterStatus { port, adapter, endpoint, state, allow, key, caps, last }`, where `endpoint` is the endpoint name (or `handoff`) and `allow` is the effective allow set as label ids, empty when the policy allows the endpoint nothing. `model-gate` adds `SendPreview` and `Scan` to the file, because `ModelPort::preview` returns them; `assistant-page` adds `Transport` and `ChatCaps`; `chat-bridge` adds `StreamState`, `ErrKind`, `ApiError`, `AnswerCard`, `SendReply`, `NoteReply` and a re-export of `ContextEdits`; `handoff-context` and `handoff-cite-check` define the context and cite types in `assist`. Test `chat_shapes.rs`: `adapter_status_round_trips`, `connstate_names_are_stable` (the JSON names are part of the UI lane's contract and a golden holds them). `AdapterStatus.caps` carries `streaming`; the golden of `connstate_names_are_stable` and `ai status --json` show it as `"streaming": false`.
2. `io/keys.rs`: `Key`, a newtype over a `String` with no `Display`, no `Clone` and no `Serialize`; its `Debug` is written by hand and prints `Key(<redacted>)`, so a struct that holds one can still derive `Debug`. `Key::len()` is the accessor everyone may call; the text is read by `fn reveal(&self) -> &str`, which only the header builder of the network adapter may call (the scan in step 7 holds that, because `io/net*` does not exist yet). The trait `KeySource { fn key(&self, name: &str) -> Result<Key, KeyError> }` with `KeyError { Unset, Empty }` is declared here; `EnvKeys` implements it and is the one place the program calls `std::env::var` (`#[expect(clippy::disallowed_methods)]` with the reason "the one reader of the environment"). A `ScriptedKeys` double for tests lives beside it. A variable name must match `[A-Z][A-Z0-9_]{2,63}`; any other is FB0900.
3. `settings.rs`, `Settings::parse(text, rows) -> Result<Settings, Vec<SettingsError>>`, pure, taking the registry rows as an argument so that tests can pass rows that are not built yet. The key table lists every allowed key with its type and default: `[model]` `order` (a list of endpoint names and `handoff`; `["handoff"]`), `retries` (2), `max_calls_per_run` (100), `max_out_tokens` (1500), `keep_calls` (true), `keep_days` (30), `proxy` (`env` or `none`); `[model.handoff]` `allow` (optional), `assistant_label`; `[model.endpoint.<name>]` `adapter`, `base_url`, `model`, `allow`, `timeout_s` (60), `key_env`, `auth` (`bearer` or `api-key`); `[search]` `semantic` (false); `[mcp]` `allow` (optional); `[chat]` `idle_minutes` (30). There is no `[decide]` table. An endpoint name is `[a-z][a-z0-9-]{0,31}` (an `EndpointName`, a type that never mixes with a data `LabelId`), and `handoff` is reserved. An `allow` entry is a `LabelId` of `core-labels`. A missing file or a missing `[model]` table means `order = ["handoff"]`. `Settings::owner()` gives `core-policy` its `OwnerSettings`: for each endpoint its `allow` (no `allow`, no entry), for `handoff` and `mcp` the optional list (`None` is no narrowing), and `keep_calls` and `keep_days`.
4. The load rules, each a `SettingsError` with a line number, the key and a help line, all FB0900: an unknown table or key; an `adapter` that is not a `Built` row of the Model port (with or without `@n`; without it, the highest built version); `[search] semantic = true` while no Index row for `semantic@1` is built; a key under `[model]` or an endpoint named `key`, `api_key`, `token`, `secret` or `password` (case-insensitive), with the help "put the key in an environment variable and name it with `key_env`"; a `base_url` with user information; an `allow` entry that is not a label id by shape, or that is `unlabelled` or `marked` (nothing can allow those two); an `order` entry that is neither `handoff` nor a configured endpoint, or that repeats; the keys the policy replaced, `approved_for`, `default`, `fallback` and a `[model.route]` table, each refused with the help "the company's policy approves endpoints; narrow with allow and list routes in order"; a `retries`, `timeout_s` or `idle_minutes` of zero or above its ceiling (10, 600 and 1440 [J]). An endpoint with no `allow` is valid and accepts nothing. An `allow` can only narrow: the effective set is the policy row's set intersected with it, so listing a label the row lacks changes nothing. A well-formed id that the policy's table does not define is not an error here; `ai status` reports it (FB0411). A `base_url` that is not `https` or loopback is FB0913 and belongs to `model-adapter-openai`, so the parser here only requires the text to be a URL with a host.
5. `io/ai_settings.rs` reads `settings.toml` of the state folder (`--state` or `FIELDBOOK_STATE`, as `audit` does) and returns its text, or `None` for a missing file; the folder is not created. `settings.rs` keeps the keys that other cards read (`role`, `[asked]`, `[backup]`, `[[backup.target]]`) in an `Owned` list, so they are neither parsed nor reported. The table is the const `KEY_TABLE`, and `xtask/src/ports_doc.rs` prints it into `ports.md` as a "Settings keys" section (table, key, type, default, the adapter row that reads it), so the keys have one documented list. A key that meets the policy (`order`, the three `allow` keys, `keep_calls` and `keep_days`) also has a row in the merge table of `core-policy` (`policy::merge::KEY_TABLE`); the test `settings_keys_have_merge_rules` fails when either table lacks the other's row. The test `settings_keys_match_docs` in `tests/settings.rs` fails when a settings key named by a registry row is missing from `KEY_TABLE`, when `ports.md` is stale against `KEY_TABLE`, or when `KEY_TABLE` and the example `settings.toml` of `state-ai` disagree. `KEY_TABLE` is also the `known_keys` argument that `adapters_match_registry_docs_and_fixtures` of `ai-kernel` takes.
6. `ai_status.rs` and `cli.rs`: `ai status [--json]`. There is no date flag (PL-03): the expiry date of a policy row is `World::now()`, and a test that needs a fixed day uses `TestWorld` with `set_now(Now)`. It parses the settings, loads the policy as `policy-load` does (the floor when no policy is configured, a Closed state when the file fails), builds the `EffectivePolicy`, reads each endpoint's key state through `EnvKeys` (the name and `set (N characters)` or `missing`, never a character of the value), reads the newest completed `ai.call` for each endpoint, joined by `tx` to its `ai.begin` from the journal (the journal is read as `audit show` reads it, failing open), and prints one line for the settings, one for the policy (`policy: none (floor)`, `policy: revision N` or `policy: closed (absent, invalid or lower revision)`), one for the `order`, one `Limits:` line (`Limits: retries 2, max_calls_per_run 100, max_out_tokens 1500`, then `, timeout_s <name> <N>` for each configured endpoint; these are the values in force after the defaults of `settings.rs`, so a changed default shows with no edit to a document), and one for each adapter of the Model port, each followed by one line for every label that was cut, which names the side that cut it (`EffectivePolicy::explain`: the policy row or the owner's list), and a warning line (FB0411) for each `allow` id that the policy's table does not define, then one for each other port with its default adapter. A port line is `<port> <adapter> <state> <allow> <key> <last>`. Settings that fail print each FB0900 with its line and exit 2; a missing key variable, an unreachable endpoint and an empty journal are not failures, and neither is a Closed policy, which shows as `Blocked` on every line. `--json` prints one document, `report_version` first:

   ```json
   {
     "report_version": 1,
     "policy": "loaded",
     "adapters": [
       {
         "port": "model",
         "adapter": "openai-compatible@1",
         "endpoint": "work",
         "state": { "kind": "Ready" },
         "allow": ["public"],
         "key": "Set",
         "caps": { "network": true, "structured": true, "embeddings": false, "streaming": false, "max_prompt_chars": 200000 },
         "last": { "outcome": "ok", "at": "2026-01-01T09:00:00Z", "attempts": 1 }
       }
     ],
     "exit": 0
   }
   ```

   `ai status --json` has `report_version`, `policy` (`floor`, `loaded` or `closed`), `adapters` and `exit` only. `state` is an object: its `kind` is `Off`, `Handoff`, `Ready`, `Busy`, `Unavailable` or `Blocked`, and the last two carry `code`: for `Blocked`, FB0413 (the policy is Closed), FB0918 (no row, an expired row or another URL) or FB0901 (the effective allow set is empty). `key` is `Set`, `Missing` or `NotNeeded`, never a value. `last` is the newest `ai.call` of that label (`outcome` is `ok`, `failed`, `invalid`, `truncated` or `cancelled`), omitted when none is recorded. `ConnState::Handoff` is shown for `handoff@1`, `Off` for an adapter whose row is `Later`, and `Unavailable { FB0912 }` for a network adapter in a build without the `net` feature (none exists yet). The verb opens no file for writing and no connection: `ai_status.rs` and `settings.rs` are inside the NS-05 and DT-05 scans of `ai-kernel`. Remove `ai status` from `PENDING` in `crates/fieldbook/tests/chips.rs` (`build-about`) and from `NOT_BUILT` in `crates/fieldbook/tests/cli.rs`; the chip is already in the Verb map. Register its case in `tests/support/chip_cases.rs` (a fresh Home copy with default settings, exit 0).

## Rollback

Revert the merge commit. `ai status` goes, and so do the parser and `Key`; no later AI card can then build, so revert them first if any has merged. An existing `settings.toml` is untouched: it is the owner's file and was never rewritten.

## BLOCKED

The settings file of a real state folder holds a table that the key table does not list and that no other card reads, so the owner's own file would fail with FB0900. Set the item to Blocked with `BLOCKED: <table> in settings.toml has no reader`, and stop. Do not make unknown keys a warning to get past it.
`OwnerSettings` of `core-policy` has no field for a settings key that this card must read. Set the item to Blocked with `BLOCKED: OwnerSettings has no field for <key>`, write the field you need, and stop. Do not read a settings key around `EffectivePolicy`, because the merge rule would then be missing.
