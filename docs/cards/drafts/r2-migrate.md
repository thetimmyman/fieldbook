# r2-migrate

- **Runs where:** home, CI Linux
- **Schema impact:** none
- **Review:** owner

## Outcome

`fieldbook migrate [--dry-run] [--json] [--today YYYY-MM-DD] [--backup-from DIR]` brings a Corpus, or the company store on the laptop, up to the schema this program reads. It reads a table of steps, one for each bump, plans every file a step produces, checks the planned tree with `check --strict` before it writes anything, refuses to write unless a backup newer than the last write exists, writes the data files and then the `schema_version` stamp last inside one journaled pair, and does nothing when it is run again. It is the only command that changes the stamp of an existing tree. `cargo xtask rehearse-migrate` runs release checklist item 6 with two executables and prints the report that item names as its evidence.

## Why

- The verb is the R2 row of [AD-17](../../decisions/0001-foundation.md#ad-17-authoring-experience); the rule that bumps ship as `migrate` from R2, rewrite in place, are idempotent and that `migrate` alone changes `schema_version` is in [Scope and versioning](../../reference/corpus-format.md#scope-and-versioning); item 6 is in [release.md](../../runbooks/release.md). Before R2 a bump ships a one-off `cargo xtask migrate-<from>-to-<to>`; this card is the later card that replaces it with the table.
- A migration rewrites a store in place, and on the laptop that store is company data kept on one device. So it plans first, checks the planned tree with the real `check --strict`, needs a backup made after the last write (a snapshot of the store as it is now, made by this program, is the way back; the gate compares fingerprints, so a snapshot that left the store out, or an edit made by hand since, does not count, and the company's own backup of the device is a second copy that the gate cannot see and does not rely on), takes the journal lock for the whole run, refuses a step that lowers or drops a label, and records the planned files in a `write.begin` before the first byte moves. The vocabulary has no `migrate` kind, so the record is a `write.begin` and `write.end` pair whose `verb` is `migrate`.
- Originals and extracted page text are bound by hashes and are never rewritten; the planner refuses a step that tries. The stamp is written last because it is the record that the migration is finished: while it is old, a rerun knows the work continues. A run stopped in the middle leaves a tree between the two shapes, and the two ways out are to run `migrate` again or to restore the snapshot.
- The planned set lists every file the steps produce, including one an interrupted run already wrote. A rerun therefore has the same planned set as the first run, and finishes it and closes its unfinished `write.begin` the way a rerun of `add` does.
- The program that wrote a snapshot cannot read the tree after a bump (FB0100), so item 6 asks three things in order: the previous version drills its own snapshot, the new version byte-verifies and restores it without a pre-migration strict check, and `migrate` runs on the restored copy, and the old version still runs on the copy that was not migrated. `xtask` is the only code that starts a process, so the rehearsal lives there.
- The check of the planned tree is a strict `check`; review dates can add warnings on a later day, but those warnings never refuse a valid migration. `migrate` takes `--today` as `check` does. The rehearsal requires it and passes it to every check and every `migrate`, so that two runs of the rehearsal on two days give the same report. `xtask` is a binary crate, so the tests of the rehearsal are in `rehearse.rs`: a file in `xtask/tests/` can run the binary and cannot reach `Runner`.
- No page, template or string shown in a browser is built here, so there is no Design bullet.
- Review is `owner` because the card builds the rehearsal that release checklist item 6 asks the owner to read, and because the command rewrites the company store in place on the laptop.

## Out of scope

- A bump itself. When a card raises the schema it adds one row to the table and its fixture; here the engine is built, and any existing `xtask` migration moves into a row.
- Going back. `migrate` only moves forward; the way back is the snapshot, restored by the version that wrote it or a later one.
- Migrating an edition or a snapshot: an edition with the same stamp never needs a new executable, and `restore` reads a snapshot as it was written.
- Starting `migrate` by itself when `check` or `build` meets an older tree. They only report; the owner runs the verb.
- Running the rehearsal on the laptop. The rehearsal runs at home; the laptop runs the same `migrate` on its company store, and the owner's first run there is after the release it ships in.

## Steps

1. Core, `migrate/mod.rs`, pure (no disk, no clock, no environment). `TreeRead` (`list(prefix)`, `read(path)`), `Change { path, bytes }`, `StepKind { Additive, Breaking }` and `Step { from, to, kind, apply }`, where `to` is `from + 1` and `apply` is `fn(&dyn TreeRead) -> Result<Vec<Change>, MigrateError>`. `MIGRATIONS: &[Step]` has one row for each bump from schema 1 to `version::SCHEMA_VERSION_MAX`. List `xtask/src` for a `migrate-<from>-to-<to>` command first: the code of each becomes the `apply` of its row, and the command, its test and its expected tree are deleted, the test now running the row on the same input against the same committed tree. An additive bump returns no changes only when every old file still parses unchanged. Adding an optional field to an exact-header file needs a preserving migration; it cannot be stamp-only. Company record revisions use new definitions/files and never rewrite historical record bytes. `read_stamp(corpus_toml) -> Result<u32, StampError>` reads the `schema_version` line and `set_stamp(corpus_toml, n)` replaces that integer and nothing else. `plan(tree, table, max) -> Result<Plan, MigrateError>` reads the stamp and returns `Newer { found, max }` above `max` and `Current` at `max`; otherwise it applies the rows from the stamp to `max` in order, each step reading the tree as the earlier steps left it, and a later change to a path replaces an earlier one. Define `enum Plan { Current, Newer { found: u32, max: u32 }, Planned(PlannedMigration) }`. `PlannedMigration { from, to, steps, changes }` lists every output in byte order of path with `corpus.toml` and its new stamp last. `MigrateError` is `Stamp(StampError)`, `NoStep(from)`, `Forbidden(path)`, `Labels(id)` or `Step(from, why)`.
2. Core, `migrate/guard.rs`. `forbidden(path)` is true below `sources/public/` and `sources/org/`, and for a `p` and four digits `.txt` file below `sources/text/`; `plan` returns `Forbidden` for a change to one. `labels_kept(before: &dyn TreeRead, after: &dyn TreeRead) -> Result<(), LabelLowered>` takes the effective labels of every item (a page, a source version or a record version) in the tree as a step found it and as the step left it, with `labels::effective_item` over each complete before/after provenance graph (handling, ledger and persisted input references), whichever file the step changed; an item missing after the step, or whose after-set omits any non-public label in its effective before-set, is `LabelLowered(id)`. Normalization may remove `public` when another label appears; public-to-company is an allowed increase. Outbound permission subset checks are unchanged, and `plan` calls it after each step and returns `MigrateError::Labels(id)`. A record version is a row of any declared immutable revision file, `records/<type>.csv` or `records/<type>@<revision>.csv`; its id is `record_id` and `version` joined with `-v` (for example `CM-000012-v2`) and its own label is the row's `handling` cell, read by header name. `labels_kept` reads its effective label through `labels::effective_item`, as for pages, including evidence, run and observation inputs. A missing input, cycle or unreadable provenance cannot become public; it refuses migration through the typed label error. A step may add a label and may never lower or drop one, so a rewrite that loses the `handling` cell of a company record, resets it to `public` or drops an add line from `labels.csv` cannot reach the disk; a step that adds a column to `labels.csv` and keeps every effective label passes, so `labels.csv` is not in `forbidden`. `backup_covers(events, selected_manifest: Sha256, now: Fingerprint) -> Result<(), BackupGap>` takes the journal's events as `audit show` reads them across all segments, finds the successful `backup.end` bound to that selected verified manifest hash, and returns `Missing` when there is none, `StaleAfter(seq)` when a `write.end` with outcome ok or a `restore.end` follows it, and `NotThisStore` when its `fingerprint` is not `now`, the fingerprint of the content store as `backup` computes it (`manifest::fingerprint` over the files below `content_root()`). The last case catches a snapshot whose target `include` left the store out, and a file changed by hand after the backup; the journal cannot see either. Other kinds do not matter.
3. Binary, `migrate.rs`. The verb acts on `layout.content_root()` (the Corpus at home, the company store `overlay` on the laptop), as `check` takes its root. In this order. (a) Under one coherent read, inspect MigrationIntent, shared PendingWrite and the stamp together, including the no-state retry protocol. Another verb's pending write refuses; matching migration recovery proceeds only after an exclusive lease and recheck. Check for a pending MigrationIntent before the stamp fast path. If one exists, use the matching recovery reader under the existing exclusive lease; --dry-run only inspects and describes it, while an applying run resumes its exact verified plan and original backup, even if the stamp is already current. Otherwise read the stamp from `corpus.toml` at the content root: missing or unparsable is FB0100, printed as `check` prints it; above `SCHEMA_VERSION_MAX` is FB0100 with the help `this tool reads schema N`, exit 1; equal prints `schema N is current; nothing to do`, exit 0, and no journal is opened, so nothing is created or appended. (b) Branch --dry-run before any Journal::open or append-producing initialization. A committed tree uses the coherent read/no-state retry path; a pending tree is inspected only by the matching recovery reader under the already-existing exclusive lease, without repair, resume or retirement. Plan and validate that snapshot. An applying run takes world.write_lease(), rechecks generation, intent and stamp, then opens the journal and reloads through read_tree_under; only matching recovery may inspect a pending tree. (c) `plan`, which also applies `labels_kept`; a lowered label is printed as `error: a migration step would lower the labels of <id>` and exits 1 with nothing written. (d) Lay the plan's changes over the base tree as a host and run `check::run` with `strict` and the date of `--today` (the clock when it is not given) on it; any error is printed with the help `migrate moves a tree that check --strict passes; fix these with the previous version first`, exit 1, nothing written. (e) `--dry-run` prints the plan and exits 0; it needs no backup and appends nothing. (f) For a new migration only, compute the fingerprint of the content store and call `backup_covers`; `Missing` and `StaleAfter` are exit 2 with `migrate needs a backup made after the last change; run: fieldbook backup` (no code), `NotThisStore` is exit 2 with `the selected backup does not hold the store as it is now; run: fieldbook backup, and check that the target's include names <store>`, and nothing is appended. (g) Persist the verified MigrationIntent through the journaled state writer before content writes, then `Journal::begin(&lease, &operation_intent, &set)` with the planned files, write each change through `io/atomic.rs` in the plan's order and skip a file whose bytes already equal the output, the stamp last. Check the final live tree strictly using the same date; only errors prevent closure. Then `Journal::end` commits the generation. While still holding the lease, remove the completed intent through `World::retire_migration_intent(&self, audited: &Audited) -> Result<(), Error>` using `Journal::state_scope(&lease)?`; cleanup failure exits 3. If the intent remains, the next run retries retirement after verification; if removal completed before a sync failure, the current-schema run is a no-op. A journal that cannot be appended makes no write and exits 3. The lines are `step 1 -> 2  additive  0 files` for each step and then `migrated: schema 2, 0 files rewritten, stamp written` with `the previous version cannot read this tree; keep the snapshot until the next backup verifies`; `--dry-run` starts each line with `dry run:` and says `would`. `--json` prints `report_version = 1` with `from`, `to`, `steps`, `files` and `applied` (the struct `MigrateReport` of step 4a). Exit 0 migrated or nothing to do, 1 FB0100 or findings, 2 refusal or usage, 3 I/O. `--today` is parsed as `check` parses it, and a bad date is a usage error. It is used for the planned and final strict checks and for nothing else: `migrate` writes no date.

5. `xtask/src/rehearse.rs`: `cargo xtask rehearse-migrate --previous EXE --current EXE --corpus DIR --today YYYY-MM-DD [--work DIR]`. `--today` is required and is passed to every `check --strict` and every `migrate` below, so that a review date that passes between two runs cannot turn step 2 or 9 from `ok` to `FAILED`; a missing or bad date is a usage error (exit 2) before anything is written, and the report names the date it was given. A `Runner` trait (`run(exe, args, cwd) -> Outcome`) has the real implementation that starts a process and a scripted one for tests. A new work folder, or an empty one given; a non-empty `--work` is refused. Without `--work` a new folder under the system temporary folder is used and kept, and the last line printed is `work folder: <path>`. Copy `--corpus` to `<work>/live/corpus`. Steps 1 to 5 and 11 run with `<work>/live` as the working folder, and its state folder is the default `.fieldbook`. Steps 6 to 10 and 12 run with `<work>/restored` as the working folder; because `restore --to` puts the roots of the snapshot at `restored/corpus` and `restored/state`, the `migrate` and `backup` calls there are `fieldbook --state state <verb> ...`. The folders `target`, `target2` and `restored` are `<work>/target`, `<work>/target2` and `<work>/restored`, given as absolute paths, so that no snapshot target lies inside a folder it holds (FB0812). The restore to `restored` is the export of the repository's public Corpus, which the floor allows; a Corpus that holds a company label fails step 5 with FB0901 or FB0918, which is the right refusal. A hash is `hash::Sha256Stream`, and a tree hash is `manifest::fingerprint` of the files below a folder, each hashed that way. Steps, each recorded as `ok` or `FAILED` with what was seen: (1) `--version` and the SHA-256 of each exe; (2) previous `check --strict --today D` exits 0; (3) previous `backup --to <work>/target` exits 0; (4) previous `restore --snapshot 1 --from <work>/target --drill` exits 0 and its last line begins `drill passed`; (5) current `restore --snapshot 1 --from <work>/target --to <work>/restored` exits 0; (6) in `restored`, current `--state state migrate --dry-run --json --today D` exits 0 and gives `from` and `to`; (7) in `restored`, previous `--state state backup --to <work>/target2` exits 0; (8) current `--state state migrate --backup-from <work>/target2 --today D` exits 0; (9) current `check --strict --today D` exits 0; (10) current `--state state migrate --backup-from <work>/target2 --today D` again prints `nothing to do` and the tree hash of `restored/corpus` is unchanged; (11) previous `check --strict --today D` in `live`, the copy that was not migrated, exits 0, so the previous version still runs; (12) previous `check --strict --today D` in `restored`: when `to` differs from `from` it must exit 1 with FB0100, and otherwise exit 0. When both exes have the same hash, step 12 is skipped and the report says `previous and current are the same build; the refusal step is skipped`. The report is a Markdown table (`#`, step, result, detail) with the hashes and the tree hashes, and no date but the one given; the exit code is 1 if any step failed. Only the work folder is written.
