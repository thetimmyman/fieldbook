# review-queue

- **Runs where:** home, CI Linux
- **Schema impact:** none
- **Review:** auto

## Outcome

`fieldbook add <folder> --propose` runs each file of the inbox through extract, classify and correlate and writes one proposal file for it (`queue/P-nnnn.toml`) with a per-file report. `fieldbook queue list`, `show`, `review`, `accept` and `reject` let a person decide. `accept` writes the original, its extraction and the register row in one ordered write set, and nothing is written without a terminal, a role of owner or lead, an `Authz` that allows the act, and a file that still has the recorded hash. A refusal is FB0822, or FB0807 when the `Authz` port denies. Proposals are state: `add --propose` writes no Corpus file, and `status` prints how many are waiting.

## Why

- Only a person's acceptance admits content. Anyone or anything may propose, including a scheduled sweep, because a proposal is state and not evidence; a source, a version or a case enters the Corpus only through an interactive accept by the owner or lead, and the journal records the actor: the operating-system principal, the role that was declared and the door it came in by ([AD-17](../../decisions/0001-foundation.md#ad-17-authoring-experience), control AL-03 in [controls.md](../../controls.md)). This is the gate that lets the pipeline be AI-first without loosening anything.
- The queue is a folder of files and not a register. The five registers are the frozen format; a proposal holds extraction text and model output, which must stay out of git, editions and the journal; and one file per proposal gives atomic updates and no merge conflicts. The cost is that the queue is not on the site, and a lost queue is made again by running intake again.
- The terminal check is the real gate and the role is the record. A person at the keyboard can declare any role, so the role stops a mistaken run as the agent and makes the journal line; the terminal check refuses redirected input and output. These are attribution and accidental-use checks; a process using a terminal can satisfy them. Agents remain prohibited from admitting content by the owner's workflow. The `Authz` port is asked after both and only narrows: the shipped adapter allows the owner, and the call is there so that a company can deny an act from its own access list without a new gate. When the app is shared, the principal comes from the company identity and the role from the company's table (`later-accounts`, `later-roles`); the terminal test stays for the personal build and for the laptop, and a hosted listener replaces it with a session (`later-hosted-service`).
- A proposal made by a model must carry its calls, and `accept` looks each one up in the journal (FB0917), so a hand-written "model" label cannot pass. The hash of the file is checked again at accept (FB0820), because the file may have changed since it was proposed. The codes are in [08: audit, backup and pipeline](../../reference/corpus-format.md#08-audit-backup-and-pipeline); FB0824 stays free.
- The order original, extraction, `extraction.toml`, row last is what lets a crash be finished by running `queue accept` again ([Adding a version](../../reference/corpus-format.md#adding-a-version), FB0211). The recipe for a new kind is [Adding a proposal kind](../README.md#adding-a-proposal-kind).
- Design: the [MAP](../../design/MAP.md#routes-and-components) rows `#queue` (RegisterTable, StatusChip, CommandChip → `pages/queue.html`) and `#queue/P-nnnn` (MetaRow, Panel, Fold, CommandChip → `pages/queue/P-nnnn.html`), with [HANDOFF](../../design/HANDOFF.md#queue-review-pages) covering the queue layout, the desk frame, empty/waiting/stale/refused/completed states and browser acceptance checks. Token groups: the existing surface/foreground/muted/border, status, space and type tokens; no new palette or layout family. The pages of step 6a are static and carry command chips; the browser portion still needs the interface lane to complete any specification the two references leave open, before that portion is implemented. The Review queue page (step 6a) reads `queue list --json` and `queue show --json`; their shapes are in the "JSON reports" section of [cli.md](../../reference/cli.md).

The queue route, states and browser checks are in [Queue review pages](../../design/HANDOFF.md#queue-review-pages) and [MAP](../../design/MAP.md#routes-and-components).

## Steps

1. Core, `pipeline/queue.rs`, pure and without a clock. `Header { id, state, kind, labels, file, sha256, pages, thin_pages }` read by `parse_header(id, text)` from the top keys only, so a list never parses a body. `next_id(names)` takes the names found in `queue/` and `queue/done/` and returns the next `P-nnnn`, so an id is never reused. `count_waiting(headers)` counts the state `proposed`. `RejectReason` has the five words `duplicate`, `out_of_scope`, `wrong`, `unsafe` and `other`, with `parse` and `word`. `finish_accept(proposal, edits)` returns the proposal with state `accepted` and each edited field set to `by = person` with no `because`; `finish_reject(proposal)` returns it with state `rejected`. `remaining_cells(row)` returns the required `sources.csv` columns that the accepted row leaves empty, in column order, and always `location`, which holds the file name until the lead replaces it with the address of the original. `stale` is computed and never written: the file's state stays `proposed`, and a file that holds `state = "stale"` is read as stale.
2. Core, the screens. `render_show(&Proposal, &Checks) -> String` prints one header line (`Proposal P-0007  new_source  labels public  <file>  12 pages, 0 thin`), then one line for each of the ten fields that has a value (field, value, the `by` of the value, and its quote or id, cut at 72 characters [J]), then the links (`version_of  S-0042 (new version)`, each related unit with its score), then the AI line when `[ai]` exists (calls, and the dropped count), then one line for each label hint (`hint  np-0007  <the support that justifies it>`; a hint is printed and applied by nothing here, and a person who may add the label applies it after the accept with `fieldbook label add`), then `not suggested: source_role (stays unknown), source_family, family_basis, as_of, lifecycle, handling`. `Checks` carries the answers of the pre-checks of step 7, and `render_show` puts one diagnostic line above the header for each failed one. `render_list(&[Header], all)` prints one line for each proposal: id, state, kind, file and pages. `review` and `show` use the same function, so what a person reviews is what `show` prints.
3. `World` gains `stdout_is_terminal() -> bool` beside the `stdin_is_terminal()` and `read_line()` of `new-verbs`, and `rename(&self, audited: &Audited, from: &Path, to: &Path) -> Result<(), Error>` for state-only moves. Disk resolves its private state root and calls `dirs::rename_in_root(&Audited, &RootPath, &Path, &Path)`; both paths must lie in that root, and neither may replace an unrelated existing target. A StateScope yields the Audited token for moving a finished proposal. TestWorld and FaultyWorld forward it. `Disk` uses `std::io::IsTerminal` for the first, `TestWorld` gets `set_stdout_terminal(bool)` beside the `set_stdin_terminal(bool)` and `push_input_line(&str)` that `new-verbs` gave it, and `FaultyWorld` forwards both new methods. `io/queue.rs` is the only code that touches the folder: it lists `queue/` and `queue/done/`, reads headers and whole files, writes a proposal and its staging folder through the atomic helper with a `StateScope` token, and moves a proposal to `queue/done/` with one rename. It also applies a `Vec<PlannedWrite>` of `pipeline-ports`: it reads each entry's bytes by its `source` (`Inbox` from the candidate's file, `Staging` from `staging/<sha256>/`, `Rendered` from the entry) and writes them through the same `io/atomic.rs` writer that `add` uses, under the `Audited` token, in list order; the caller builds `WriteSet { labels, files, affected }` from the `file` of each entry for `Journal::begin`. `io/mod.rs` gets the module line and this card's `StateLine` for `read_state_summary` of `status-command`: `N proposals waiting`, made from `queue::count_waiting`, so the format has one reader. The snapshot of `status` passes unchanged.
4. `adapters/pipeline.rs`: `Stages` owns its parts: `pub struct Stages { pub extractors: ExtractorChooser, pub classifier: Box<dyn Classifier>, pub correlator: Box<dyn Correlator>, pub index: Box<dyn IndexPort>, pub admit: Box<dyn Admit> }`, where `ExtractorChooser` is the function type of `extraction::select`. `staged@1` is not a part of it: `propose.rs` (step 5) uses `staged@1` when a staging folder exists and calls `stages.extractors` otherwise. `Stages::defaults(model: &Model) -> Stages` builds the parts from the core extractors, `rules@1`, `exact-ids+bm25@1`, `Bm25Index::public(model)` (id `bm25f@1`) and `corpus-add@1`. `run_pipeline` passes `stages.index.as_ref()` to every `correlate` call. `run_pipeline(stages, view, candidate) -> Result<Outcome, RunError>` is the one place that sequences the stages. If the view has the hash the outcome is `Present(version id)`. Otherwise it classifies, correlates, runs `validate` from `pipeline-ports` on every suggestion whatever adapter made it, drops each failure and counts it, drops a suggestion for a field that the candidate's `origin` already set (`by = origin`) and counts it the same way, because the owner's declaration beats a guess, and builds the proposal: the kind derived from the separate SourceChoice in pipeline-ports: zero links means New, one preselects Existing, multiple remain Unresolved until a person chooses; keep all correlation alternatives; the `Answers` link becomes the `purpose` entry, which `run_pipeline` builds because a correlator builds no `Suggestion`: `Judged { value: <the question's text, read through CorpusView>, by: <the link's by>, because: <the link's support, as text> }`. A `StageError::Failed` becomes `RunError::Failed(code, stage)`; a `Deferred` becomes `RunError::Deferred(ticket)`. Nothing here names a model.
5. `propose.rs`, `add <folder> --propose [--confirm-public] [--recursive] [--json]`. The folder must be the state folder's `inbox/` or inside it, else exit 2 naming the inbox path; `--source` and `--metadata-only` with `--propose` are exit 2. It walks in the order and with the refusals of `add-folder-mode` (FB0821, FB0400 and FB0410 each give `refused` and one `refuse` event. FB0821 comes first, then the labeller and store admission of `add-folder-mode`, all before the lookup for waiting, rejected and present, so without `--confirm-public` every Corpus file is refused with FB0410). `propose.rs` calls `add::label_context` of `add-new-and-edition` once for the run, and the candidate and the proposal take their `labels` from `labels::for_text` in that context: with the flag, `public` unless a marking is found. With a company store on the machine the flag is refused once, before the first file, with FB0822 (reason `label`) and exit 1; without the flag the candidates there take their labels as `r2-org-intake` step 6 says. For each other file: choose the extraction (`staged@1` when `staging/<sha256>/extraction.toml` exists, so `stage-command` output wins; else call stages.extractors for every supported extension, including CSV and workbooks, and write successful extraction to `staging/<sha256>/`; unsupported extensions use none), then `run_pipeline`. Before the first proposal it asks the gate with `Act::Propose` (step 8): a deny is FB0807, one `refuse` event and no proposal. A hash that already has a proposal in `queue/` prints `waiting`, one in `queue/done/` that was rejected prints `rejected`, and the register prints `present`; none of the three writes anything. A new proposal appends `queue.propose` first (`proposal`, `proposal_kind`, `sha256`, the adapter ids), then writes the file; a journal that cannot be appended writes no proposal and exits 3. A proposal with no extraction is still written and prints `warning   FB0825  <name>` after its line. A `RunError::Failed` prints `failed    <code>  <name>`; a `Deferred` prints `deferred  H-nnnn  <name>`; neither writes a proposal, and the folder goes on. The lines are `proposed  P-0007  new_source  <name>`, `proposed  P-0008  new_version  <name>  (of S-0042)`, `waiting   P-0003  <name>`, `present   S-0042-v2  <name>` and a final `done: 2 proposed, 1 present` with zero counts left out. `--json` prints the document of `add --json` with `"verb": "add --propose"`: besides the words of `add`, a file's `result` is `proposed` (with `proposal`), `waiting` (a proposal for the hash is in the queue; `proposal` names it), `rejected` (it was rejected before; `proposal`), `failed` (`code`) or `deferred` (`ticket`), and `counts` has a key for each word that occurs. The run writes the document to `reports/last-add.json`, as `add` does. Exit 1 if any file is refused or failed, 3 on an I/O error, else 0. `add --propose` writes no file under `corpus/`.
6. `queue.rs`, `queue list [--all] [--json]` and `queue show P-nnnn [--json]`. `list` reads headers only and prints the waiting proposals (with `--all`, the ones in `queue/done/` too). `show` reads the whole file and runs the pre-checks of step 7. `--json` prints one document, `report_version` first. For `list`:

   ```json
   {
     "report_version": 1,
     "verb": "queue list",
     "proposals": [
       { "id": "P-0003", "state": "proposed", "kind": "new_source", "labels": ["public"], "file": "b.pdf", "sha256": "<64 hex>", "pages": 12, "thin_pages": 1 }
     ],
     "counts": { "proposed": 1, "accepted": 0, "rejected": 0, "stale": 0 },
     "exit": 0
   }
   ```

   `queue list --json` reads headers only. A key that does not apply to the kind is omitted (`file`, `sha256`, `pages` and `thin_pages` belong to the file kinds; a `note` has `title` and a `decision` has `spec`). `state` is `proposed`, `accepted`, `rejected` or `stale`. By default only `proposed` and `stale` are listed; `--all` adds `queue/done/`. `counts` always covers every state.

   For `show`:

   ```json
   {
     "report_version": 1,
     "verb": "queue show",
     "id": "P-0007",
     "state": "proposed",
     "kind": "decision",
     "labels": ["public"],
     "candidate": { "file": "D-0002", "sha256": "<64 hex>", "bytes": 512 },
     "checks": [
       { "check": "provenance", "code": "FB0917", "severity": "error", "seq": 40 }
     ],
     "ai": {
       "calls": [ { "seq": 40, "adapter": "handoff@1", "template": "decide@1", "verified": false } ],
       "dropped": 0
     },
     "decision": {
       "spec": {
         "id": "D-0002",
         "question": "<text of the question>",
         "kind": "choice",
         "options": [
           { "id": "opt-a", "label": "<label>", "summary": "<text>" },
           { "id": "opt-b", "label": "<label>", "summary": "<text>" }
         ]
       },
       "adapter": "rules-model@1",
       "pick": { "kind": "choice", "option": "opt-b", "label": "<label>" },
       "confidence": 640,
       "confidence_kind": "stated",
       "rationale": "<text>",
       "evidence": [
         { "unit": "C-0012", "cited": true, "quote": "<text>" },
         { "unit": "C-0013", "cited": false }
       ],
       "flags": ["weak_evidence"]
     },
     "exit": 1
   }
   ```

   `queue show --json` is the proposal file as JSON (the keys of the file, with `report_version` in place of `proposal_version`) plus `checks`, `preview` and `completion`. `preview` is `{ state: "available", files: [{ path, sha256, shown }], affected }` or `{ state: "unavailable", reason }` with a closed reason word (`stale`, `refused`, `unresolved_source`, `kind_not_built`, `completed` or `unavailable`). Available files remain in planned write order, register last. `completion` is absent while waiting, or `{ outcome: "accepted" | "rejected", seq, ids, source_choice? }` from retained proposal/acceptance-intent/journal facts. Completed details never replan an admitted source. The other kinds carry their own table as the file has it: `row` (each field `{ value, by, because }`), `links`, `extraction` for the file kinds, `note` for a note. `checks` lists the pre-checks of step 7 that failed, in order, as `{ check, code, severity, seq? }` with `check` one of `source` (FB0820), `provenance` (FB0917, with the `seq` of the call that did not resolve) and `extraction` (FB0825); a check that passes is not listed. `ai.calls[].verified` is true when `verify_provenance` found the call's `seq` and `output_sha256` in the audit log; it is the one source for the word "verified" next to a model label, and the page shows it only when true. `exit` is 1 when a check is an error. Neither appends an event. `show` exits 1 when a pre-check is an error and 0 for the FB0825 warning.
6a. Queue pages. Add the rows `queue` (`pages/queue.html`: the waiting proposals first, then `queue/done/`, one row for each with id, kind, title, state, labels, extraction and origin) and `queue-detail` (`pages/queue/P-nnnn.html` for each proposal: the queue show report including its available preview or unavailable reason and recorded completion, the pre-check lines and, only for an actionable waiting proposal, the three commands `fieldbook queue review`, `fieldbook queue accept <id>` and `fieldbook queue reject <id> --reason <word>` as chips) to `PAGES`, and the renderers in `fieldbook-render/src/desk/queue.rs`. A `stale` proposal shows "Propose it again." in place of the commands; a proposal with FB0917 shows "unverified origin" and "Accept is refused until the origin resolves in the audit log."
7. The pre-checks, run by `show`, `review` and `accept`, in this order. (1) The `check_source` of the kind's row in `KINDS` (step 9). For `new_source` and `new_version` it reads the candidate's file in the inbox and hashes it: a missing file or another hash is FB0820, and the proposal is stale. (2) For every entry of `ai.calls`, for every proposal kind, `verify_provenance` from `ai-kernel` looks up its `(seq, output_sha256)` in the journal's events, read as `audit show` reads them across all segments: no match is FB0917. (3) A proposal with no extraction is the FB0825 warning. `accept` stops on (1) and (2) with exit 1 and writes nothing; `reject` skips (1) and (2), so a stale proposal can still be rejected.
8. The gate, `gate(world, ctx, act, scope) -> Result<Actor, Refused>`, called first by `review`, `accept` and `reject` with `Act::Accept`, and by `add --propose` with `Act::Propose`. For `Accept` the tests come in this order. (1) Standard input and standard output must both be terminals. (2) The role in `settings.toml` (read by `audit-journal`; `agent` when absent) must be `owner` or `lead`. Either failure is FB0822, exit 1, with a message that says which (`queue accept needs a terminal`, or `role agent may not accept; set role in settings.toml`). These two tests are the personal build's check of who is at the keyboard and they stay when the app is shared; what changes then is where the principal and the role come from, not the tests. (3) `ctx.authz.allow(&actor, act, &scope)`, where `actor` is the one the journal was opened with and `scope` is the content store and the labels of the proposal named (the first waiting one for `review`). A `Deny` is FB0807, exit 1, with the message `error[FB0807]: <act> on <store> is not allowed for this actor`. `Propose` skips (1) and (2), because anyone or anything may propose, and asks only (3). Each refusal appends one `refuse` event (`verb`, `code`, `reason` of `authz` for FB0807, `labels`, and the `sha256` and `name_sha256` of the proposal named, or of the first waiting one for `review`; none if there is none) and nothing else. The `Actor` is returned to the caller for the screen and the journal fills the envelope on its own. Each refusal message, with its `error[FB0822]` or `error[FB0807]` line, goes to standard error and standard output stays empty.
9. `queue accept P-nnnn [--source-choice new|SOURCE-ID]`. `kinds.rs` holds one const table, `KINDS: &[KindRow]`, with a row for each proposal kind that can be accepted. The row type is `pub struct KindRow { pub name: &'static str, pub check_source: fn(&Ctx, &Proposal) -> Result<(), Fb>, pub admit: for<'a> fn(&'a AdmitEnv<'a>, &Proposal) -> Result<Box<dyn Admit + 'a>, AdmitError>, pub after_accept: fn(&Ctx, &Proposal, &StoreLease) -> Result<(), String>, pub describe: Option<fn(&Proposal) -> Vec<String>> }` with `pub struct AdmitEnv<'a> { pub world: &'a dyn World, pub model: &'a Model, pub policy: &'a EffectivePolicy, pub stages: &'a Stages }`; it is `KindRow` and not `Kind` because `fieldbook_core::audit::Kind` exists. `Ctx` is the `Ctx { io, journal, corpus }` of `ai-kernel`, so a row can read the journal (the `decision` row does, for FB0917), and `Proposal`, `Admit`, `AdmitError` and `Fb` are those of `pipeline-ports`. `verify_provenance` needs the journal as a stream of parsed events across all its segments, and `audit-journal` gives only `audit show --last` and `audit verify`. If no such reader exists, set the item to Blocked with `BLOCKED: journal cannot be read as events`, and stop. Do not accept a model-made proposal without the check, and do not parse the journal file in `queue.rs`.
