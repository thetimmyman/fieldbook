# mutation-report

- **Runs where:** home, CI Linux
- **Schema impact:** none
- **Review:** owner

## Outcome

`cargo xtask mutants` runs the pinned `cargo-mutants` over two sets of code and prints one report. Over `fieldbook-calc` it only reports. Over the label, policy, egress and authorisation modules of `fieldbook-core` it is a gate: it exits 1 when a mutant survives that is not in the owner-reviewed skip file `tests/mutants-skip.toml`, and, in the full run, when a skip entry matches no mutant. A pull request runs the gate over the lines it changed (`--changed-since`), so a pull request that touches no gate file passes at once. The weekly run in `scheduled.yml` is the full gate, and it keeps the report as an artifact.

## Why

- The code that decides what leaves a store is written by an agent, and its tests are written by the same agent. A mutation run is a check from outside that: it changes the code in small ways (a `true` for a comparison, a missing `!`) and asks whether any test notices ([ADR 0004, Consequences](../../decisions/0004-company-boundary.md#consequences); control EG-01 in [controls.md](../../controls.md)).
- A surviving mutant is a place where the code can change and no test fails. In `egress::check` that is a refusal that nothing proves.
- Some mutants change no behaviour (for example, a different but equal loop bound). Zero survivors is not reachable on real code without a way to say so. The skip file is that way, and it has three rules: each entry names the mutant without line numbers (`file`, `function` and `replacement`), carries one line saying why behaviour is unchanged, and is reviewed by the owner like the policy crates. An entry that matches no mutant is stale and fails the gate, so the file cannot grow quietly.
- `cargo-mutants` is already listed in [dependencies.md](../../reference/dependencies.md#developer-tools) at a pinned version, due in P5 for the gate and at Day 90 for the report. This card adds the pin to the `[cargo]` table of `.config/tools.toml` (installed with `cargo install --locked`, and in CI at the same version by `taiki-e/install-action`), so that `cargo xtask doctor` checks its installation and exact-source dependency review compares the pin. It adds no crate to the program.
- The `outcomes.json` that the tool writes is the only interface to it, and its shape can change with a version. The fixture is a verbatim copy of a real file, and the ignored test `outcomes_fixture_matches_the_pinned_tool` runs the tool over a demo crate every week and compares, so a bump of the pin that changes the shape fails the weekly job and not a pull request.
- A full run mutates every function of the gate set and runs the tests for each, which is too slow for a pull request. The pull request runs only the mutants on the lines it changed (`cargo mutants --in-diff`), which is what its author can act on. The cost: a test deleted without touching a gate file, and a skip entry that has gone stale, show in the weekly run and not in the pull request. The week is the delay.

## Scope

- Files: `xtask/src/{main.rs,mutants.rs}` (the unit tests are in `mutants.rs`: `xtask` is a binary crate, so an integration test cannot reach `judge`), `xtask/tests/fixtures/mutants/{outcomes.json,skip.toml,skip-stale.toml}`, `xtask/tests/fixtures/mutants/demo/{Cargo.toml,src/lib.rs}` (a crate with its own empty `[workspace]`, never built by the workspace), `.cargo/mutants.toml`, `tests/mutants-skip.toml`, `.config/tools.toml` (the `cargo-mutants` pin, under `[cargo]`), `.github/workflows/scheduled.yml` (one job), `justfile` (one recipe).
- Registration lines: `.github/workflows/ci.yml` (the `mutants` job, its entry in the `needs` list of `ci-ok`, and the `tool:` line of the `rust` job, this card's entries only); `xtask/src/tools.rs` (three edits: the entry of `cargo-mutants` in `TOOLS`, whose length becomes `[Tool; 7]`; its probe `&["cargo", "mutants", "--version"]`; and the sample line `("cargo-mutants 27.1.0\n", "27.1.0")` in the test `versions_are_found_in_each_tools_output`); `docs/reference/dependencies.md` (the `cargo-mutants` row), `docs/controls.md` (the EG-01 row), `docs/decisions/0001-foundation.md` (the AD-08 row `mutants`) and `AGENTS.md` (the Commands line `just mutants`).
- Docs to update: [dependencies.md](../../reference/dependencies.md) (the `cargo-mutants` row: add the command `cargo xtask mutants` and the weekly job), [controls.md](../../controls.md) (the EG-01 row names the artifact `mutants-report` as evidence), [AD-08](../../decisions/0001-foundation.md#ad-08-ci-design) (a row for the job `mutants` in the table), [AGENTS.md](../../../AGENTS.md) (one line: `just mutants`). No `CHANGELOG.md` line: the owner sees nothing new.

## Out of scope

- Mutation testing of any other crate or module. The gate set is the modules named in Outcome.
- Running the full gate on every pull request. A pull request runs it over its changed lines, and the whole set runs weekly. A run on every release tag is not part of this card: whether `release.yml` should also require it is the owner's decision, and adding it later is one job in that file.
- A tool other than `cargo-mutants`.

## Preconditions

- Cards merged: `core-labels` and `core-policy` (the label, policy, egress and authorisation modules of the gate set), `check-ci-and-docs` (the job `changes`, `ci-ok` and `ci_ok_needs_every_job`), `scheduled-workflow` (`scheduled.yml`) and `day1-dependencies-3` (the shared committed-lock Cargo/cargo-deny and exact-source MAX/JEV pin review recipe).

## Steps

1. `.cargo/mutants.toml`: `test_tool = "nextest"` and `exclude_globs = ["**/tests/**"]`. It holds no `examine_globs`: the two sets are the consts `GATE_SET` and `REPORT_SET` of `xtask/src/mutants.rs`, passed to the tool as `--file` flags, so that one list feeds the run, `judge` and `gate_changed`. `GATE_SET` is `crates/fieldbook-core/src/labels/**`, `crates/fieldbook-core/src/policy/**`, `crates/fieldbook-core/src/egress/**` and `crates/fieldbook-core/src/authz.rs`; `REPORT_SET` is `crates/fieldbook-calc/src/**`. No `exclude_re` is used for equivalent mutants: those go in the skip file so that each carries a reason. The tool runs only the tests of the package that holds the mutant, and `test_workspace` stays at its default, so a test that kills a gate-set mutant lives in `fieldbook-core`, and one that kills a calc mutant lives in `fieldbook-calc`.
1a. The tool, by [Adding a crate, a tool or an action](../README.md#adding-a-crate-a-tool-or-an-action). In `.config/tools.toml` add `cargo-mutants = "27.1.0"` under `[cargo]` (the version that the `cargo-mutants` row of `dependencies.md` already holds), with the comment of step 5 above it. In `xtask/src/tools.rs` raise `TOOLS` to `[Tool; 7]` and add the entry (`key` and `binary` `cargo-mutants`, `probe` `&["cargo", "mutants", "--version"]`), and add the sample line `("cargo-mutants 27.1.0\n", "27.1.0")` to `versions_are_found_in_each_tools_output`, so that `cargo xtask doctor` reports the tool and `just setup` installs it; `every_checked_tool_has_a_readable_pin` and `ci_installs_the_pinned_versions` then cover the pin and the workflows. The `dependencies.md` row gets the command `cargo xtask mutants` and the weekly job (Docs to update).
2. `xtask/src/mutants.rs`, the pure part. `Outcome { file, function, replacement, summary }` and `parse_outcomes(json: &str) -> Result<Vec<Outcome>, String>` read the `outcomes.json` that `cargo-mutants` writes: for each element of `outcomes` whose `scenario` is a `Mutant` object it takes `file`, `function.function_name` (an empty string when `function` is null), `replacement` and the `summary` string (`CaughtMutant`, `MissedMutant`, `Timeout` or `Unviable`); the element whose `scenario` is `"Baseline"` is not an outcome, and a baseline whose `summary` is not `Success` is an error ("the tests fail without a mutation"). `Skip { file, function, replacement, reason }` and `parse_skips(text: &str) -> Result<Vec<Skip>, String>` read `tests/mutants-skip.toml`, an array of `[[skip]]` tables; an unknown key, a missing key, or a `reason` that is empty or has a line break is an error that names the entry. `split(&[Outcome]) -> (gate, calc)` sorts by `GATE_SET` and `REPORT_SET`. `judge(gate: &[Outcome], skips: &[Skip], full: bool) -> Verdict`: a `MissedMutant` or a `Timeout` is a failure unless a skip entry equals its `file`, `function` and `replacement` (no line numbers, so an edit above the function does not break the entry); `Unviable` is ignored; `CaughtMutant` counts. When `full` is true a skip entry that matches no outcome is a failure (`stale`); when it is false the run covered only the changed lines, so stale entries are not judged. A failure line is `missed: <file> <function> <replacement>`, `timeout: ...` or `stale: ...`, with the three keys spelt as the skip file must spell them, so that the owner can paste them. `gate_changed(names: &[String]) -> Vec<String>` returns the names that match `GATE_SET`. The calc set is not judged: `report(calc) -> Vec<String>` gives one line for each file, `<file>: caught C, missed M, timeout T, unviable U`.
3. `cargo xtask mutants (--gate [--changed-since BASE] | --report)`, registered in `xtask/src/main.rs`. Each mode runs the tool with `--output <temporary folder>` and one `--file` flag for each glob of its set, reads `<folder>/mutants.out/outcomes.json`, and treats the tool's exit codes 0, 2 (a mutant was missed) and 3 (a timeout) as a finished run, because `judge` decides; any other code (1, a usage error; 4, a failed baseline) stops with the tool's message and exit 2. `--gate` calls `judge(.., full = true)` and prints `mutants: gate ok, N caught, K skipped` or one failure line each, then exits 0 or 1. `--gate --changed-since BASE` takes `git diff --name-only BASE...HEAD`, calls `gate_changed`, and when it is empty prints `mutants: no gate file changed` and exits 0 without starting the tool; otherwise it writes `git diff BASE...HEAD` for those files to `<folder>/gate.diff`, adds `--in-diff <folder>/gate.diff` to the run and calls `judge(.., full = false)`. `--report` prints the `report` lines and `mutants: report, M missed` and always exits 0, unless the tool did not run (exit 2). Each mode also writes what it printed to `out/mutants/gate.txt` or `out/mutants/report.txt`. `justfile`: `mutants` runs `cargo xtask mutants --gate`.
4. `tests/mutants-skip.toml` starts empty, with a header comment that states the three rules of Why and the form of an entry (`[[skip]]` with `file`, `function`, `replacement`, `reason`). A change to this file needs the owner's review, and the PR description says why for each entry. A later card that must add an entry lists `tests/mutants-skip.toml` in its Files, as the cards README says in its Mutation job bullet.
5. `xtask/tests/fixtures/mutants/demo/` is a small crate whose tests catch most of its mutants, miss one (an untested function that returns a `bool`) and make one unviable (a function that returns a type with no default value). `outcomes.json` is a verbatim copy of the file that the pinned tool wrote for it; `skip.toml` has one entry for the missed mutant and `skip-stale.toml` one entry that matches nothing. The tests are in `mod tests` of `mutants.rs` and read the fixtures with `include_str!("../tests/fixtures/mutants/outcomes.json")`: `a_missed_mutant_in_the_gate_fails`, `a_missed_mutant_with_a_skip_entry_passes`, `a_skip_entry_matches_without_line_numbers`, `a_skip_entry_for_another_function_does_not_match`, `a_stale_skip_entry_fails`, `a_stale_skip_entry_is_not_judged_on_a_changed_run`, `a_skip_entry_without_a_reason_fails` (an empty reason and a two-line reason), `a_skip_file_with_an_unknown_or_missing_key_is_refused`, `the_shipped_skip_file_parses` (reads `tests/mutants-skip.toml`), `a_missed_mutant_in_calc_only_counts`, `a_timeout_is_a_miss_unless_skipped` (the fixture text with one `summary` changed to `Timeout`), `an_unviable_mutant_is_ignored`, `the_fixture_outcomes_are_read` (the counts for each summary, and the baseline is not counted), `a_failed_baseline_is_an_error`, `gate_changed_picks_only_gate_files`, `gate_changed_is_empty_for_a_docs_change`, `the_gate_set_and_the_report_set_do_not_overlap`, and the `#[ignore]` test `outcomes_fixture_matches_the_pinned_tool`, which runs `cargo mutants --dir xtask/tests/fixtures/mutants/demo --output <temporary folder>` and requires that `parse_outcomes` gives, for the new file, the same list of `file`, `function`, `replacement` and `summary` as for the fixture. After a bump of the `cargo-mutants` pin run that test, and when it fails copy the new `outcomes.json` over the fixture: this is the one place that changes. Write that sentence as a comment above the pin in `.config/tools.toml`.
6. CI. In `ci.yml` (the recipe "Adding a CI job" in [the README](../README.md#adding-a-ci-job)): a job `mutants` with `needs: [changes]`, the pinned actions, `timeout-minutes: 45`, and a checkout with `fetch-depth: 0`; every step after checkout carries `if: needs.changes.outputs.code == 'true' && github.event_name == 'pull_request'`. The steps install `cargo-nextest` and `cargo-mutants` with `taiki-e/install-action` at the pins of `.config/tools.toml` and run `cargo xtask mutants --gate --changed-since "origin/${{ github.base_ref }}"`. Add `mutants` to `needs` of `ci-ok` and its row to the AD-08 table. In the `rust` job, append `,cargo-mutants@27.1.0` to the `tool:` line of the `taiki-e/install-action` step: the step `Check the tools` runs `just doctor` on every pull request, and `doctor` checks `cargo-mutants` from step 1a on. A pull request that changes no gate file passes in seconds. In `scheduled.yml`, which runs weekly, on `workflow_dispatch` and on a pull request that changes the file: a job `mutants` with the conventions of the other jobs of that file (read-only token, `persist-credentials: false`, `ubuntu-24.04`) and `timeout-minutes: 120`. It installs the same two tools, runs `cargo nextest run --locked -p xtask --run-ignored only outcomes_fixture_matches_the_pinned_tool`, then `cargo xtask mutants --gate`, and then, whatever the gate did, `cargo xtask mutants --report`, and uploads `out/mutants/` as the artifact `mutants-report` (`retention-days: 30`). It is the full gate, and the only run that judges stale entries.
7. Run the full gate once at home (`just mutants`). For each surviving mutant, write the test that kills it, in `fieldbook-core` (step 1). Add a skip entry only for a mutant that provably changes no behaviour, and put the reason in one line. Run again until it exits 0.

8. The shipped skip-file test validates actual entries without requiring emptiness. `an_empty_skip_file_parses` separately covers empty input. Keep owner review, reasons, exact mutant matching and full-run stale-entry checks; accepting an unmatched skip must fail.

## Acceptance

```sh
cargo nextest run --locked -p xtask mutants::
cargo xtask doctor; echo "exit $?"
cargo xtask mutants --gate --changed-since HEAD
cargo xtask mutants --gate
cargo xtask mutants --report
cargo nextest run --locked -p xtask --run-ignored only outcomes_fixture_matches_the_pinned_tool
gh run list --workflow scheduled.yml --branch card/mutation-report --limit 1
just check
```

Expected: the unit tests pass; `cargo xtask doctor` prints an `ok    cargo-mutants` line and `exit 0`; `--changed-since HEAD` prints `mutants: no gate file changed` and exits 0; the full gate prints `mutants: gate ok, N caught, K skipped` with N above 0 and exits 0; `--report` prints one line for each file of `crates/fieldbook-calc/src/` and then `mutants: report` and exits 0; the ignored test passes; the pull request's `scheduled.yml` run is `completed success` with the job `mutants` green and the artifact `mutants-report` attached, and its `ci.yml` run has the job `mutants` green; `just check` exits 0. The `gh run list` line above is evidence only when the `gh` CLI is installed and authenticated: `just doctor` checks the tool pins and is not `gh` authentication. Without it, use the Actions page for the exact branch and commit, record the run identity and result, and inspect the required artifacts there. A successful hosted run is required either way before the card is complete.

Dependency acceptance also requires the actual committed-lock Cargo/cargo-deny and exact-source MAX/JEV pin/profile/release-age evidence of the shared dependency recipe; no deferred command is assumed present.

## Negative control

Record K from the passing full run before the plant. On a branch, add `pub fn never_called(&self) -> bool { true }` to `impl LabelSet` in `crates/fieldbook-core/src/labels/set.rs` and commit it. `cargo xtask mutants --gate` must exit 1 and print a `missed:` line that names `labels/set.rs`, `never_called` and the replacement `false`; `cargo xtask mutants --gate --changed-since HEAD~1` must exit 1 with that line and no other. Add a skip entry for it with an empty `reason`: both runs must exit 1 and say that the reason is missing. Give the entry a one-line reason: both runs must exit 0, and the full run prints K+1 skipped and the changed-only run reports the planted mutant skipped. Change the entry's `function` to `other`: the full run must exit 1 with a `stale:` line and the `missed:` line again, and the changed run must exit 1 with the `missed:` line alone. Remove the function and the entry: both runs exit 0. Then, in `judge`, compare only `file` and `replacement`: `a_skip_entry_for_another_function_does_not_match` must fail. Restore it. Judge stale entries on a changed run: `a_stale_skip_entry_is_not_judged_on_a_changed_run` must fail. Restore it. Count a `Timeout` as caught: `a_timeout_is_a_miss_unless_skipped` must fail. Restore it. Remove `cargo-mutants@27.1.0` from the `tool:` line of the `rust` job in `ci.yml`: the step `Check the tools` must fail with `FAIL  cargo-mutants`. Restore it.

## Rollback

Revert the merge commit. The `mutants` jobs of `ci.yml` and `scheduled.yml`, the entry in `needs` of `ci-ok` and the pin in the `tool:` line of the `rust` job go with it. The report on `fieldbook-calc` goes back to the Day 90 plan, and the label and egress modules have no mutation gate until this card is merged again. Company data is not held in the company store until it has been (P6 precondition).

## BLOCKED

- `cargo mutants` is missing or not the pinned version: run `just setup` and stop if it still fails.
- A mutant survives and you cannot decide whether it changes behaviour: do not add a skip entry. Write `BLOCKED: undecided mutant <file>/<function>/<replacement>` and stop. The owner decides.
- The full gate does not finish in the 120 minutes of the weekly job, or the changed-lines run takes more than the 45 minutes of the pull request job: write `BLOCKED: gate too slow` with the two times and stop. The owner decides whether to narrow the set or to split the run.
- `outcomes_fixture_matches_the_pinned_tool` fails on the pinned version because the shape of `outcomes.json` is not the one step 2 reads: write `BLOCKED: outcomes shape` with the keys that differ and stop.
