# r2-state-and-journal

- **Runs where:** home, CI Linux, CI Windows, owner on laptop
- **Schema impact:** none
- **Review:** owner

## Outcome

On the laptop the program keeps its state at `%LOCALAPPDATA%\Fieldbook\state\` and treats each folder of that data folder as a store with a rule: `overlay\` (the company store) holds the labels the policy lists (with no policy, `public`, `unlabelled` and `marked`), `working\` holds `public` and `unlabelled`, and `state\` holds the same and also `owner-supplied`, which only its logs carry, unless the policy lists more. With no policy, on a machine with a company store, `working\` and `state\` also hold `marked`; under a loaded policy a store holds `marked` only if its `[[store]]` row lists it, and a store with no row holds what the floor gives it without `marked`. A write whose labels its store does not hold is refused (FB0412). The program marks the files it makes not content indexed (`init --overlay` and `restore` mark the store folders, in `r2-company-ids`) and supplies the read of the mark, `winattr::is_marked` and `World::is_not_indexed` (the `check` that fails when the mark is gone, FB0420, is raised only in `r2-company-ids`). It refuses a data folder, a store or a drop folder under a git work tree, or in a place that fails the place test: a sync root, a reparse point, or a network drive where the rule needs a local folder (FB0415). The test is on the folder and never on its name. A company share is valid as a drop source and as a backup target, and is never a live store. `backup` and `restore` cover `overlay\`, `state\` and `working\`; a snapshot records the `labels` it holds and goes through the egress decision once; `restore --drill` checks and fingerprints the restored `overlay\` where it checks `corpus\` at home, in a folder under the data root. The company store has its own regression set, `overlay\eval\regression.toml`, and a question asked there can be promoted into it and into no other file. The file `overlay\store.toml` is read by one parser, `store_toml.rs`, and the journal lists the `store_uid` it holds. A journal folder is read by one name rule, so a copy that a sync client made blocks the append, while the program's own first segment and the folder that `audit verify --repair` makes never do. Drill 5 in the runbook gains the two paragraphs that only this card can write (its chat step already reads `q` and Enter, from the runbook pass before this card), and a Windows CI test runs its PowerShell on a temporary data folder. The owner then runs the whole drill once at the laptop.

## Why

- The folders, the refusal of a git work tree or a failed place test (FB0415) and the attribute are the Data root bullet of [AD-16](../../decisions/0001-foundation.md#ad-16-release-2-shell-and-its-gate); the journal and the backup are its Audit journal and backup bullet; the checks are DR-01 and DR-02 in [controls.md](../../controls.md). On the laptop the journal is the only history (git is not approved there), so a snapshot that left out `state\` could not be checked against its recorded head, and one that left out `overlay\` or `working\` would lose the owner's only copies.
- Which stores exist comes from where the state folder is, and what each may hold comes from the policy, never from `settings.toml`. The preset comes from facts on the machine and never from the name of a folder (`Layout::decide`): a company store (`overlay\store.toml`) beside the state folder, the machine policy file, or a state folder under the user's local application data makes it the laptop's, and anything else is the home layout. On the laptop, a flag or variable that names a state, overlay or working folder other than the fixed laptop folders is refused (FB0419). What a store holds is the `holds` of its `[[store]]` row in the policy, or its floor row when the policy has none ([ADR 0004, section 4](../../decisions/0004-company-boundary.md#4-stores-and-admission)). A line in `settings.toml` cannot widen a store, so an edit cannot move a company item into a store that the company has not approved, and the owner has no store config of their own to widen. The class of an item is its label set, written to its `handling` cell by the labeller, and every write is checked against the store it goes to. Every later use of "which store" (`Candidate.labels`, the proposal kinds that differ by store, the journal's `store`, `backup.toml`) reads the `Layout` and never a path prefix of its own.
- Windows Search would otherwise put company text in an index other tools read (DR-01). The standard library sets the attribute on a file it creates and cannot set it on an existing folder, so the program marks the files it makes and reports the files it did not make; the folder-level mark is the `attrib +I` line the owner already uses for `working\`.
- A journal folder is the one place where two copies of a chain can sit side by side without anyone noticing: a sync client's conflict copy, a person's duplicate. The program's own names are few and exact, so one function names them and any other name that begins with `journal` is a stray. The failure it prevents: a rule that forgot the first segment, `journal.jsonl`, and so refuses every open on the laptop, or one that forgot the folder `journal.broken-<seq>` that `audit verify --repair` makes and so locks the owner out of a journal that was just repaired. The reader that finds a chain's segments uses the same function, so there is one name rule and not two.
- Drill 5 as written ends the chat session with Ctrl-C and expects a stop event. The program cannot catch Ctrl-C (that needs a signal handler, which the program does not install), so a session ends when the owner types `q` and Enter, and `chat-bridge` prints `chat: stopped after N calls`. The runbook's chat step is corrected by the runbook pass that precedes this card, so that the text and `chat-bridge` agree before anyone runs the drill; this card keeps it so with a test (`runbook_drill5_asks_for_q_and_never_ctrl_c`) and writes the two paragraphs that only it can write, the `attrib` warning and the FB0901 refusal.
- The runbook's PowerShell is run by a test, as Drill 4's shell is, so the text and the program cannot drift apart. The test script starts by putting its session in Constrained Language Mode [J], so a command that mode refuses fails in CI and not at the laptop.
- No page, template or string shown in a browser is built here, so there is no Design bullet. The label banner and the hidden copy-context control of DR-01 are pages and belong to `r2-overlay`.
- Review is `owner` because the Acceptance includes Drill 5 on the owner's laptop, which only the owner can run.

## Steps

1. Core, `layout.rs`, pure (no disk, no environment): `StoreCfg { id: StoreId, dir, writable, under_git }`, `Preset { Home, Laptop }` (`#[non_exhaustive]`; it replaces `LayoutKind`) and `Layout { preset, root, state, stores }`. `pick_state(arg, env, local_app_data) -> Option<PathBuf>` returns the first of `--state`, `FIELDBOOK_STATE` and `<local_app_data>\Fieldbook\state`, else none (the caller then uses `.fieldbook/` beside the Corpus). `Facts { store_toml_beside_state, machine_policy_exists, state_under_local_app_data }` is what the caller read from the disk and the operating system, and `Layout::decide(&Facts)` picks the Laptop preset when any one is true and the Home preset otherwise. The name of a folder is never a fact. `fixed_laptop_folders(local_app_data)` returns the one `state`, `overlay` and `working` folder of the Laptop preset as the `LaptopFolders` of `policy-load` (`policy/place.rs`; this card imports the type and defines none), and `flags_allowed(laptop, &fixed, &flags)` of `policy-load` compares the `Flags` that `cli.rs` builds from a `--state`, `--overlay` or `--working` flag with it (FB0419); the resolver passes `layout.preset == Preset::Laptop` as `laptop`. Each preset is one function that builds the `stores` list (`Layout::home(root)` and `Layout::laptop(local_app_data)`, pure, with `under_git` false; `build_state` and the tests call them), so a third preset later (a service) adds one function and one variant and no `match` elsewhere: at home `corpus` and `state`; on the laptop `corpus` (the edition, not writable), `overlay`, `working` and `state`. `under_git` is filled in by `io::layout::resolve`, which probes the disk; the pure tests set it by hand. The methods: `stores()` lists the `StoreCfg` in byte order of id; `roots()` lists the root names of the writable stores in byte order (`corpus`, `state` at home; `overlay`, `state`, `working` on the laptop); `content_store()` is `corpus` or `overlay` and `content_root()` is its folder; `rule(&Policy) -> StoreRule` is `Policy::store_rule(&content_store())`, so what a store may hold comes from the policy and the floor and never from a setting; `default_include()` is `roots()`; `data_root()` is the laptop's folder that holds the stores; `other_registers()` lists the `registers` folder of every other Corpus-shaped store (the edition on the laptop, none at home); `policy_path()` is `<program data folder>\Fieldbook\policy.toml` on the laptop, the folder being the answer of `World::program_data()` (the operating system's known-folder call, never an environment variable), and none at home (where `--policy FILE` exists only in a build with the feature `test-hooks`, see `policy-load`); and `settings_template()` returns the existing text at home and `SETTINGS_TEMPLATE_LAPTOP` on the laptop: `role = "owner"`, `[backup] default = "it"` and one `[[backup.target]]` with `id = "it"`, `kind = "it-location"` and `path = '<folder IT names in its answer to IT-26>'` in single quotes.
2. `io/layout.rs`: `resolve(...) -> Result<Layout, Refusal>` applies `pick_state`, checks whether `overlay/store.toml` exists beside the state folder by calling `policy::company_store_beside` of `policy-load` (the file is tested in one place; the answer is `Facts.store_toml_beside_state`), builds the layout, and for the Laptop preset probes the data root, each store folder and the state folder. `lib.rs` passes `layout.preset == Preset::Laptop` to `policy::resolve` as `laptop`, and `resolve` asks `company_store_beside` itself, so that floor B and the Laptop preset cannot disagree about whether a company store exists. `under_git` is true when any ancestor holds a `.git` file or folder (found with `World::exists`), and the other facts are `World::place(path)`: a `PlaceFacts { reparse, sync_root, network }`. The method, its `Disk` body and the setter `TestWorld::set_place` come from `backup-snapshot`, and `Disk::place` already reads the operating system through `io/win.rs` (`windows-facts`: the reparse tag or junction, the cloud-file attributes of a sync client or a sync-root registration, and a network drive or UNC path), so this card changes neither it nor the setter. A folder is never judged by its name. Each probe goes to `labels::placement(Placement { laptop, under_git, role, facts, declared })`, where `role` is `LiveStore`, `State` or `Drop`. A refusal prints `error[FB0415]: the data folder <path> is under a git work tree` or `error[FB0415]: the data folder <path> is a sync root, a reparse point or on a network drive; Fieldbook keeps its data on the local disk only; a company share is valid as a drop source and as a backup target, not as a live store; move it, or pass --state`, appends no journal line and exits 2 before any file is opened or created (DR-01). `r2-pull-and-sync` applies the same probe to a drop folder. At home no placement test is made, because the state folder is `.fieldbook/` inside a checkout by design; there the rules are the write-time guard of step 4 and the ignore test: `check` on the home layout, when `under_git` is true, reads the checkout's ignore text through `World::read_ignore() -> String` (new here; the `Disk` body reads `.gitignore` and `.git/info/exclude` of the root that `io::find_root` found and joins them with a line feed; `TestWorld` returns what `set_ignore_text` sets), passes it to `labels::fieldbook_is_ignored`, and when that is false reports `error[FB0415]: .fieldbook/ is not named in an ignore file of this checkout` and exits 1. `cli.rs` declares `--state` with `env = "FIELDBOOK_STATE"`, so clap reads it and `std::env` is not named. `World::local_app_data()` is the operating system's known-folder call and is added here (`Disk` calls `io/win.rs`; `TestWorld` returns what `set_local_app_data` sets); `World::program_data()` is the same call and comes from `policy-load`. No environment variable moves a laptop folder. `Disk` also implements the `Groups` trait of `core-policy`: `in_group(name)` calls `io/win.rs` and answers none when the logon token cannot be read, so on the laptop a role comes from the token, and off Windows no group is known. Under the feature `test-hooks` alone, `cli.rs` also declares the hidden `--local-app-data DIR` beside the `--program-data DIR` of `policy-load`; no release profile enables the feature, and `cargo xtask binscan` and the CI build of the release profile fail if it is on. `--help` and `--version` do not resolve a layout. `lib.rs` resolves once per run and gives the `Layout` to `Journal::open`, `backup`, `restore` and the policy loader, and `Roots::of(&layout)` (in `io/root.rs`; it replaces the `Roots::at_home` call of `core-policy`, and the roots then also hold `overlay` and `working` on the laptop) to `Disk::new`: `io/policy.rs` asks `Layout::policy_path()`, so the laptop reads the machine-level file whatever any flag or variable says, and a policy inside `data_root()` or under a `.git` ancestor is FB0414 (`policy-load` already refuses one inside the Corpus or the state folder). `io/state.rs` calls `resolve` instead of its own rule.
3. `io/winattr.rs`: the constant `NOT_CONTENT_INDEXED = 0x2000`; `mark_new(&Layout, &mut OpenOptions)`, which on Windows, for the laptop layout, calls `OpenOptionsExt::attributes(0x2000)` and otherwise does nothing; and `is_marked(path) -> Option<bool>`, which on Windows reads `MetadataExt::file_attributes` and elsewhere returns none. `io/atomic.rs` makes its temporary file through `mark_new`, and the rename keeps the attribute; `io/journal.rs` makes `journal-NNNN.jsonl`, `journal.torn-<seq>` and `lock` through it. If `io_writes_only_through_atomic` matches `winattr.rs`, add that one file to the test's list of two and give the reason in the test; do not move the call.
3b. `store_toml.rs`, pure (`pub mod store_toml;` in `lib.rs`): `StoreToml { store_uid, writer, restored_from: Option<String> }`, `parse` and `render`. The parser denies unknown keys. `writer` is an integer from 0 to 9999, `store_uid` a lower-case version 4 UUID, `restored_from` the `store_uid` of another store, and `render` writes the keys in that order, so `parse(render(x))` is `x`. This card only reads the file; `r2-company-ids` writes it (`init --overlay`), stamps `restored_from` on `restore --to` and refuses on it (FB0836). `World::fresh_uid() -> String` takes its bytes from the standard library's per-process random keys (`std::hash::RandomState`); the uid tells two stores apart and is not a secret. `Disk` answers it, and `TestWorld` returns a fixed value until `set_fresh_uid` changes it. `World::is_not_indexed(path) -> Option<bool>` calls `winattr::is_marked` of step 3, so the attribute is read in one place and answers `None` on a system with no such attribute (`TestWorld` answers from `set_not_indexed` and `None` for a path never set); the `check` that raises FB0420 from it is built by `r2-company-ids`. Tests, in the core `tests/store_toml.rs`, which includes the generator once with `#[path = "../../../tests/support/rng.rs"] mod rng;`: `store_toml_round_trips`, `restored_from_round_trips`, `unknown_key_is_refused`, `writer_above_9999_is_refused`, `uid_must_be_a_version_4_uuid`, `a_missing_uid_is_refused`, and `store_toml_never_panics_on_random_and_mutated_bytes` (the test builds 200 byte strings of length 0 to 256 from `Rng::new(1)` and takes the text of `tests/fixtures/laptop-mini/overlay/store.toml` with each byte once flipped and once deleted; each goes through `String::from_utf8_lossy` into `StoreToml::parse`, and the result is a `StoreToml` whose `render` parses back to itself, or an error that names a key, never a panic).
4. Map the existing write_lease/read_tree_under seam and ordinary shared reads to every Layout root; retain the store-then-journal order and short idle-handle behavior. The journal. `store` has been an envelope key since `audit-journal`; this card gives it its value. `Journal::open` and `Journal::open_for_repair` take the layout, and every event carries `store`: the store of its write set (a write set names one store: `Journal::begin(&lease, &intent, &WriteSet)` is `begin_in(self.layout.content_store(), &lease, &intent, ws)`, and `begin_in(store: StoreId, &StoreLease, &OperationIntent, &WriteSet) -> Result<Audited, JournalError>` stamps `store` on `write.begin` and `write.end`; `build --overlay` and `clean --site` call `begin_in(StoreId::State, ..)`, because they write the derived site under `state`, and other in-store writers keep `begin`; outward writers retain `begin_export` and its bound destination, policy and hashes), or, for an event with no write set (`journal.open`, `ai.*`, `backup.*`, `refuse`), `Layout::content_store()`. No `zone` key is ever written, so there are no old events to keep valid, and `event_schema` stays 1; a later card that adds an envelope key raises it, and the verifier keeps reading every schema it has written. `journal.open` carries `stores`, the `store_uid` of every store the run opened, read from `overlay/store.toml` through `store_toml::parse` of step 3b (empty before a company store exists; a `store.toml` that does not parse stops the run with `error[FB0100]` naming the key, exit 2, before the journal opens). At start the run compares them with the previous `journal.open`: a store that was listed and is not there appends `store.missing` and `check` warns (FB0808). `Journal::begin_in` is also the one door a write passes. Before it appends `write.begin` it calls `labels::admit` with `Policy::store_rule(&store)` (for the content store that is `Layout::rule`) and `labels::git_guard` with the `under_git` of that store; a refusal appends one `refuse` event (`code`, `labels`, `reason` of `store` or `git`) and no `write.begin`, and the file is not touched. The intake cards check earlier and give their own messages; this is the check that holds when one of them forgets. `Journal::open` and `Journal::open_for_repair` also list the audit folder with `audit::names::classify(name: &str) -> Option<JournalName>` (`crates/fieldbook-core/src/audit/names.rs`, pure, with `render(&JournalName) -> String` as its inverse and `is_stray(name: &str) -> bool`). The names the program makes are `journal.jsonl` (the first segment, `Segment(1)`), `journal-NNNN.jsonl` (four digits, 0002 or more, the later segments, `Segment(N)`), `journal.torn-<seq>` (a file: the torn tail that `Journal::open` moved aside, `Torn(seq)`) and `journal.broken-<seq>` (a folder that `audit verify --repair` makes, `Broken(seq)`), where `<seq>` is one to twenty decimal digits; matching is exact and case-sensitive. `lock`, `chat.lock` and every other name that does not begin with `journal` (the prefix test ignores the case of the letters) are not the journal's and are left alone. A name that begins with `journal` and is none of the four is a stray, a copy that a sync client or a person made (`journal (1).jsonl`, `journal-0002 (1).jsonl`, `journal-HOST.jsonl`, `journal-0001.jsonl`, `Journal.jsonl`). The open then fails with exit 3 and the message `the audit folder holds a file that is not part of the journal: <name>; move it out of the folder and run again`, appends nothing, and a repair is refused the same way, because moving a chain aside with a copy beside it would hide the fork. A name that is not Unicode is tested with its lossy form for the prefix only, so it is a stray whenever it begins with `journal`. Which segments make a valid chain is the verifier's to say (FB0800); this check looks at names only. The reader that finds a chain's segments (`io/journal.rs`) calls the same `classify` and keeps the `Segment` names in the order of their number, so there is one name rule and not two. `audit-samples.jsonl` gains a second `write.end` line with `"store":"overlay"`, and `every_kind_has_sample_and_no_free_text` still passes. The callers of `Journal::open` and `Journal::open_for_repair` change with the signature: `io/state.rs`, `backup.rs` and `restore.rs` (Files), `crates/fieldbook/src/audit.rs` and `crates/fieldbook/tests/support/state.rs` (Registration lines). `build_state(dir, events)` keeps its signature and builds the laptop layout of its folder (the parent of `dir` holds `overlay` and `working` beside it) when any event names the store `overlay`, and the home layout otherwise. `grep -rn 'Journal::open' crates` finds no other call.
4a. Known-bad.
