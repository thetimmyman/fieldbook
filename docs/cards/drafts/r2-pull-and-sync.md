# r2-pull-and-sync

- **Runs where:** home, CI Linux, CI Windows
- **Schema impact:** none
- **Review:** owner

## Outcome

`fieldbook sync` reads the company data sources the owner lists in `systems.toml` and turns what it finds into proposals. The first adapter is `file-drop@1`: a folder that the company's own tools fill, which may be on a company share. `sync` lists from a cursor, plans each file with one pure function (`Present`, `NewSource`, `NewVersion`, `Older`, `Duplicate`, `Unmatched`), labels it from the policy's `[[source]]` row (and refuses a stream whose folder lies outside that row's `root`, FB0835), copies each new file to `state\inbox\<system>\<stream>\`, and runs the intake pipeline's deterministic stages. It writes no file under the company store and nothing to the source. A person accepts, one by one or with `queue accept --all --system S [--stream T]` after one confirmation that lists them. `sync --dry-run` shows each file's key, date and planned outcome and writes nothing, `--full` lists the stream from the start, and `overlay-add@1` writes the origin cells, the `series` cell of a vintage stream, the `doc_kind` cell of the stream's row and `supersedes` of an accepted pull. A stream that says `workbook = true` has `values_only = true` written into the extraction of each source it proposes, and the queue says "values only (saved from a workbook)" beside it. `check` raises FB0215 and FB0216 from the origin cells, `doc_kind`, `series` and the version chain (`check/origin.rs`). The failures it prevents are in Why.

## Why

- Company data lives in other systems, and typing it in is why a knowledge base goes stale. One port, `Pull`, serves a public feed and a system-of-record read alike, because they differ only in the labels of what they read, and that belongs to the policy's `[[source]]` row ([ADR 0004, section 8](../../decisions/0004-company-boundary.md#8-sync-the-pull-port)).
- Proposals only. A sync that wrote sources would put a bad export into the evidence without a person. The failure it prevents: a half-saved quote letter replaces the current one.
- `Older` is a rule because someone drops last month's file into a share again, and without it that file would supersede this month's.
- `versioning` and `as_of` have no default. A wrong guess is silent: a `vintage` stream declared for revisions would leave two current quote letters side by side.
- The cursor is only a saving. The hash and the key decide what is new, so a lost or damaged cursor costs one re-list and cannot cause a duplicate.
- The labels come from the policy and never from the file's content or a model. A system with no `[[source]]` row labels everything `unlabelled`, and nothing leaves. The failure it prevents: a model that is asked what a quote letter is allowed to be, and answers `public`.
- A source id is bound to a folder tree, the `root` of its `[[source]]` row. A stream whose folder lies outside it is refused (FB0835) and journaled with the reason `root`. The failure it prevents: the owner repoints a source id whose default is `public` at any folder, and everything in it arrives as public. The id alone is a name; the folder is the fact.
- A pulled file is transit content bound to its destination company store. Check that store before copying or proposing it; State holds applies separately to logs and retained calls. Backup and outward export still evaluate the effective labels of every included item.
- `sync` makes no call to a model. The rules classifier and the exact-id correlator run, and `queue ingest` can add more later, under a policy row. So `sync` is a deterministic verb, and a run with a model endpoint configured sends nothing.
- `file-drop@1` never writes to, moves or deletes anything in the source. The company's own tools own the folder.
- A workbook saved as CSV keeps the numbers on display and drops the formulas, and a manual-calculation setting or a stale cached cell can leave a wrong figure on display (R-13). `sync` cannot tell from the file, so the owner says it once per stream with `workbook = true`; each CSV source of that stream then carries `values_only = true` in its extraction and is shown as "values only (saved from a workbook)" in the queue, on the source page and in the title of its text. A `.xlsx` or `.xlsm` file needs no such word, because `xlsx-sheets` reads the stored value and flags a workbook with manual calculation. The failure it prevents: a price taken from a stale export is read as if a formula stood behind it.
- The origin cells are one rule in one place. `check/origin.rs` holds `cell_problem` (the three origin cells of one row), `kind_problem` (`doc_kind` and `series`) and `class_problem` (the versions that share an origin key), and `r2-records` calls the first for its record versions. The failure it prevents: `sources.csv` and a records file that disagree about what a valid origin is.
- `series` is written by `sync` and may be changed by a person, and it is not a key of `systems.toml`: the files of a vintage stream are separate sources that belong together, and the stream id is the one name they all share, so `series` holds it. A revision stream is one source with versions and has no series. The failure it prevents: a series name typed by hand differently in two places, and a vintage that does not join.

## Out of scope

- An adapter that needs the network, a database or a report (`later-company-source-read`). It has `Needs::Net`, is built only with the feature `net-pull`, which its own card adds, passes `GuardedPull` and has its own card with Review owner. It reads its credential from the Windows credential store through a `Secrets` port; the environment variable is for the home preset only. `file-drop@1` needs no credential, and a secret never appears in `systems.toml`, the journal or an error line.
- Turning a stream's file into typed records. A stream with `load` is not pulled here: `sync` prints `stream <id>: load is built by r2-records` and goes on (`r2-records`).
- A scheduler. Fieldbook installs none; a task the company already runs may call the verb.
- Reading text out of a PDF or a Word file (`later-pdf-native-ocr`, `later-docx-import`). Such a file is preserved, hashed, labelled and proposed with no extraction, and the proposal says `needs-extraction`.
- A source file that disappears from a drop folder. Nothing in the store changes.
- A per-file ledger. A changed folder digest re-reads every file of that stream's folder, and the hash keeps that safe. A stream of thousands of files is the reason to add a ledger, and it is not built here.
- Who may read which source (`later-source-access`) and a journal line for each read of a source (`later-read-audit`).

2. Contract suite P, `tests/support/pull_suite.rs`: the function `pull_suite(make)` takes a constructor of an adapter over a fixture folder. 6. `sync/plan.rs`, pure. `OriginIdentity { system: String, stream: String, key: OriginKey }` and `plan(&StreamCfg, Option<(&Matched, &OriginIdentity)>, &Sha256, &Held) -> Outcome` with `Outcome { Present, NewSource, NewVersion { base }, Older, Duplicate, Unmatched }` and the const `OUTCOMES`. OriginIdentity copies system and stream from the validated configuration ids (vocab::stream_id_form); no new id grammar is introduced. `Held::build(rows, store_keys, proposals)` reads the origin cells, hashes, versions and `as_of` of the company `sources.csv`, the hashes of the other stores (the edition), and the header of each proposal in `queue/` (waiting) and in `queue/done/` (rejected) with its origin and hash; a stale or accepted proposal counts for nothing. `Held::note_proposed(identity: &OriginIdentity, hash: &Sha256)` records an item that was proposed, or that a dry run would propose, so that two files with the same bytes in one run give a proposal and a `Duplicate`, and the dry run and the real run print the same outcomes. The rules, in order: no match is `Unmatched`; the hash held under this origin key (or by a source that has no origin, or in another store) is `Present`, and so is the hash of a waiting or rejected proposal with this key; the hash held under another origin key, by a source or a proposal, is `Duplicate`; a known key in a revision stream whose `as_of` is earlier than the current version's (compared as the first day of the date) is `Older`; a known key with new bytes is `NewVersion { base }`, where `base` is the current version id; otherwise `NewSource`. `origin_key(stream, matched)` is `{key}` in a revision stream and `{key}@{as_of}` in a vintage stream, built with `OriginKey::new`, so the limit of 200 bytes holds for the whole cell and a key that its date suffix pushes over it is refused as FB0833 with its length and no text.
