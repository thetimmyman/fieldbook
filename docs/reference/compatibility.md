# Published compatibility

The published manifest protects the meaning of stored calculations, requests and adapter versions. The check is `cargo xtask compat --base release-baseline.toml`; adding a new version never rewrites an old binding. The [recurring recipe](../cards/README.md#published-compatibility) registers additions here.

## Published manifest

`compat/published.toml` is strict TOML with `compat_schema = 1`, `calculation_epoch` (positive u32), `case_set_sha256` (full lowercase SHA-256), and sorted `[[binding]]` rows. Unknown keys, duplicate identities, missing fields and unsupported schemas refuse. Epoch/case-set metadata is separate from immutable version rows.

Each binding has `kind` (`calculation`, `run-schema`, `adapter`, `template` or `schema-keyword`), `id` (the complete versioned id), `runner` (one of those same words), and nonempty `files`. An adapter also has `port`; all other kinds forbid it. Identity is `(kind, port-or-absent, id)`, so two ports may retain the same adapter id without colliding. Every id ends in `@` and a positive decimal version. The runner must match kind.

Each `files` entry has `role` (`implementation`, `contract`, `input` or `expected`), `path` and `sha256`; input and expected entries also have the same `case` id. There is exactly one input and one expected file per case, at least one case, one contract and one implementation entry per binding. Paths are dedicated per-version files: nonempty slash-separated repository-relative paths with no drive prefix, absolute path, dot/parent component, symlink or duplicate. Hashes cover whole file bytes and are full lowercase SHA-256. Do not hash a whole shared registry or use movable line ranges. Sort bindings by identity and files by role, case and path. The shared parser returns `Published { calculation_epoch, case_set_sha256, bindings: Vec<Binding> }` with validated `BindingId`, `RunnerKind` and `BoundFile` values; `bound_files()` yields the sorted distinct path/hash set and rejects conflicting hashes for a path. Archive collectors consume that output, not another parser.

The first bindings are calculation `build_up@1`, calculation `children_sum@1` and run-schema `canonical-run@1`. Their implementations live in dedicated `crates/fieldbook-calc/src/versions/{build_up_v1,children_sum_v1,run_v1}.rs` files, reached through the existing calculation/run dispatch. Contracts and historical inputs/expectations live under `compat/calculation/build_up@1/`, `compat/calculation/children_sum@1/` and `compat/run-schema/canonical-run@1/`. Calculation inputs are a strict compatibility-only `ReplayCase { replay_schema: 1, calculation_epoch: u32, case: Case }` envelope: positive epoch, existing strict Case, unknown fields denied at both levels. Expectations use the full canonical Run bytes or exact refusal code. Ordinary Case files gain no replay metadata. Run-schema inputs are complete typed Runs; expected files contain their canonical bytes. Include positive and refusal vectors for each calculation. Shared registries may grow without changing these files. The first manifest binds all these files; a row that lacks its current registered version or vector pair fails coverage.

## Executing historical vectors

One runner registry in xtask dispatches `(RunnerKind, BindingId)` to the currently built implementation. Calculation runners parse the archived ReplayCase and call `evaluate_replay(&ReplayCase)`, which supplies its pinned epoch to the same current version lookup used by ordinary `evaluate(&Case)`. The ordinary entry uses current CALC_EPOCH. The runner compares the full canonical result or refusal to the archived expected bytes; it neither strips nor rewrites the epoch. The run-schema runner calls the retained canonical version. Later adapter, template and schema producers add their typed runner, fixtures and version rows together, before publishing them. An unknown runner/id refuses; it is never a skipped test. Synthetic runner hooks test future categories before those producers exist.

The guard reads the prior manifest and files from the descriptor's exact commit, verifies every bound hash, compares old identities and files with the candidate, then runs the archived inputs through current dispatch against the archived expectations. Changing current code and goldens together cannot bless changed historical output. A new version leaves old implementation and vectors executable. A deliberate removal requires the owner-reviewed migration recipe. Before baseline comparison, recompute the full current case-set SHA-256 with the calc-cases EPOCH ordering/encoding and require the published digest to match it and the published epoch to equal compiled CALC_EPOCH. EPOCH retains its 16-hex digest. Changed case-set metadata requires an epoch strictly greater than the prior compatibility epoch.

## Baseline descriptor

`release-baseline.toml` is strict TOML with `baseline_schema = 1` and exactly three tables: `[compatibility]`, `[tool]` and `[edition]`. Each has `kind = "empty"` or `kind = "release"`. Empty forbids all other fields. Release requires `tag`, full lowercase 40-hex `commit` and full `archive_manifest_sha256`. A release compatibility table also requires sorted `[[compatibility.file]]` path/hash rows for `compat/published.toml` and all its bound public blobs. Tool and edition forbid file rows; their archive manifests identify the exact payloads. Tool tags start `v`, edition tags start `edition-`; compatibility may name either stream. Missing declared history or material refuses and never means empty. The initial descriptor has three explicitly empty tables.

The parser returns `Baselines { compatibility: Option<CompatibilityBase>, tool: Option<ReleaseBase>, edition: Option<ReleaseBase> }`. Compatibility retrieval verifies the exact tag/commit and reads blobs from the full-history checkout; archive verification additionally checks the corresponding durable archive manifest. It uses no stored archive address or credential.

Every accepted release advances compatibility to its verified archived manifest and vectors. Tool acceptance advances tool and preserves edition. Edition acceptance advances edition and preserves tool; raw and rendered editions share this stream. An acceptance that publishes both tags advances both only after both archives verify. The owner-reviewed advancement happens before another implementation card merges and does not change the tagged descriptor.

Archive verification selects the predecessor for its stream. A tool archive with an empty tool binding rehearses its current packaged smoke and synthetic restore fixture even if compatibility already names a raw edition. An edition archive with an empty edition binding inspects its current pair. A nonempty stream binding requires its exact previous archive; the other bindings do not substitute for it. Migration uses the tool binding and the Corpus and date of that tool commit.
