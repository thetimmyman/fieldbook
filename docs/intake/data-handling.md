# Fieldbook data handling statement

Edition {edition}. Tool version {tool_version}.

This statement says what data Fieldbook touches, where it lives, when it leaves, and how it is deleted. It claims no certification and no compliance status under any scheme. It describes the files in this edition (Tier 0: files only). The sections on the program (from R2) say what the installed program holds, where, and when any of it leaves: company data stays in the company store, under labels that the company's policy file defines, and leaves only through a destination that file names.

## 1. Labels

| Label | What it is | Where it lives | Rule |
|---|---|---|---|
| `public` | Public sources, summaries of them, and synthetic examples | In the edition, in the `originals\` folder and in the source repository | The only data Fieldbook ships. Every example number is marked synthetic |
| A company label | Data that the company's own label table names, such as a vendor quote under an NDA, a bid cost build, a specification, a transaction or a project schedule. The labels are opaque codes that IT defines in the policy file (IT-33, IT-34) | Only in the company store (`overlay\`) on the laptop, and only if the policy's row for that store lists the label. The owner's own notes typed into the fillable workbooks sit in `working\`, under the labels that store may hold | Company data never enters an edition or a source repository, and nothing carries it back to the owner's home equipment or to GitHub. At Tier 0 Fieldbook does not read these files. The program sends it only to a destination that the policy names for that label: an AI endpoint, the Handoff pack, the chat Bridge, an export, a backup or a print (IT-27) |
| A controlled category | Controlled unclassified information, export-controlled technical data, source selection information, third-party proprietary data. It is one or more company labels like any other | Only where the company has authorised this laptop, this store and the owner's access for it | Held in a store only if the policy's row for that store lists the label. With no policy file, a laptop with a company store holds a file with such a banner as `marked`, for the owner's own use, and sends it nowhere. The tooling never classifies, and never strips or edits a marking. A file with such a banner is refused by the public Corpus and given a label in the company store. Fieldbook makes no claim of compliance or authorisation under any scheme |
| `unlabelled`, `marked` and `owner-supplied` | Built in. `unlabelled`: nothing could say what a text is. `marked`: a marking or a source's own label was found and no rule of the policy maps it. `owner-supplied`: text the owner typed or pasted at a prompt | `unlabelled` and `marked` in a store whose row lists them; with no policy file, `unlabelled` in `overlay\`, `working\` and `state\`, and `marked` there too on a machine with a company store. `owner-supplied` is never stored on a page, a source version or a record; only the question log and the call records in `state\` carry it | `marked` goes to no destination, and `unlabelled` goes to none but the backup folder that the owner recorded as company storage when no policy is loaded. No policy row can list either. `owner-supplied` goes to Handoff and to a destination whose row lists it |

Fieldbook does not decide what a document is. It looks for banner shapes, for the labels a source gives its own files and for the path rules in the policy. On public intake it stops at a banner. On company intake it gives the file a label and holds it. A person remains responsible for what they type into a working copy.

The Corpus holds finance and contracting reference material. The public Corpus needs no technical data, drawings, specifications or test data, and none belongs in it. Company specifications, drawings and files that the company authorises Fieldbook to read are synced into the company store, under labels, and searched there.

## 2. Where data rests

| Place | Holds | Label | Notes |
|---|---|---|---|
| Owner's personal development equipment | Working copy of the source repository | `public` | Not employer equipment or network |
| Private repository on GitHub | Source repository and release files | `public` | Hosted build runners are used for builds and tests |
| The transfer channel | The two zips and their hash list | `public` | Chosen and operated by IT |
| `%LOCALAPPDATA%\Fieldbook\edition\` | The site, registers, templates | `public` | Replaced whole by each new edition |
| `%LOCALAPPDATA%\Fieldbook\originals\` | Byte-exact public documents; HTML and SVG kept as `.txt` | `public` | Replaced when sources change |
| `%LOCALAPPDATA%\Fieldbook\working\` | Copies of templates the owner fills in | The labels the policy lets this store hold | Outside the edition folder so a new edition never overwrites it. Mark it not content-indexed (see README.txt) |
| `%LOCALAPPDATA%\Fieldbook\overlay\` (the company store, from R2) | Pages, source versions and typed records (quotes, estimates, rates, transactions), and the originals synced from company data sources with their extracted text and search index | The labels the policy lets this store hold | Created by `init --overlay`. Marked not content-indexed. Not in git or a synced folder (FB0415). Backed up with the rest (section 5) |
| A company data source (from R2) | The company's own files and exports that the owner can already read, such as a folder that the company's tools fill | The source's own labels, mapped by the policy | Read only: Fieldbook reads as the owner's account and writes nothing to the source. Nothing is read until the owner lists the source in `systems.toml` |
| `%LOCALAPPDATA%\Fieldbook\state\` (the program, from R2) | The schema-validated audit journal holds no content; invalid files and repair archives may contain arbitrary fields. In the AI build, call records: the prompt and reply of each AI call | No content labels for schema-valid journal events; invalid bytes need classification. Call records keep the request labels | Call records hold company text, so they carry the labels of the request and sit in the data root. They are kept 30 days at home and are off on the laptop until IT answers IT-31; the company sets the retention, and the policy's `model` row can cap it. IT may collect the journal (IT-26) or have it exported (IT-35) |
| An endpoint IT approved (the AI build only) | The prompt of each call: a context pack and the owner's question | Only the labels that the policy's row for that endpoint lists (IT-27, IT-33) | What the endpoint keeps is the operator's. Nothing is sent until IT approves an endpoint |
| Edge's storage for local pages | localStorage: Day-N start date, display preferences and named-pack metadata (name, unit ids, view fingerprint). sessionStorage fieldbook.ask: the typed question, scope, context ids and thread notes for one page transfer | Pack ids and preferences are metadata; the typed question and notes are owner-supplied text and may contain company information | No unit or record bodies or answers are stored. The Assistant page removes fieldbook.ask when it reads it. Pages work without storage. Browser data is cleared through IT's browser procedure |
| Paper | The printed day-one binder | `public` | Public content only |

The folder is under the user's local application data, not Documents or Desktop, so OneDrive folder redirection does not copy it. A live store, the state folder or a drop folder inside a git work tree or a synced folder is refused (FB0415), because a sync client would carry company text out of the store. A company share is never a live store or a state folder, because a sync client writes conflict copies of the journal. It is valid as a source to read from, and as a folder that the program writes to on the owner's command (a backup, an export, a restore into an export folder, or a journal export) when the policy allows that folder (section 3). The data root stays `%LOCALAPPDATA%\Fieldbook\` and cannot be pointed at a synced path. At rest, files rely on the laptop's disk encryption and file permissions. Fieldbook adds no encryption of its own and holds no keys, passwords or accounts. A store holds only the labels that the policy's row for it lists. With no policy file, `overlay\`, `working\` and `state\` hold `public` and `unlabelled`, and `marked` too on a machine with a company store; `state\` also holds `owner-supplied` (its logs); and a text with any other label is refused (FB0412).

## 3. What leaves the laptop

In the silent build, and in this edition and every tool version before 0.2.0, nothing leaves it by any action of Fieldbook, apart from the files the installed program writes on the owner's command to a place the policy allows: a backup, an export or a journal export (sections 5 and 7). Those are file writes to a folder, not network requests; if the folder is a share, the operating system's file-sharing client carries them. The files in this edition make no network request in the interactions tested (see `network-silence.md`). No file is written outside the data folder. There is no export, upload, sync, telemetry or crash report in this edition.

In tool versions before 0.2.0, and in the pages of a later edition, one user action is outside Fieldbook's control: the owner may copy a context pack, a block of public Corpus text plus the owner's question, into an assistant that IT has approved. The page checks the question for marking banners first and refuses on a match. From 0.2.0 the AI build adds one action Fieldbook performs: when the owner runs `ask`, it sends a prompt of the same kind to the endpoint named in the settings and in the policy file. The labels of every part of the prompt are checked first against the policy's row for that endpoint (the company lists them; with no row nothing is sent, IT-27 and IT-33), the question is checked for marking banners, and an audit line is written before anything is sent. What the endpoint keeps is the operator's, and IT-27 asks IT to approve it. What the owner types in the question is the owner's responsibility. See `ai-development-statement.md`.

## 4. Retention and deletion

- A new edition replaces `edition\` whole. The previous zip is the rollback.
- Deleting `%LOCALAPPDATA%\Fieldbook\` removes that folder. At Tier 0 there is no installer or registry entry. Clear Fieldbook page storage separately through IT’s browser-clearing procedure; folder deletion does not clear it or promise secure erasure.
- Deleting files on a solid-state disk does not overwrite them. Sanitisation follows the laptop's disk-encryption policy, such as destroying the key. Fieldbook promises no secure overwrite.
- `working\` is the owner's. It is not touched by an edition update or by removal of `edition\`.
- `overlay\`, the company store, holds records that the company may have to keep. Fieldbook deletes none of them. It purges only call records, by the retention in the settings, capped by the policy. Retention schedules and legal holds are the company's. Deleting the data folder deletes the company store, so the company's backup (section 5) is the copy that survives.

## 5. Backup and restore

**Tier 0 (files only).** No program runs, so Fieldbook makes no backup. The only data that cannot be rebuilt is `working\`, the owner's copies of workbooks, CSV files and notes. `edition\` and `originals\` come from the two zips, and the previous zip is the rollback. The owner copies `working\` to a place IT's policy covers (IT-26) and compares hashes with `Get-FileHash` (IT-23); README.txt and the transfer runbook give the commands, and the Windows drill runs them. After you approve a decision package, use Save As to keep a dated copy of the approved workbook alongside the working copy.

**From the program (Day 1 at home, R2 on the laptop).** `fieldbook backup` copies the data folders to a target folder named in `settings.toml` or on the command line: `overlay\` (the company store, with its records and the originals synced from company data sources), `state\` and `working\` on the laptop, and `corpus/` and `.fieldbook/` at home. A snapshot carries the labels of everything in it, and the policy's `backup` row for the target must allow every one of them (FB0901). The target is a location the company names (IT-26). A snapshot is a folder of plain files with a `SHA256SUMS` list and a `backup.toml`. `backup verify` re-hashes it, and `restore --drill` restores it into a temporary folder, runs `check --strict` and `audit verify`, and deletes the folder. `restore` never writes over live data: it fills an empty folder, either inside the data folder or, as an export, in a folder that an `export` row of the policy lists with every label of the snapshot, and the owner swaps the folders. The program keeps the newest seven snapshots and the newest of each of the last four weeks, and removes a snapshot only after a newer one has verified.

In the silent build and the AI build alike, `backup` and `restore` start no process, install no scheduled task and make no network connection. A schedule belongs to IT's backup tooling or to a task the owner adds, and either can read the program's exit codes. If IT's tool copies the data folder itself, `backup verify --raw` checks the copy it restores. A target on a synced folder gets a warning unless the setting declares it. A target with `include = ["audit"]` collects the journal only. Schema-valid events have no content fields; invalid journal or repair bytes can contain arbitrary content and require classification and an allowed target. The include setting does not make invalid bytes content-free. Where the target should be, and how it fits IT's backup, is question IT-26. Until IT answers, the default target is a folder on the same disk, which protects against a bad edit and not against losing the laptop. A target is valid only if the policy has a `backup` row whose `paths` hold it and whose `allow` covers the labels of the snapshot. A store that holds `unlabelled` or `marked` text cannot be backed up under a policy, because no row can list those two. The owner gives `unlabelled` text real labels with `label add`; `marked` text keeps that label until the policy maps its marking and `label reapply` runs. `audit export` writes the journal's lines and a manifest to the folder that the policy's `[audit]` table names (IT-35). It is a file write, and IT's own tools collect the files.

Source files, hashes and formats are open (Markdown, CSV, TOML, plain text), so the data outlives the tool.

## 6. Markings, controlled data and export control

- Fieldbook never classifies and never strips, edits or hides a marking found on a document.
- Public originals are kept byte-exact, with their markings.
- The Corpus is public information and synthetic examples, so it holds no technical data. The company store may hold the company's technical data, specifications and files, where the company has authorised that storage and the owner's access to them. Fieldbook gives them labels and applies the policy. It does not decide whether a document is controlled, and it makes no claim of compliance. No cloud service is added. There is one user now. A second user arrives only with the company application, with identity from the company, and that is a later change with its own questions for IT.

## 7. Logs and diagnostics

Tier 0 files produce no logs.

The program (Day 1 at home, R2 on the laptop) keeps one local audit journal in its state folder: an append-only file with a hash chain, checked by `fieldbook audit verify`. An entry records that something happened and names it by id, hash, count, role or a word from a closed list. It covers every write to the Corpus or overlay the program makes, every refused write, every call to an AI service (the adapter, the model id, hashes of the prompt and the output, and the ids of the context), every acceptance or rejection in the review queue with the role that made it, every question asked (as a hash), every backup, restore and settings change, every change to the policy file in force or to a label, every sync run (the source, the stream and counts), every call to the tool server, and every export of the journal itself. Every entry names who did it, the role, the store and the way in (the command, the page or the tool server). Designated egress authorization and outward-write entries carry labels, destination and the policy hash used for authorization. The next journal-writing operation records a changed policy observation with `policy.change`; read-only commands append nothing. Ordinary in-root writes and refusals do not acquire a policy field. No entry holds content: no file text, no question, no prompt, no answer, no file name or path, and no label title or counterparty name: a label appears by its id. A test rejects an entry with any other field.

The journal does not record a page opened in Edge, a file edited by hand, or the developer tools' build steps. It does not stop someone who can rewrite the whole file; the length and head recorded in each backup show that. So does a copy of the journal that IT collects with `audit export` into the folder its policy names (IT-35): IT compares the exported head with `audit verify --anchor-seq N --anchor-head HEX`. The journal does not see a screenshot or a copy made by hand. A separate question log holds the text of the owner's questions so a missed question can become a test. It lives in the state folder, is labelled `owner-supplied` on the laptop, never leaves it except in a backup that the policy allows, and can be cleared, reduced to hashes or turned off in `settings.toml`; that setting does not affect the journal. The silent build sends nothing anywhere. The AI build sends only a request to an endpoint IT has approved, and each one is in the journal first (`ai-development-statement.md`). IT may collect a schema-validated journal under its handling rules. An unvalidated journal is not assured content-free. If `fieldbook audit verify` reports a broken chain (FB0800 or FB0801), the owner runs `fieldbook audit verify --repair`. It moves the whole journal, unchanged, into a folder `journal.broken-<seq>` beside it, where `<seq>` is the number of the first bad line, starts a new chain whose first entries name the last good line, and prints a warning that names the folder (FB0804). Nothing is deleted or merged, the old entries stay readable in that folder, and backup remains conditional on classification and the target’s allowed labels. Repair preserves original bytes, including invalid or free-text fields. An unvalidated journal or repair archive is not assured content-free; IT collection follows the company’s handling rules. Schema-invalid bytes contribute unlabelled to backup, while a schema-valid chain-hash failure alone does not add content labels; the length and head that each backup recorded can be compared with the old file.

## 8. Cryptography

Fieldbook uses SHA-256 only to check file integrity. Integrity checks on the laptop use `Get-FileHash`, which is part of Windows. At home the tools use a pure-Rust library for the same hash. That library is not a validated cryptographic module. Fieldbook does no encryption, signing or key handling in this edition. The AI build (from `v0.2.0`) adds TLS from a maintained library for its endpoint calls, a random per-session secret for the chat page, and reads an endpoint key from an environment variable without writing it to a file (IT-28).

Terminal presence, a writable role setting and Git author text are accidental-use checks and attribution, not proof of a human identity. The agent must not run acceptance, label changes or certification; consequential decisions use the owner review flow outside these writable settings. The scripted PTY drill tests mechanics and grants no authority to approve real work.
